## Findings

**1. In-memory is the default in every major framework; persistence is an added layer.**
- FACT: LangGraph says persistence "matters when an agent needs to continue a conversation, resume after an interruption, recover from a failure, or remember information across interactions," and splits it into *checkpointers* (thread-scoped short-term state) and *stores* (cross-thread long-term memory). Source: LangGraph "Persistence" — https://docs.langchain.com/oss/python/langgraph/persistence
- FACT: The OpenAI Agents SDK "built-in session memory" (`SQLiteSession`) exists to avoid manually re-sending `.to_input_list()` history between runs. Source: OpenAI Agents SDK "Sessions" — https://github.com/openai/openai-agents-python/blob/main/docs/sessions/index.md
- FACT: Microsoft's Agent Framework treats durability as an *extension*: "An ordinary Agent Framework agent runs in-process: its conversation history lives in memory and is lost when the process ends." Source: "Durable agents" — https://github.com/microsoft/agent-framework-durable-extension/blob/main/docs/features/durable-agents/README.md

**2. When frameworks add persistence, they route *production* to databases, not flat files.**
- FACT: LangGraph's own checkpointer table: `MemorySaver`/`InMemorySaver` = RAM, "lost" on restart; `SqliteSaver` = "Ideal for experimentation and local workflows… local file-based storage for development"; `PostgresSaver` = "used in LangSmith. Ideal for using in production." Source: "Checkpointers — Checkpointer libraries" — https://docs.langchain.com/oss/python/langgraph/checkpointers
- FACT: OpenAI Agents SDK's built-in session backends: `SQLiteSession` is the default "local development and simple apps" backend; the documented paths to shared/multi-process memory are `RedisSession` ("shared memory across workers… low-latency distributed deployments"), `SQLAlchemySession` (Postgres etc.), `MongoDBSession` ("horizontally-scalable, multi-process session storage"), and `DaprSession`. Their operational guidance: "Use in-memory SQLite for temporary… file-based SQLite for persistent… Redis for shared, low-latency session memory… MongoDB for multi-process, horizontally-scalable storage." Source: OpenAI Agents SDK "Sessions — Built-in session implementations / Operational patterns" — https://github.com/openai/openai-agents-python/blob/main/docs/sessions/index.md
- FACT: Microsoft durable agents persist session state in "external storage" (Durable Task / Azure Storage) specifically to get "multi-instance scale-out — any worker can resume a session," crash recovery, and human-in-the-loop waits of "days/weeks with zero compute." Source: "Durable agents" — https://github.com/microsoft/agent-framework-durable-extension/blob/main/docs/features/durable-agents/README.md

**3. Documented scaling cost of checkpoint-style run state: unbounded growth, solved by pruning and delta storage.**
- FACT: "Over long conversations, checkpoints accumulate. This can increase latency and storage costs. Fix: prune old checkpoints or set a retention policy." Source: LangGraph "Persistence — Troubleshooting" — https://docs.langchain.com/oss/python/langgraph/persistence
- FACT: By default "checkpoints write the full value of every state channel at each super-step"; `DeltaChannel` stores only deltas, making checkpoint blobs "O(1) per step instead of O(N)… at the cost of… storage-vs-latency tradeoff." Source: "Checkpointers — Optimize checkpoint storage" — https://docs.langchain.com/oss/python/langgraph/checkpointers
- FACT: LangGraph's custom-checkpointer guidance says "get by id" must be "O(1) or close to it"; "A scan with a value filter on every lookup works but does not scale," and index design is called out as correctness+performance-critical. Source: "Checkpointers — Row key / index design" — https://docs.langchain.com/oss/python/langgraph/checkpointers
- FACT: LangGraph offers configurable durability modes (`exit`/`async`/`sync`): "exit" is fastest but "you cannot recover from system failures (like process crashes) mid-execution"; "sync" persists every checkpoint before continuing "at the cost of some performance overhead." Source: "Checkpointers — Durability modes" — https://docs.langchain.com/oss/python/langgraph/checkpointers

**4. Filesystem-as-state is used where human readability, git, and zero-infra win — with explicit limits.**
- FACT: Claude Code stores agent memory as files: project/user CLAUDE.md files plus auto memory at `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index. Limits are documented first-party: "The first 200 lines of `MEMORY.md`, or the first 25KB… are loaded at the start of every conversation"; topic files "are not loaded at startup… read on demand"; "Auto memory is machine-local… Files are not shared across machines or cloud environments"; CLAUDE.md should target "under 200 lines per file" because longer files "consume more context and reduce adherence." Source: Claude Code "How Claude remembers your project" — https://code.claude.com/docs/en/memory
- FACT: The MCP reference "Knowledge Graph Memory Server" persists the whole knowledge graph to a single JSONL file (`MEMORY_FILE_PATH`, default `memory.jsonl`) — a file-backed, single-process memory with no server-side DB. Source: modelcontextprotocol/servers, `src/memory/README.md` — https://github.com/modelcontextprotocol/servers/blob/main/src/memory/README.md
- OPINION (local first-party experience, not a benchmark): this repository (mini-agi) is a filesystem-as-state agent kernel (canonical memory + a checkpoint journal) and its own AGENTS.md records file-based operational hazards: "NEVER restore the checkpoint journal through git… it destroys working-tree journal lines and orphans BEGINs. Repair through checkpoint.sh only," and the rule against chaining `grep -c` (a zero-match exits 1 and silently breaks a `&&` chain) because such chains were a real failure cost. Source: `AGENTS.md` at repo root of mini-agi. This is documented pain from the flat-file model, not a measured comparison.

**5. The middle ground: SQLite is an embedded database that is itself a file, and its own docs bound its scaling.**
- FACT: "SQLite does not compete with client/server databases. SQLite competes with fopen()." Source: SQLite "Appropriate Uses For SQLite" — https://www.sqlite.org/whentouse.html
- FACT: SQLite supports "an unlimited number of simultaneous readers, but it will only allow one writer at any instant in time." FACT: over a network filesystem, "file locking logic is buggy in many network filesystem implementations… two or more clients might try to modify the same part of the same database at the same time, resulting in corruption… there is nothing SQLite can do to prevent it." FACT: "Very large datasets" and "many concurrent writers" are both listed as cases where a client/server RDBMS "may work better." Source: SQLite "Appropriate Uses" — https://www.sqlite.org/whentouse.html
- ESTIMATE (vendor design guidance, no published numbers in the sources reached): LangGraph's and OpenAI's own backend menus imply the scaling curve is roughly in-memory → SQLite file → Postgres/Redis/MongoDB, but neither publishes a benchmark for agent state at scale in the pages cited.

**6. Long-term (cross-thread) agent memory has a different shape than run state and is also DB- or vector-store-backed in the frameworks.**
- FACT: LangGraph's long-term memory is a `Store` abstraction (namespace + key + JSON value), with production backends `PostgresStore`, `MongoDBStore`, `RedisStore`, `UpstashStore`, and optional semantic/vector search; the reference SQL schema uses `TEXT[]` namespace + `JSONB` value + GIN index. Source: LangGraph "Stores" — https://docs.langchain.com/oss/python/langgraph/stores
- FACT: Microsoft Agent Framework ships a separate "vector-stores-and-embeddings" feature area, i.e., durable memory is treated as a database/vector-store concern rather than a filesystem one. Source: microsoft/agent-framework repo, `docs/features/vector-stores-and-embeddings/` — https://github.com/microsoft/agent-framework/tree/main/docs/features

## Verdict

**Established (fact, from primary sources):**
- Run state durability is not free in any architecture: default agent run state is in-memory and lost on process end (MS Agent Framework durable-agents doc), and even file-backed checkpoints grow unboundedly and need pruning/delta encoding (LangGraph).
- All three major frameworks route *production* durability to databases, not flat files: LangGraph to Postgres ("Ideal for using in production"), OpenAI Agents SDK to Redis/SQLAlchemy/MongoDB/Dapr for "shared," "distributed," "horizontally-scalable" memory, Microsoft to Durable Task external storage for "multi-instance scale-out."
- Flat-file memory is chosen for readability/git/zero-infra (Claude Code, MCP memory server) and its costs are explicit in primary docs: context-window limits (~200 lines/25KB), on-demand loading, and machine-locality (not shared across machines/cloud).
- File/SQLite concurrency is bounded: one writer at a time, and network-filesystem file-locking bugs can corrupt state (sqlite.org). "Scale-out" and "concurrent writers" are exactly the cases the primary docs route to client/server DBs.

**Uncertain:**
- "Which scales better" is only answered as vendor design guidance, not measurement, in the sources I reached. No published benchmark was found comparing flat-file vs SQLite vs Postgres for agent run state at load. Scale-out behavior of a flat-file model across many worker processes is unverified from primary sources (both Claude Code and the MCP memory server are explicitly single-machine/single-process).

**What would settle it:**
- A measured benchmark: N concurrent agent sessions writing checkpoints/history to (a) one file per run, (b) SQLite single file, (c) Postgres/Redis — measuring p95 write latency, crash-recovery correctness, and cross-host consistency as N grows; plus a vendor-published load test (e.g., LangGraph Postgres checkpointer at concurrency) if one exists. None was available in the sources reached, so this remains open.
