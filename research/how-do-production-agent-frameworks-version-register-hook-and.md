## Findings

Scope note: "skills" and "tools" are two overlapping concepts. MCP/OpenAI/LangChain/CrewAI model *tools* (callable functions with schemas); Anthropic/OpenAI/Claude Code model *skills* (versioned bundles of instructions + files). Below, each claim is tagged **fact** (stated in the cited source), **estimate** (inference from a source), or **opinion** (my synthesis).

### 1. Versioning

| Framework | Mechanism | Source |
|---|---|---|
| Anthropic API skills | `container.skills[]` carries `{type, skill_id, version?}`. Version format: date-based (`20251013`) for Anthropic-managed skills, epoch timestamp (`1759178010641129`) for custom skills; `latest` is accepted. A dedicated **Skill Versions API** exists for version management. **fact** | Using Agent Skills with the API, https://docs.claude.com/en/docs/build-with-claude/skills-guide |
| OpenAI hosted skills | Skills are "versioned bundle[s] of files plus a SKILL.md manifest." `skill_reference` takes `skill_id` + `version` (integer or `"latest"`). Version pointers: `default_version` (used when none given) and `latest_version`. New versions via `POST /v1/skills/<skill_id>/versions`. Delete rules: can't delete the default version; deleting the last version deletes the skill. **fact** | Skills, https://platform.openai.com/docs/guides/tools-skills |
| MCP Registry (servers) | `server.json` MUST define a `version` string; it "MUST be unique for each publication" and is immutable after publish. Semver recommended; version-range strings (e.g. `^1.2.3`, `1.x`) are **prohibited**. **fact** | Versioning Published MCP Servers, https://modelcontextprotocol.io/registry/versioning.md |
| MCP spec (protocol itself) | The spec is versioned and snapshotted (2025-11-25, 2026-07-28) and runs a formal feature lifecycle (Active → Deprecated → Removed). **fact** | MCP docs index, https://modelcontextprotocol.io/llms.txt; Specification 2025-11-25, https://modelcontextprotocol.io/specification/2025-11-25/ |
| MCP tools (individual) | No per-tool version field. Tools are identified by a `name` with a defined charset and uniqueness "scoped to a single server"; aggregation collisions are handled by client-side prefixing, not versions. **fact** | Tools, https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md |
| Claude Code plugins | `plugin.json` has an optional `version`; if omitted, "the commit SHA is used and every commit counts as a new version." Community marketplaces pin approved plugins to a specific commit SHA. **fact** | Create plugins, https://code.claude.com/docs/en/plugins |
| CrewAI (enterprise) | The AMP "Tools Repository" advertises "version control and sharing capabilities" (vendor-claimed; I could not verify the mechanism). **fact** (vendor claim) | Tools, https://docs.crewai.com/concepts/tools |
| LangChain/LangGraph tools | No tool-level versioning in the docs read. Versioning/deployment is handled by LangGraph Server + LangSmith Deployment, which is outside the tool object. **fact (absence)** | LangGraph overview, https://docs.langchain.com/oss/python/langgraph/ |

### 2. Registration / discovery

- **MCP (protocol-standardized):** Servers declare a `tools` capability (optionally `listChanged`) and answer `tools/list` with `{name, title, description, icons, inputSchema, outputSchema, annotations}`. Listing supports pagination and caching (`ttlMs`, `cacheScope`), and servers "SHOULD return tools in a deterministic order" to enable client caching. This is the only framework where registration is an on-the-wire contract. **fact** | Tools, https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md
- **OpenAI Agents SDK:** `@function_tool` auto-derives name, description (docstring), and input JSON schema from the Python signature via `inspect` + `griffe` + `pydantic`; or build a `FunctionTool(name, description, params_json_schema, on_invoke_tool)` manually. Registration is passing tools to `Agent(tools=[...])`. Tools can be hidden until loaded via `defer_loading=True` + `ToolSearchTool()`, or grouped under `tool_namespace(name=..., description=..., tools=[...])`. **fact** | Tools, https://openai.github.io/openai-agents-python/tools/
- **Anthropic skills:** Registration is filesystem placement — `~/.claude/skills/` (personal) or `.claude/skills/` (project) — or upload via the Skills API (`/v1/skills`) for workspace-wide availability. Discovery is by YAML frontmatter (`name` + `description`, both length-limited, XML-tag-free, with reserved words banned) loaded into the system prompt; full content loads only when triggered ("progressive disclosure"). **fact** | Agent Skills overview, https://docs.claude.com/en/docs/agents-and-tools/agent-skills/overview
- **Claude Code plugins:** A `.claude-plugin/plugin.json` manifest registers skills/agents/hooks/MCP servers; skills are namespaced (`/plugin-name:skill`) to avoid collisions, and distribution runs through marketplaces with review + commit-SHA pinning. **fact** | Create plugins, https://code.claude.com/docs/en/plugins
- **OpenAI hosted skills:** Upload as multipart/zip bundles containing exactly one `SKILL.md` (case-insensitive match, frontmatter validated against the agentskills.io spec); reference via `skill_id`, or inline as base64 zip. Limits enforced at registration: 50 MB zip, 500 files/version, 25 MB uncompressed. **fact** | Skills, https://platform.openai.com/docs/guides/tools-skills
- **LangChain:** `@tool` requires type hints (they "define the tool's input schema"); `args_schema` can override with a Pydantic model or raw JSON Schema. Reserved argument names (`config`, `runtime`) are enforced with runtime errors. Tools can be dynamically filtered at runtime by state/permissions/feature flags instead of pre-registered. **fact** | Tools, https://docs.langchain.com/oss/python/langchain/tools
- **CrewAI:** Tools register as `BaseTool` subclasses (`name`, `description`, `args_schema`) or via `@tool`; typed output models are optional Pydantic classes. **fact** | Tools, https://docs.crewai.com/concepts/tools
- **MCP Skills (emerging):** The "Skills Over MCP" WG is standardizing skills discovery/consumption; current direction is SEP-2640, a Resources-based Extensions-Track skill primitive, coordinated with the agentskills.io spec. **fact** | Skills Over MCP WG charter, https://modelcontextprotocol.io/community/working-groups/skills-over-mcp.md

### 3. Hooking

- **OpenAI Agents SDK (in-process lifecycle):** `RunHooks`/`AgentHooks` receive callbacks `on_tool_start`/`on_tool_end` (immediately before/after a local tool is invoked), plus `on_agent_start/end`, `on_handoff`, `on_llm_start/end`. Attached per-run or per-agent (`agent.hooks`). The `@tool` wrapper adds the full runtime pipeline (schema validation, context injection, guardrails, timeouts, failure handling, tracing) around the raw callable; calling `__wrapped__` bypasses it. **fact** | Lifecycle, https://openai.github.io/openai-agents-python/ref/lifecycle/; Tools, https://openai.github.io/openai-agents-python/tools/
- **Claude Code (external, event-based):** Hooks fire at named lifecycle points — per session (`SessionStart`/`SessionEnd`), per turn (`UserPromptSubmit`, `Stop`), and **on every tool call** (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`, plus `PermissionRequest`/`PermissionDenied`). Handlers are shell commands, HTTP endpoints, MCP tools, LLM prompts, or subagents; `matcher` (tool name / regex) + `if` (permission-rule syntax) filter when they run. MCP tools are matched as `mcp__<server>__<tool>`. Hooks can return `permissionDecision: "deny"` to block a tool call. Hooks live in settings files, managed policy, plugin `hooks/hooks.json`, or skill/agent frontmatter; `allowManagedHooksOnly` lets enterprises suppress user/project/plugin hooks. **fact** | Hooks reference, https://code.claude.com/docs/en/hooks
- **MCP (change notification):** Servers declaring `listChanged` push `notifications/tools/list_changed` over a `subscriptions/listen` stream when the tool list changes — the protocol-level equivalent of a change hook. **fact** | Tools, https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md
- **LangChain (middleware):** Tool execution is wrapped by middleware (e.g. `wrap_tool_call` for retry/error-to-message conversion); `ToolNode` runs tools inside the graph. **fact** | Tools, https://docs.langchain.com/oss/python/langchain/tools
- **CrewAI (event bus):** Tools emit structured events (`ToolFailureDetectedEvent`, `ToolUsageFinishedEvent`) that subscribers observe via an event bus. **fact** | Tools, https://docs.crewai.com/concepts/tools

### 4. Gating / enforced contracts / validation gates

- **OpenAI Agents SDK guardrails:** Three layers — *input guardrails* (run on first-agent input; parallel or blocking execution), *output guardrails* (run on final output), *tool guardrails* (input checks before a function-tool runs — can skip, replace output, or raise a tripwire; output checks after). Tripwires raise exceptions and halt the run. Ordering is configurable vs. approvals: `ToolExecutionConfig(pre_approval_tool_input_guardrails=True)` runs input checks before the human-approval interruption; otherwise they run after approval. Tool guardrails apply only to `function_tool` tools, not hosted/built-in tools or handoffs. **fact** | Guardrails, https://openai.github.io/openai-agents-python/guardrails/
- **OpenAI `allowed_callers`:** A tool declares whether it may be invoked directly by the model and/or by programmatic tool-calling (`["direct"]`, `["programmatic"]`, or both) — an access gate on the tool itself. Approval/HITL interrupts run through `RunState` pause/resume. **fact** | Tools, https://openai.github.io/openai-agents-python/tools/
- **MCP enforced contract:** `inputSchema` MUST be a valid JSON Schema object (2020-12 default), and `outputSchema` is optional but binding when present: servers "MUST provide structured results that conform"; clients "SHOULD validate." Tool annotations (behavior metadata) "MUST [be] consider[ed] untrusted" from non-trusted servers. Servers MUST validate all inputs, enforce access controls, rate-limit, and sanitize outputs; clients SHOULD validate tool results before handing them to the LLM, and there SHOULD be a human able to deny invocations. `x-mcp-header` constraints are enforced by rejecting malformed tools from `tools/list`. SEP-1303 ("Input Validation Errors as Tool Execution Errors") routes input-validation failures into the `isError: true` tool-result channel. **fact** | Tools, https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md; llms.txt, https://modelcontextprotocol.io/llms.txt
- **Anthropic enterprise skills gates:** Pre-deployment approval gates for five dimensions (triggering accuracy, isolation, coexistence, instruction following, output quality); required eval suites of 3–5 queries per skill (should-trigger / should-not-trigger / ambiguous); separation of duties (authors ≠ reviewers); risk-tier vetting (code execution, instruction manipulation, MCP references, network calls, hardcoded credentials); integrity checksums verified at deploy time and signed commits. Recall is capped — max **8 skills per request** — to protect trigger accuracy. **fact** | Skills for enterprise, https://docs.claude.com/en/docs/agents-and-tools/agent-skills/enterprise; Using Agent Skills with the API, https://docs.claude.com/en/docs/build-with-claude/skills-guide
- **Claude Code permissions vs. hooks:** The hooks doc is explicit that hooks are *not* the enforcement layer: "Because the `if` filter is best-effort, use the permission system rather than a hook to enforce a hard allow or deny," and a hook "can deny the call, but staying silent doesn't approve it." **fact** | Hooks reference, https://code.claude.com/docs/en/hooks
- **LangChain:** Schema contract is enforced by construction (type hints required, reserved names rejected). Error handling is middleware-based; there is no built-in guardrail/tripwire layer in the tools page read — gating (HITL, interrupts) is a LangGraph graph-level feature, not a tool-level one. **fact (as scoped to the source)** | Tools, https://docs.langchain.com/oss/python/langchain/tools
- **CrewAI:** Declarative failure contracts — a tool returns `ToolFailure(code, retryable)` instead of a string; the framework records it "never guesses whether a string looks like an error." `tool_failure_policy` (`ignore` / `warn` default / `raise`) with most-specific-wins precedence (tool → task → agent → crew). `max_usage_count` limits a tool's calls. **fact** | Tools, https://docs.crewai.com/concepts/tools

### 5. Drift detection

- **Anthropic (only explicit "drift" usage found):** Enterprise guide's Monitor stage: "Rerun evaluations periodically to **detect drift or regressions** as workflows and models evolve"; declining trigger accuracy or output quality is a defined signal to update or deprecate a skill. This is a manual/review-driven process, not an automated gate. **fact** | Skills for enterprise, https://docs.claude.com/en/docs/agents-and-tools/agent-skills/enterprise
- **LangChain:** Drift/issue detection is externalized to **LangSmith Engine**, which "monitors your traces, detects issues, and proposes fixes" and can open a PR with the fix. **fact** | LangGraph overview, https://docs.langchain.com/oss/python/langgraph/; Tools, https://docs.langchain.com/oss/python/langchain/tools
- **MCP:** The nearest protocol-level drift signal is `notifications/tools/list_changed` — the server announces its tool set changed, so a host can detect that its cached contract is stale (i.e., contract-change detection, not behavioral drift). **fact** | Tools, https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md
- **OpenAI (SDK + platform):** No behavioral-drift detection appears in any page I reached. The only lifecycle primitive is the SDK's lifecycle hooks (observability), and the platform Skills guide's guidance is "inspect … before using," not periodic re-validation. **fact (absence)** | Lifecycle, https://openai.github.io/openai-agents-python/ref/lifecycle/; Skills, https://platform.openai.com/docs/guides/tools-skills
- **CrewAI:** Failure recording + event bus provide the raw data for drift analysis but no detection policy itself. **fact (absence)** | Tools, https://docs.crewai.com/concepts/tools

### 6. Cross-framework comparison (synthesis)

| Dimension | OpenAI Agents SDK | Anthropic (API / Claude Code) | MCP | LangChain/LangGraph | CrewAI |
|---|---|---|---|---|---|
| Versioning | Hosted skills: `skill_id` + int/`latest`; default/latest pointers | API skills: `version` (date/epoch/`latest`) + Versions API; plugins: semver or git SHA | Registry: server `version` (semver, immutable); no per-tool version | None at tool level | AMP Tools Repository claims version control |
| Registration | Decorator/`FunctionTool`; `tool_namespace`; tool search | Filesystem `SKILL.md` dirs; Skills API; plugin manifest | Wire contract: `tools/list` + capability negotiation | `@tool` + type hints/`args_schema`; dynamic filtering | `BaseTool` subclass / `@tool` |
| Hooks | In-process `on_tool_start/end` etc. | External events (`PreToolUse`/`PostToolUse`…), 5 handler types | `notifications/tools/list_changed` | Middleware (`wrap_tool_call`), `ToolNode` | Event bus |
| Gates | Input/output/tool guardrails + tripwires; `allowed_callers`; approvals | Pre-deployment security review + eval suites; permission system (not hooks) | JSON Schema input/output contract; client-side validation; HITL SHOULD; OAuth authorization | Schema-by-construction; HITL at graph level | `ToolFailure` + `tool_failure_policy`; `max_usage_count` |
| Drift | None found | Periodic re-run of evals ("detect drift") | `list_changed` (contract change) | LangSmith Engine | None found |

Opinion: only Anthropic treats skill/tool quality as a *reviewable, versioned artifact with a lifecycle and re-evaluation cadence*; MCP is the only one that turns the tool contract (schema) itself into an on-the-wire, cacheable, change-notifiable object; the other frameworks put enforcement in the host application, not the artifact.

## Verdict

**Established (fact):** (1) Only hosted/uploaded *skills* get real versioning — Anthropic (`version` param, Versions API, `latest`) and OpenAI (`skill_id` + int version, `default_version`/`latest_version` pointers, immutable-ish delete rules) — while MCP *tools* have no per-tool version and rely on the registry's immutable semver server version. (2) MCP is the only framework where registration and the enforced contract are standardized on the wire (`tools/list` with `inputSchema`/`outputSchema`, capability negotiation, deterministic ordering, caching, `list_changed`). (3) Hooking splits into in-process lifecycle hooks (OpenAI SDK `on_tool_start/end`), external event hooks (Claude Code `PreToolUse`/`PostToolUse`, which can `deny` a call), middleware (LangChain), and an event bus (CrewAI). (4) Gating is a host-side concern in every framework: OpenAI guardrails + tripwires + `allowed_callers` + approvals; Anthropic's pre-deployment security review, eval suites, and 8-skill recall cap; MCP's schema contract + client validation + human-in-the-loop SHOULD; Claude Code explicitly separates hooks (best-effort) from the permission system (hard allow/deny).

**Uncertain:** LangGraph/LangChain tool-level gates and CrewAI's "version control" claim — I reached the tools/overview pages but not their full gate/registry internals; CrewAI AMP "version control and sharing" is a vendor claim I could not verify mechanically. MCP authorization (OAuth 2.1 / enterprise-managed) is listed in the docs index but I did not read that page's details.

**Missing / would settle it:** Genuine behavioral *drift detection* is nearly absent — only Anthropic documents re-running evals to detect drift, and LangChain delegates it to LangSmith Engine; OpenAI and CrewAI showed none in the sources reached. Reading (a) OpenAI's sandbox-skill capability reference, (b) LangGraph's interrupts/HITL concepts page, and (c) MCP's authorization spec page would close the largest gaps in the gating and drift rows.
