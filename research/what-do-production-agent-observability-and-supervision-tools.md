## Findings

### 1. Human-in-the-loop review queues: shared mechanics
Across the tools documented below, the HITL review-queue pattern is consistent: a collector of traces/runs, a rubric (score config), an assignment model, and a completion state machine. Facts below are from each vendor's primary docs.

- **LangSmith annotation queues** group runs or whole threads, prescribe a rubric ("Instructions" + feedback keys), and track reviewer progress. Queues present one item at a time ("single-run") or two runs side-by-side for A/B comparison ("pairwise"). Items carry states **Needs Review → Needs Others' Review → Completed**. [fact] — *Use annotation queues*, LangSmith docs, https://docs.langchain.com/langsmith/annotation-queues.md
- LangSmith queue collaborator settings: an item can be held until **every workspace member** marks it Done, or a set **number of reviewers per run** must finish it; **assigned reviewers** can be named explicitly. **Reservations** lock an item to a reviewer for a set time, and expire and release it back into the queue if the reviewer leaves without marking Done. Because of these settings, "the number of items visible to each reviewer can differ from the total queue size." [fact] — *Use annotation queues*, LangSmith docs, https://docs.langchain.com/langsmith/annotation-queues.md
- **Langfuse annotation queues** require a **Score Config** defining scoring dimensions; queues can be assigned to users; traces/observations/sessions are added singly or in bulk; processing is fully keyboard-driven (navigation + scoring keys). [fact] — *Annotation Queues*, Langfuse docs, https://langfuse.com/docs/evaluation/evaluation-methods/annotation-queues.md
- **Braintrust human review** defines review scores (categorical, continuous, free-form), which appear in logs/experiments/datasets. Review work is managed via a dedicated Review page with views (**Awaiting review**, **Assigned to me**, **Completed**), SQL filtering, and a **kanban** layout (**Backlog / Pending / Complete**). Rows can be **assigned** to team members; assignees get email (and optional Slack DM) notifications. [fact] — *Set up human review* and *Manage review work*, Braintrust docs, https://www.braintrust.dev/docs/annotate/human-review/index.md and .../manage-review-work.md

### 2. Consensus and multi-reviewer handling
- Braintrust stores each reviewer's scores independently; continuous/categorical scores are **averaged** on the parent span, free-form scores require a reviewer (or admin) to pick a value via **"Set as base span value"**. A **"N total reviews"** indicator shows agreement vs. divergence; Braintrust explicitly does not support blind review. [fact] — *Review with multiple reviewers*, Braintrust docs, https://www.braintrust.dev/docs/annotate/human-review/multiple-reviewers.md
- LangSmith's per-run reviewer thresholds and reservation locking serve the same purpose (preventing two reviewers from grading the same comparison simultaneously in pairwise queues). [fact] — *Use annotation queues*, https://docs.langchain.com/langsmith/annotation-queues.md

### 3. Attention routing: how items get into queues in the first place
The dominant documented pattern is **rule/filter + sampling**, not pushing every trace at a human.

- **LangSmith automation rules** are defined as **filter + sampling rate (0–1) + action**. Actions include **Add to annotation queue**, Add to dataset, Trigger webhook, Extend data retention, run online evaluator, Trigger alert. Documented examples: "Send all traces with negative feedback to an annotation queue," and "Send 10% of all traces to an annotation queue … to spot check." Action ordering within a rule is fixed (queue → dataset → webhook → evaluator → alert). [fact] — *Set up automation rules*, LangSmith docs, https://docs.langchain.com/langsmith/rules.md
- The LangSmith docs also explicitly suggest routing runs that already carry user feedback (e.g., thumbs-down) into a queue for triage. [fact] — *Use annotation queues*, https://docs.langchain.com/langsmith/annotation-queues.md
- **Braintrust Topics** auto-classifies production logs by task, sentiment, issue type, and custom patterns. Logs can be filtered by topic classification (SQL on `classifications.Task.label`, etc.), and matching logs **assigned** to reviewers; topic-matching scorers can be run **online** with a **sampling rate** via automations. [fact] — *Act on findings from Topics*, Braintrust docs, https://www.braintrust.dev/docs/observe/topics/act-on-findings.md
- **Datadog Agent Observability "Patterns"** performs automated hierarchical topic clustering of production traffic to surface user intents and coverage gaps; **Insights** runs outlier detection across span name, workflow type, and Patterns topics, surfacing anomalies in the UI for the selected time window. [fact] — *Agent Observability* overview, Datadog docs, https://docs.datadoghq.com/llm_observability/
- **LangSmith Engine** automatically detects recurring issues in traces, diagnoses root cause, and proposes resolution — an alternative to manually triaging every failed run. [fact] — LangSmith Observability overview, https://docs.langchain.com/langsmith/observability.md

### 4. Interrupt-based attention (approval-style HITL)
- **LangGraph (LangSmith/Deployment)** implements HITL via **dynamic interrupts**: the graph pauses at `interrupt(...)`, returns an interrupt payload to the caller, and is resumed by posting a `Command(resume=...)` with the human's input. Static interrupts (`interrupt_before/after`) exist but the docs explicitly recommend against them for HITL, calling them debug/test tools. **Time travel** lets an operator list checkpoints (`get_history`), mutate state (`update_state`), and resume from the edited checkpoint. [fact] — *Human-in-the-loop using server API* and *Time travel using the server API*, LangSmith docs, https://docs.langchain.com/langsmith/add-human-in-the-loop.md and https://docs.langchain.com/langsmith/human-in-the-loop-time-travel.md

### 5. Notification-noise controls (the documented, primary-source answers)
- **LangSmith alerts are threshold-based on aggregated metrics** (run count, cost, errors count or error %, average feedback score, latency) over a configurable window (5 or 15 minutes), are **project-scoped**, and can be scoped further by a filter builder (status/run type/tag/error). Notifications route to **Slack, PagerDuty, Dynatrace, or any webhook**. Noise controls documented in-source: PagerDuty dedup ("to receive the same alert again within an hour … you must resolve the active incident"), and the webhook payload includes `alert_rule_id` documented as "a de-duplication key in the webhook service." Best practices listed: start with broader thresholds and refine, adjust sensitivity to criticality, route to appropriate on-call. [fact] — *Alerts in LangSmith*, https://docs.langchain.com/langsmith/alerts.md
- **Langfuse monitors are a severity state machine**: `OK / WARNING / ALERT / NO_DATA / PAUSED`. Alerts fire **only on severity transitions**; **Renotify is off by default** (re-firing every N minutes only if enabled); **no-data handling** can suppress alerts ("Keep the previous severity", "Show severity NO_DATA" with no alert, or delayed sustained-NO_DATA alert). Notifications go through **Automations** to Slack, webhook (HMAC-signed), or GitHub Actions. [fact] — *Monitors and Alerts*, Langfuse docs, https://langfuse.com/docs/metrics/features/monitors.md
- **Braintrust's anti-noise mechanism is a daily digest instead of per-event alerts**: a beta "Topics digest" posts once a day to Slack covering the previous 24h — summary of activity shift, biggest topic mover, highlight traces, and one takeaway. [fact] — *Act on findings from Topics*, https://www.braintrust.dev/docs/observe/topics/act-on-findings.md
- **Braintrust score visibility** controls also reduce per-reviewer noise: scores can be restricted to specific members/groups or shown **conditionally** (e.g., only when a triage score indicates deeper review is needed) — documented as a display filter, "not an access control." [fact] — *Set up human review*, https://www.braintrust.dev/docs/annotate/human-review/index.md
- **OpenAI Agents SDK** reduces captured volume rather than notification volume: tracing is on by default but can be disabled per-run, sensitive-data capture (`trace_include_sensitive_data`) can be turned off, and custom/sampled trace processors can be installed in place of the default exporter. [fact] — *Tracing*, OpenAI Agents SDK docs, https://openai.github.io/openai-agents-python/tracing/

### 6. Supervising multiple concurrent agents
- **OpenAI Agents SDK** structures supervision around grouping: traces carry `workflow_name` and an optional `group_id` to link multiple traces from one conversation (e.g., a chat thread id), giving operators a conversation-scoped view rather than per-call noise. [fact] — *Tracing*, OpenAI Agents SDK docs, https://openai.github.io/openai-agents-python/tracing/
- **Langfuse sessions** group traces/observations into one session for replay of the full interaction. [fact (page title/description)] — Langfuse docs index, https://langfuse.com/llms-docs.txt → *Sessions*, https://langfuse.com/docs/observability/features/sessions.md
- **HumanLayer**: the original human-in-the-loop-API product is deprecated; the repo README states "the code here is pretty much all deprecated." The current product (humanlayer.com) is an AI-coding IDE whose marketing positions task/session grouping, real-time session visibility, and cloud daemons as the way to supervise many parallel agent sessions. I verified only the marketing homepage and the repo README; no detailed supervision-docs were reachable (docs.humanlayer.dev transport-error). [fact (README/pivot); opinion (its efficacy as a supervision console)] — https://github.com/humanlayer/humanlayer, https://www.humanlayer.dev

### 7. Not verified
- I could not verify any vendor documentation quantifying how much notification noise these controls actually reduce (no measured alert-fatigue data found in primary docs). No claim is made about effectiveness.
- Arize Phoenix was reached only at its overview; it documents tracing → evals → datasets → experiments but I found no HITL review-queue or alerting page, so Phoenix is not claimed as a review-queue tool. [fact] — https://docs.arize.com/phoenix/quickstart/

## Verdict
**Established** (primary docs, multiple vendors): the HITL review-queue surface is standard — rubric-driven queues over traces/sessions, reservation/locking, reviewer-count or assigned-reviewer completion, and multi-reviewer consensus handling (LangSmith, Langfuse, Braintrust). Attention routing is overwhelmingly *pre-filtering*: rule + sampling-rate automations route a fraction of filtered runs into queues (LangSmith), and topic/issue classification feeds assignment and online scoring (Braintrust Topics, Datadog Patterns/Insights, LangSmith Engine). Notification-noise reduction is documented as **threshold aggregation + severity state machines + transition-only firing + dedup keys + daily digest**, not as per-trace paging (LangSmith alerts, Langfuse monitors, Braintrust Topics digest). For concurrency, grouping surfaces (OpenAI `group_id`/workflow_name, Langfuse sessions, HumanLayer task/session views) are the documented answer to supervising parallel agents.

**Uncertain / gaps**: (1) no primary source quantifies alert-fatigue reduction or operator-attention effectiveness — these mechanisms are documented, their benefit is my inference, not measured. (2) HumanLayer's original HITL-API product is deprecated; only the pivoted coding-IDE homepage was reachable, so its supervision claims are unverified marketing. (3) Arize Phoenix HITL queues and Helicone/AgentOps alerting were not verified. (4) One fetched source (LangSmith Engine, Phoenix, Datadog alert internals beyond overview) was read only partially.

**Evidence that would settle it**: a controlled/observational study or vendor case study reporting notification volumes before/after such controls (e.g., alert count per incident, % of queue items that change an outcome), and access to a dedicated agent-supervision console's documentation (e.g., Arize AX, AgentOps, HumanLayer's current docs) to compare routing/digest behavior.
