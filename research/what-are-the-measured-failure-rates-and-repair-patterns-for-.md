## Findings

Scope note: "failure" of structured JSON output exists at three distinct layers, and the primary sources measure them separately: (1) syntactic JSON parse failures, (2) JSON-Schema compliance, (3) semantic/value correctness of a schema-valid object. Claims are tagged **fact** (measured in the cited source), **claim** (first-party/vendor statement, not independently measured), or **estimate** (derived arithmetic), per the contract.

### 1. Failure rates without schema enforcement (prompting only)

**Fact (cross-model "format collapse" is a distinct, measured no-enforcement failure; abstract-level, PDF only).** PromptPort (Kotte, arXiv:2601.06151) formalizes the phenomenon that AloLab [62], TSCG [66], and Palabrita [70] observed independently: "structured extraction with LLMs fails in production not because models lack understanding, but because output formatting is unreliable across models and prompts" — the same prompt returning clean JSON on GPT-4 produces **fenced, prose-wrapped, or malformed output on Llama**, so strict parsers reject otherwise-correct extractions. On a **37,346-example camera-metadata benchmark across six model families**, it introduces a dual metric that separates the two failure layers: **ROS (strict parsing — operational reliability) vs CSS (post-canonicalization — semantic capability)**, finding severe format collapse (e.g., **Gemma-2B ROS 0.116 vs CSS 0.246**) and large cross-model portability gaps (**0.4 to 0.6 F1** — the same model family differences as §7's interface findings). The recovery layer (deterministic canonicalization + a lightweight DistilBERT verifier with safe-override and explicit abstention) **recovers format failures (+6 to 8 F1), adds verifier-driven semantic selection (+14 to 16 F1 beyond canonicalization), and approaches per-field oracle performance (0.890 vs 0.896 zero-shot)** without modifying base models, generalizing to held-out model families. Implication: this is the cleanest *measurement* of the format-collapse gap that §1/§2 quantify at the compliance level — it shows strict-parse accuracy can be ~0.12 while true capability is ~0.25 for a 2B model, i.e., a parser-rejectable-but-semantically-correct output is a first-order, cross-model reliability variable with a measured recovery lever (canonicalization + verifier, not retries).

**Fact.** JSONSchemaBench (Geng et al., Microsoft/EPFL/JSON Schema org; arXiv:2501.10868, §5, Table 4) measures *empirical coverage* — the fraction of generated outputs that are schema-compliant — on ~10K real-world schemas using Llama-3.2-1B-Instruct (greedy decoding, 2-shot). With no constrained decoding ("LM only"), empirical coverage / compliance was:
- GlaiveAI function-calling schemas: **0.90** (10% fail)
- GitHub-Easy: **0.65** (35% fail)
- Kubernetes: **0.56** (44% fail)
- Snowplow: **0.46** (54% fail)
- GitHub-Medium: **0.38** (62% fail)
- GitHub-Hard: **0.13** (87% fail)
- JSONSchemaStore: **0.21** (79% fail)

So prompting-only schema compliance collapses to 13–46% on medium-to-hard schemas. Note the benchmark uses a small open model; these are lower bounds for compliance of weak models, not for frontier models.

**Fact (frontier models).** SchemaBench (Lu, Li, Cong et al., Tsinghua; arXiv:2502.18878) measures *valid-JSON-string* generation (schema-only, greedy decoding, `jsonschema`-validated) on ~40K schemas (avg nesting depth 16.7) — the largest direct measurement of native JSON validity found. Table 2, overall correctness: **GPT-4o 61.06%**, GPT-4o-mini 43.98%, Qwen-2.5-7B 42.38%, Llama-3.1-8B 36.45%, Llama-3.2-3B 28.51%, MiniCPM-3-4B 27.77%. Per-subtask, GPT-4o: Complex-schema 84.47%, Custom-format 61.56%, **Escape-translation 37.14%** (open models 8–16%). So even a frontier model produces a schema-valid JSON string on only ~61% of complex schemas when generating natively; the paper's headline: "the latest LLMs are still struggling to generate a valid JSON string." Failure-mode decomposition (Fig. 3): GPT-4o has 13% validation + **8% parser** errors; Llama-3.2-3B 23% and MiniCPM-3-4B 36% parser errors; a floor of ~5% pattern-regex errors across all models. Note these schemas are substantially deeper (avg depth 16.7) than JSONSchemaBench's github splits, which explains the lower numbers; together the two benchmarks bracket the no-enforcement failure regime (roughly 40–90% failure on complex schemas depending on depth and model size).

**Claim (first-party).** OpenAI docs distinguish JSON mode from Structured Outputs: JSON mode "outputs valid JSON: Yes" but "adheres to schema: No"; Structured Outputs adheres (source: OpenAI "Structured model outputs" guide, https://developers.openai.com/api/docs/guides/structured-outputs). I.e., vendor-framed failure mode of JSON mode is schema-level, not syntax-level. No measured rate given.

**Claim (first-party).** Anthropic docs state that without structured outputs Claude "can generate malformed JSON responses or invalid tool inputs," enumerating "parsing errors from invalid JSON syntax, missing required fields, inconsistent data types, schema violations requiring error handling and retries" (source: https://docs.anthropic.com/en/docs/build-with-claude/structured-outputs). No measured rate given.

### 2. Failure rates with schema enforcement (constrained decoding)

**Fact.** Same benchmark, Table 4 (open engines run on the same Llama-3.2-1B backend; OpenAI/Gemini use proprietary models, so cross-comparison is explicitly "not directly comparable"):
- **Function-calling schemas (GlaiveAI):** compliance rate (empirical ÷ declared) — LM-only 0.90; Guidance 0.98; Llama.cpp 0.97; Outlines 0.96; XGrammar 0.93; OpenAI 1.00 (declared coverage 0.89); Gemini 1.00 (declared 0.86).
- **GitHub-Hard:** LM-only 0.13; Guidance 0.69 (empirical 0.41); Llama.cpp 0.63; XGrammar 0.41; Outlines 0.06; OpenAI 1.00 but declared coverage only **0.09**.
- **Kubernetes:** Guidance 0.92; Outlines 0.58; OpenAI 1.00 but declared 0.21.
- **JSONSchemaStore:** Guidance 0.88 (empirical 0.30); Llama.cpp 0.69; XGrammar 0.43; Outlines 0.24; OpenAI 1.00 but declared 0.06.

Pattern: closed providers (OpenAI/Gemini) show near-perfect compliance **within a small declared subset** (they "reject" or error on 70–94% of real-world schemas); open grammar engines cover far more schemas but with lower per-schema compliance (31–77% on hard suites). The authors' conclusion: compliance is only guaranteed on the subset of JSON Schema features the engine implements; under-constrained engines "cannot guarantee that all responses will be valid, often necessitating additional post-processing or retry logic" (§5.3).

**Fact.** JSON Schema Test Suite coverage (Table 5–6): of 45 feature categories, Guidance had full coverage in 13 and moderate in 21; Llama.cpp 1/5; XGrammar 1/3; Outlines 0/2. Failure-mode breakdown (categories where the failure occurred at least once): compile errors — Outlines 42, Llama.cpp 37, Guidance 25, XGrammar 3; over-constrained — Llama.cpp 18, Outlines 16, Guidance 7, XGrammar 5; under-constrained — **XGrammar 38**, Outlines 8, Llama.cpp 7, Guidance 1. Over-constraining suppresses valid outputs; under-constraining is the direct cause of the residual failures that force retries.

**Fact.** Efficiency with enforcement (Table 2, LlamaCpp backend, median): Guidance time-per-output-token 6.37 ms vs LM-only 15.40 ms on GlaiveAI (i.e., constrained decoding *faster* than unconstrained — the paper's headline "~50% speedup" finding); Llama.cpp 29.98 ms; Outlines 30.33 ms with 3.48 s one-time grammar-compilation cost. So enforcement is not inherently slower, but implementation matters.

**Fact.** XGrammar (Dong et al., MLSys '25; arXiv:2411.15100, §4.1): the *mask-generation* cost of CFG constrained decoding can be driven below the LLM's own per-token latency. Measured per-token mask latency is under 40 µs/token for JSON Schema and unconstrained JSON (Llama-3.1-8B, RTX 4090), "up to 3x speedup on JSON Schema and over 100x on CFG compared to the best baseline" (Outlines, llama.cpp grammar, lm-format-enforcer); end-to-end structured-output serving on H100 reaches "up to 80x speedup." With CPU/GPU overlap the authors report "near-zero overhead" end-to-end. Key mechanics, measured on Llama-3.1 (128k vocab) + JSON grammar: context-dependent tokens are <1% of vocabulary (1,134/128k), reduced to 120 by context expansion, and the mask cache drops from 160 MB to 0.46 MB. Caveat from JSONSchemaBench Table 2: XGrammar achieves this at the cost of *under-constraining* — it had the highest under-constrained failure count (38 categories) on the JSON Schema Test Suite, so low overhead can mean weaker enforcement (over-permissive masks) depending on configuration.

**Fact (GCD mask computation can be made vocabulary-independent; verified in full text).** PSC / Parser Stack Classification (Li, Dong, Li, Li; PKU/SJTU/Tsinghua, arXiv:2608.03065, ISSTA 2026) is the next step in the XGrammar-style overhead elimination: instead of parsing to decide validity for each candidate token (worst-case O(|V|) per step — significant for 128k–262k-token vocabularies), PSC proves the set of parser stacks accepting a token is a *regular language* and precompiles a single FSA that classifies the current parser stack once per step (O(1) mask lookup), so **mask computation becomes independent of vocabulary size**. Measured vs SOTA baselines (XGrammar, GreatGramma, Formatron, LLGuidance; teacher-forcing on 1,000 samples per language + 1,000 schemas from MaskBench; Llama-3.2 128k / Qwen2.5 151k / Gemma-3 262k vocabularies): **mask computation up to 700× faster on complex programming-language grammars (Java/Go/SQL) and up to 30× faster on schema-conformant JSON**, with **end-to-end LLM throughput approaching unconstrained decoding** (correctness on par: 99.6–100% of samples processed, no parser errors — unlike Formatron/LLGuidance which fail on Go). Overhead analysis includes a preprocessing break-even point: preprocessing cost is small for simple grammars but significant for complex ones, and results are shareable across users (preprocessing providers vs decoding users). Implication: the "enforcement is free" claim (Verdict §d) now has a *vocabulary-independent* bound — with PSC the GCD overhead is a one-time preprocessing cost plus O(1) mask lookup, so constrained decoding throughput can equal unconstrained; combined with XGrammar's <40 µs/token, the efficiency side of the enforcement trade-off is effectively solved.

**Fact (locally constrained decoding — the stack Outlines/XGrammar/OpenAI ship — is *distribution-biased* and *fails constraint satisfaction within a finite token budget*; verified in full text).** "Mitigating Bias in Locally Constrained Decoding via Tractable Proposals" (Dang, Song, Zhang, Zhao, Van den Broeck, Ermon; UCLA/Stanford, arXiv:2606.01926) is the first clean measurement that the standard *mask-and-renormalize* stack does not sample from the target conditional distribution p_lm(x|C) and does not guarantee validity at termination. Two mechanisms, both named in §2: (i) **bias** — LCD masks only tokens that immediately violate the constraint (the "loose" criterion 𝒳_{t,*}: extendable at *any* length), so the renormalized distribution "deviates from the target conditional distribution, introducing substantial sampling bias" (their toy example: uniform p_lm over 3 bits with constraint "exactly one 1" gives LCD p=1/4,1/4,1/2 on the three valid strings vs the true 1/3 each); and (ii) **no finite-budget guarantee** — a decoder can emit locally-valid unmatched `{` forever, so a length-n sequence may still violate the constraint; "to the best of our knowledge, all" deployed constrained-decoding systems (Outlines, XGrammar, OpenAI Structured Outputs) "perform LCD and do not guarantee constraint satisfaction within a given token budget." Their fix: tensorize the constraint FA for GPU-parallel reachability and mask with the *budget-aware* criterion 𝒳_{t,n} (valid completion within the remaining n−t tokens) — **Globally Constrained Decoding (GCD)** guarantees validity at termination — plus **P-GCD**, which circuit-multiplies the tensorized FA with a distilled HMM (a probabilistic look-ahead of future valid mass) to build both an SMC proposal and potential. Measured (xLAM function calling on Llama-3.1-8B-Instruct, 1,000 filtered instances, JSON + Python-like; CommonGen on GPT2-Large; Spider text-to-SQL, 500 instances; RS as ground truth; SMC framework, k particles): **constraint satisfaction at fixed budgets — LCD 95.26% (JSON k=4) / 95.40% (JSON k=16) / 98.12% / 99.20% (Python-like) vs GCD and P-GCD 100.0% at every budget** — "LCD can fail to satisfy the constraint even at moderate particle budgets"; **accuracy — LCD peaks at 69.7% on xLAM JSON regardless of particles (k=8→16 flat), while P-GCD (H=16384) reaches 70.5% at k=4 and 71.6% at k=16; on Spider, P-GCD at k=4 (67.9%) already beats LCD at k=8 (67.2%)** (full table: LCD 59.8/65.4/67.2, GCD 59.0/66.8/69.0, P-GCD 56.2/67.9/69.1 at k=1/4/8) — i.e., the bias is worth real points at fixed compute. Cost is the honest counterweight: LCD 1.08× and GCD 1.10× unconstrained wall-clock (1.69 ms/token H100), but **P-GCD runs 3.11×–10.2× slower depending on HMM size (5.26/8.23/17.30 ms/token at H=1024/4096/16384)**, plus a one-time HMM distillation (~2 GPU-hours for 2M vLLM samples + 0.2–3 h training); smaller HMMs still help (P-GCD H=1024 at k=8 = 71.1% > LCD best 69.7%), so "robust to the quality of the HMM approximation." Engineering note: operating directly on NFAs matters — for the Spider SQL grammar the character-level NFA is 7,999 states vs 57,263 for the equivalent DFA (token-level: 31,858 vs CPU OOM), and DFA size grows exponentially for JSON `anyOf` constraints. Implication for this report: **the "constrained decoding guarantees valid output" premise is itself only approximate — the deployed LCD stack (a) samples from a biased distribution (valid-but-distorted, compounding the §3 semantic gap) and (b) can still emit invalid output at budget, so the measured "100% validity" of closed providers is a *termination-time* guarantee on their supported subset, not a *sampling-fidelity* guarantee; GCD removes (b) at ~1.1× cost, P-GCD also mitigates (a) but is 3–10× expensive** — another axis on which "enforcement is free" needs qualification.

**Fact (enforcement can *disable* another capability — verified in full text).** "Constraint Tax" (Li, Zhang, Lv, Focus AI; arXiv:2606.25605): when tool calling and JSON-Schema constraints are enabled *together*, the JSON Schema is compiled into a grammar/FSM token mask, and **all six tested open-weight models (Qwen3.6-35B, Qwen3.5-122B/397B, Qwen3-VL-235B, GPT-OSS-20B, Nemotron-3-Super) dropped Tool Invocation Rate from 100% to 0%** (Suppression Rate 100%) — complete tool-call suppression — while the closed GPT-5.4-mini stayed at 100% (Table 7). Suppression is robust: TIR stays 0% across schema complexity (1–3 / 5–10 / 20+ fields), across tool-enforcement settings (even `tool_choice="required"`), and across frameworks (SGLang and vLLM identical). Root cause is mechanism-level: for the Qwen XML-style tool format, the leading `<` (U+003C) is not part of any valid JSON FSM state, so tool-call tokens are masked "by design" — the absence of tool calls under joint constraints is a direct consequence of decoding, not model preference. Mitigation (Transparent Two-Pass Execution — decouple tool execution from schema-constrained response generation): TIR **0%→100%**, JSON compliance unchanged, end-to-end success **0%→100%**, at the cost of one extra LLM round + tool-output context. Implication: schema enforcement is not free in agent stacks — it can silently remove action-taking behavior while preserving high schema compliance (the paper's "evaluating tool use and structured output separately may overlook important reliability issues"). The paper also cites the Constraint Tax line (Ray, 2024): strict schemas raise format compliance but can lower answer accuracy.

**Fact.** Quality impact (Table 8, Llama-3.1-8B, three reasoning tasks): constrained decoding does not hurt and slightly helps task accuracy vs unconstrained: GSM8K 80.1% (LM-only) → 83.8% (Guidance), 83.7% (XGrammar); Last-Letters 50.7% → 54.0%; Shuffle-Objects 52.6% → 55.9%. Guidance's ~3-point gain is attributed to token-healing. Caveat from an independent benchmark (verified in full text): the TOON study (Matveev, arXiv:2603.03306; 21 models, 4 cases × 10 runs, up to 3 repair cycles) found "plain JSON generation shows the best one-shot and final accuracy, even compared with constrained decoding structured output, where the only significant advantage is the lowest token usage as a trade-off for slightly decreased accuracy overall and significant degradation for some models." Its per-model data resolves the mechanism: constrained decoding acts as a **guardrail for weak models** (Qwen2.5-Coder-7B-fast: 0% plain-JSON one-shot at 37,705 tokens → 75% under JSO at 4,440 tokens) but **degrades strong models** (Hermes-4-405B one-shot 92.5% plain → 35.0% constrained), and JSO is the **absolute token-efficiency winner on simple tabular data** (users case 556 tokens). The two results are consistent in magnitude — the measured quality effect of enforcement is small and capacity-directional; it is not a reason to avoid or to rely on enforcement, whereas compliance is.

**Claim + fact (first-party, one vendor).** OpenAI's Structured Outputs launch post (Pokrass et al., OpenAI, 2024-08-06, https://openai.com/index/introducing-structured-outputs-in-the-api/) publishes its own measured ladder for "complex JSON schema following": prompting alone <40% (gpt-4-0613), trained-only model 93% (gpt-4o-2024-08-06), and **100% with strict constrained decoding** ("our new model gpt-4o-2024-08-06 with Structured Outputs scores a perfect 100%"). The 93%→100% step is the vendor's own motivation: model behavior is "inherently non-deterministic," so training alone was insufficient and CFG-based constrained decoding was layered on. Two scoping facts the vendor itself states: (a) the guarantee holds only for the supported JSON-Schema subset ("Structured Outputs allows only a subset of JSON Schema"), and (b) "Structured Outputs doesn't prevent all kinds of model mistakes... the model may still make mistakes within the values of the JSON object." One-time cost: first request with a new schema takes "<10 seconds... more complex schemas may take up to a minute" (then cached). These numbers are not independently replicated; they are the vendor's own eval, consistent in shape with JSONSchemaBench's finding that closed-provider compliance is ~100% *within their supported subset*.

**Fact (guided decoding in a real RAG workload; verified in full text).** Newmind AI's RAG study (Uğur et al., IEEE SIU 2025, arXiv:2509.06631) measures hallucination (false-positive doc-reference) rates for Outlines vs XGrammar vs LM Format Enforcer on Qwen2.5-72B and Llama-3.3-70B across 0/1/2-turn prompts (Table III): 0-turn FP rates 0.49–3.20% across methods; **multi-turn prompting cuts FP rates to as low as 0.06–0.30%** (Llama 2-turn LMF 0.06%, Qwen 2-turn XGrammar 0.12%); semantic quality stayed >91 (judge) for all methods. Backend choice matters at scale: in an extrapolated 10M-chunk/100K-query RAG, replacing LM Format Enforcer with XGrammar cost ~1,600–4,000 (Qwen) / 134–2,000 (Llama) additional missed references — XGrammar's format handling degraded reference recall in some turn settings even where its FP rate was lowest. Latency was roughly backend-independent (30–51 s/sample). Takeaways: enforcement method and prompt turns jointly determine grounding reliability; "lowest FP" and "best recall" do not always pick the same backend.

**Claim (first-party).** OpenAI: Structured Outputs "ensures the model will always generate responses that adhere to your supplied JSON Schema, so you don't need to worry about the model omitting a required key, or hallucinating an invalid enum value." Anthropic: structured outputs "guarantee schema-compliant responses through constrained decoding… Always valid… No retries needed for schema violations." Both are guarantees **within a documented subset of JSON Schema** (both docs list "JSON Schema limitations" / "supported schemas").

**Fact (the grammar-level fix for the format tax; verified in full text, ICML 2025).** CRANE (Banerjee, Suresh, Ugare, Misailovic, Singh; arXiv:2502.09061) provides the theoretical explanation for the format tax — constraining outputs to grammars that only allow syntactically valid *final answers* reduces reasoning expressivity (formally: a constant-layer LLM under such a grammar can only solve logspace-uniform TC0 problems, so st-connectivity/NL-complete problems become unsolvable unless TC0=NL) — and shows that **augmenting the output grammar with reasoning-permitting rules (Ga→R·G) preserves reasoning while keeping the final answer in the original grammar**. Its CRANE decoding (alternate unconstrained reasoning / constrained final windows, delimiter-switched) **outperforms both SOTA constrained decoding and unconstrained decoding** on GSM-symbolic/FOLIO (Table 1): e.g., Qwen2.5-Math-7B 29% (constrained) / 29% (CoT) → **38% CRANE**; DeepSeek-R1-Distill-Llama-8B 21% → **31% (+10 pp)**; QwQ-32B 43% → 46%; with 100% parse where unconstrained CoT had ~10% syntax errors. This is the measured counter-approach to the format tax: instead of "think first, format later" at the prompt level, design the grammar itself to permit an internal reasoning channel — grammar enforcement and reasoning are compatible when the grammar is reasoning-augmented.

**Fact (single-pass decoupling; verified in full text).** In-Writing / "Thinking Before Constraining" (Nguyen, Silva, Zumot, Tupikina, Aghasaryan, Alam; Nokia/Télécom Paris, arXiv:2601.07525) is the single-call embodiment of "think first, format later": the model reasons unconstrained (state −1) and **structured decoding engages only after a trigger token** (state 0), so the same model both solves and parses — no separate parser model. Measured against the same prompts/models as Tam et al. (LLaMA3-8B-it, Gemma2-9B-it; zero-shot, 9 prompt variations averaged): **In-Writing beats the NL-to-Format two-step baseline on almost every task** — GSM8K LLaMA 74.7→77.9 (Gemma 86.5→86.9), ShuffleObj LLaMA 27.0→39.0, and the classification gains are large: **DDXPlus Gemma 22.9→50.1 (+27.2 pp — the source of the "up to +27%" headline), LLaMA 12→30**, MultiFin Gemma 70→86.9, Sports LLaMA 69.5→77.4, Task280 LLaMA 65.3→74.0. With better prompt structure (In-Writing-IF/BF) LLaMA GSM8K reaches 80.0–80.5%, above the 79.6% of 8-shot CoT. Overhead: only **10–20 extra tokens (~0.5–1.5 s)** vs natural generation. Two caveats matter for deployment (correcting the earlier abstract-level phrasing): **(a) premature trigger-token generation is a documented failure, not an eradicated one** — small models (Qwen3-1.7B, SmolLM2-1.7B) emit `{` mid-reasoning and get forced into the schema early, so on GSM8K Text-to-NL beats In-Writing for them (the paper's mitigation: use `<eos>` as the unique trigger); and (b) In-Writing is "not a perfect parser" (Appendix A.4.1 shows constraint-decoding parse failures). This is one of the four measured format-tax remedy families (trigger-gated in-call decoupling) alongside reasoning-augmented grammars (CRANE), prompt-level decoupling (two-pass / thinking), and draft-conditioned decoding (DCCD).

**Fact (draft-conditioned decoding; verified in full text).** Draft-Conditioned Constrained Decoding (Reddy, Walker, Ide, Bedi; arXiv:2603.03305) formalizes the "hidden cost": constrained decoding is a repeated reverse-KL projection onto the prefix-valid set, and its quality degradation is driven by **low feasible mass** — per-step distortion KL = log(1/α(h_t)) where α is the probability the model assigns to valid next tokens, so the cumulative "projection tax" and trajectory-dependent bias grow whenever the schema forces low-probability syntax (braces, quotes, field names); on a toy single-slot JSON the constraint admits ≈1% of the vocabulary, so renormalization repeatedly perturbs the distribution toward locally-valid-but-semantically-wrong trajectories. DCCD's two-step, training-free procedure — unconstrained draft (semantic plan) first, then constrained decoding *conditioned on the draft* — raises feasible mass before masking, and it consistently beats standard constrained decoding (XGrammar) on every model×dataset in Table 2 (1B–14B; GSM8K, MATH500, GSM-Symbolic, FOLIO/Prover9): **GSM8K 1B: CD 15.24% → DCCD 39.04% (+23.8 pp); 1.5B: 49.36→73.92 (+24.6 pp, the largest gain)**; 7B 81.58→91.28; 14B 86.43→95.15; and it fixes GSM-Symbolic where CD collapses to 0.0 at 1B (DCCD 9.0). Parameter efficiency: a **1.5B+1.5B DCCD pair (3B total) scores 12.7 accuracy-per-billion on MATH500 vs 3.6 for an 8B CD model (≈253% better)**, and a 7B+1.5B pair (8.5B) beats a single 14B CD on GSM8K with 39% fewer parameters. Test-time scaling: sampling+voting drafts scales better than sampling under hard constraints — GSM8K DCCD 78→83% (n=1→13) vs CD 64→73%; MATH500 DCCD 42→47% vs CD 29→37%, saturating around n≈7. This is the fourth measured remedy family (draft-conditioned projection) alongside reasoning-augmented grammars (CRANE), trigger-gated decoding (In-Writing), and prompt-level two-pass.

**Fact (the format-vs-correctness gap is 100% at baseline and prompt-optimization closes it where decoding costs; verified in full text).** "When Correct Isn't Usable" (Galeone, Park, Ettorre, Ligorio; Alomana, arXiv:2605.02363) measures *output accuracy* = task-correctness × valid-JSON jointly, on GSM8K/MATH with a strict {reasoning, answer} JSON contract, three 7–9B models + a GPT-4o probe. Baseline: **NAIVE prompting reaches 77–85% task accuracy (GSM8K; GPT-4o 84.3%) yet 0% output accuracy across all models/datasets** — no model emits valid JSON without format guidance; **a minimal hand-written REFERENCE prompt still yields 0% output accuracy for Gemma-2-9B and GPT-4o** (both systematically wrap JSON in markdown fences, a model-specific generation default, despite 88.4%/95.7% underlying task accuracy recovered by a fallback parser). **CONSTRAINED decoding (vLLM JSON grammar) enforces validity but at 3.6×–8.2× inference latency and can degrade task performance** (Gemma GSM8K: 52.4% of constrained outputs are exact duplicates; output accuracy 15.3% vs 52.5% Llama), so on GSM8K constrained decoding beats only the 0% baselines and still loses to a good static prompt (Qwen REFERENCE 74.3%). The repair that wins is **automated system-prompt optimization (AloLab: iterative black-box optimizer, meta-agent Claude Sonnet 4.5, no fine-tuning): GSM8K output accuracy 84.15/87.41/85.75% (Llama/Gemma/Qwen) and MATH 34–40%, at 0.63–1.06× NAIVE latency** (optimization cost paid once), with 29/30 paired McNemar comparisons vs the best static prompt significant (p≈0); **GPT-4o jumps 0% → 95.2% [94.75,95.59]** by adding a single "no markdown fences" directive. Two ablations carry the mechanism: replacing the meta-agent with Claude 3 Haiku drops mean output accuracy 84.15→61.0% with std rising <1→21.8 pp (3/5 runs collapse) — *optimizer capability, not the loop alone, drives reliability*; and the residual failure class is **format-execution inconsistency — correct reasoning present but the answer field holds the wrong value, LLM-judge-verified at 1.5–1.8% of AloLab failures** (a serially-decoupled field, the same reasoning-value gap as §3). Implication for this report: on strict JSON contracts, the measured default is 0% output-accuracy *before any format handling*; constrained decoding guarantees syntax but pays 3.6–8.2× latency and can distort, and the cheapest measured fix is model-observed prompt optimization — reinforcing that format reliability is a *prompt/decode design decision*, not a property of the model alone.

**Fact (the constraint tax on small models: validity up, correctness down, errors go hidden; verified in full text).** "The Constraint Tax" (Ray, arXiv:2605.26128) is a paired validity-vs-correctness protocol on sub-3B SLMs (Qwen2.5-0.5B/1.5B, SmolLM2-1.7B; 15,000 generations, 5 deterministic task families, vLLM/SGLang/MLX; every number from logged artifacts). Main aggregate: **hard answer-only schema decoding raises schema validity 61.5%→100.0% (+38.5 pp) but lowers answer accuracy 19.7%→11.0% (−8.7 pp) and raises wrong-valid-schema outputs 49.5%→88.9% (+39.4 pp)** — the parser sees a cleaner stream while the executor receives more well-formed objects carrying wrong content. Per-model answer tax: Qwen2.5-0.5B −11.9 pp, Qwen2.5-1.5B −20.0 pp (largest), SmolLM2-1.7B 0.0 (its prompt-only baseline is so weak that constraints *help* — constraints aid when they remove syntax failures without disrupting search, hurt when they convert visible format failures into valid wrong decisions). The production analogue is the sharpest number: **a calendar tool-call task where prompt-only JSON reaches 91.5% executable accuracy (100% schema-valid) vs the same object hard-encoded as a schema reaching 48.0% executable accuracy (also 100% schema-valid) — a −43.5 pp executable loss, CI [−51.0,−36.0], with 102 of 104 failures being a single-field wrong `duration_minutes` (a 30-min meeting scheduled as 180)** — "the error is semantic, not structural," and a deterministic delayed-packaging control (reason free, constrain late: solve then re-serialize) keeps 91.5% at 100% validity. The tax does not vanish at the 3B boundary: Qwen2.5-3B pays −15.3 pp answer accuracy (39.0→23.7) with wrong-valid 43.6→75.2. Backend dependence: Qwen replicates across vLLM/SGLang but SmolLM2 differs (18.7 vs 25.7) — constrained decoding is a serving-path property, not model-only. The paper's deployment rule: report schema validity, answer accuracy, executable accuracy, and **wrong-valid-schema rate as a first-class reliability metric** (it counts failures that pass parsers — retries help invalid JSON but not wrong valid answers). Implication for this report: this is the small-model quantitative core of the §3 valid-but-wrong gap — enforcement moves the failure from *visible* (unparseable) to *hidden* (valid-but-wrong), exactly why §3's deterministic verifiers and the Verdict's "right verifier" point matter.

**Fact (token-level runtime control as a distinct enforcement layer; verified in full text).** ATLAS-RTC (Cruz, Purdue, arXiv:2603.27905) is a closed-loop controller that intercepts generation at the logit distribution each step (unlike static grammar constrained decoding or post-hoc validation): it observes a runtime state (entropy, invalid-token mass, contract stage), scores structural drift against a stateful *stage-aware* JSON contract, and applies a graduated six-level ladder — no-op → logit biasing → temperature modulation → token masking → mid-step KV-cache rollback/re-steering — masking only at structural decision points and leaving value-generation zones free (intervening during value generation "corrupts output; this was the primary failure mode of every prior approach we tested"). Measured on Qwen2.5-7B-Instruct, strict no-retry first-attempt evaluation: **structured JSON under ambiguous prompts: first-attempt schema validity 56.7%→76.7% (+20.0 pp; peak +23.3 pp on the hardest schema), with average latency *falling* 88% on the hard task (5,498→663 ms) because long malformed outputs are prevented**; **agent tool-call generation: first-attempt success 20.6%→58.3% (+37.8 pp), search tool 0.0%→96.7%, database_query 45.0→78.3** — "many failures arise from decoding artifacts rather than task misunderstanding" (baseline emits preamble tokens like "Sure"/"Here" before structured output). Rollback is rare (~0.8 corrections/run, max depth 3 tokens) — structural errors are localized. Honest failure characterization (matches the report-wide valid-but-wrong theme): **it enforces structure, not semantics — on send_email (missing required field "summary"), first-attempt success *drops* 16.7→0.0 pp because stricter detection exposes incomplete content the baseline sometimes passed stochastically**; it degrades on schemas requiring multiline string values and when the baseline already saturates. Implication for §4/§5: preventing malformed output *during* decoding is a cheaper alternative to the retry loop — it avoids the "malformed first attempt triggers retry loops that spike latency and inference cost before any safety predicate has been checked" — while leaving the semantic-value gap (§3) to verifiers.

**Fact (SE-wide error taxonomy and the limits of decoder-side enforcement; verified in full text).** "Empirical Study for Structured Output Control in LLMs for Software Engineering" (Song, Rajput, Sun, Ezzini, Bissyandé, Klein; Univ. Luxembourg, arXiv:2606.09395) is the broadest syntax/structural/value taxonomy measurement: 9 models (7 general-purpose incl. GPT-4.1-mini, 2 domain-specific) × 4 structured SE tasks (BigCodeBench code, Spider SQL, CallNavi JSON, BFCL v2 function-calling), zero-shot, error-classified. **Unconstrained: on the JSON and function-calling tasks, syntax+structural errors account for ~80.7% of all failures** (e.g., LLaMA-3.1-8B emits 1,833 syntax errors on BFCL v2; Gemma2-9b 2,203), while coding tasks (BigCodeBench/Spider) have <20% format-related failures — structure is the dominant failure mode exactly where JSON/API contracts apply. Enforcement results (Outlines/LLGuidance/XGrammar, CFG Lark grammar for JSON/SQL, regex for function-calling; SGLang): **grammar/regex enforcement cuts syntax errors to near-zero but improves task-level accuracy only modestly** — CallNavi exact-match 0.4883→0.5130 (+2.5 pp, structural errors persist ~300/729, i.e., most outputs valid-JSON-but-structurally-wrong), Spider pass@1 0.6767→0.7113; the single large gain is BFCL v2 AST-match 0.1759→0.5274 because unconstrained function-calling was dominated by syntax failure. Two findings matter for enforcement design: (a) **Mixture-of-Experts models gain almost nothing from decoder-side constraints** — Qwen3-30B-A3B exact-match unchanged (0.5665), Mixtral-8x7B AST-match rises only 0.4086→0.5277 under Outlines and *collapses to 0.2363 under LLGuidance* (worse than unconstrained) — because logit masking operates after expert routing, so it suppresses invalid tokens but cannot redirect the committed routing trajectory (structural errors stay ~408–622); (b) **usable grammars are scarce** — of the top-10 TIOBE languages, only Python (Lark) and SQL (Lark) grammars parsed even a basic control-flow test, GBNF coverage is nearly absent, and the BigCodeBench Python grammar crashed Outlines/LLGuidance decoders (indentation/nesting), excluding the code task from CFG evaluation entirely. Stability: constraints do not hurt output fluency (BLEU/pass@5 ~unchanged). The paper's strict control, **TTMG (template token-match generation: fixed-format scaffolding tokens + free-form spans) "nearly eliminates syntax errors, yet substantial structural and semantic errors persist"** — direct confirmation that syntax enforcement is necessary but insufficient, matching the report-wide valid-but-wrong theme.

**Fact (the grammar-scarcity bottleneck has a measured remedy: learned CFGs; verified in full text).** Autogrammar (Cheang et al., AWS; arXiv:2608.05493) addresses the [63] finding that "usable grammars are scarce": for low-resource DSLs there is no hand-written grammar, and GCD cannot be used without one. Motivation quantified: across 416 AWS services (Boto3), **23% expose a string parameter that must conform to a DSL, and AWS uses ≥59 unique DSLs** — all low-resource vs Python. Autogrammar is a declaratively-specified agent (Kripke structure + LTL constraints; an LM resolves nondeterministic choices) that **learns a context-free grammar from documentation + execution logs** (no membership oracle), then plugs it into any GCD tool. Measured on three DSLs (CloudWatch Logs Insights, Dynatrace Query Language, Datadog Search Syntax; 5-fold CV): learned grammars achieve **near-perfect precision on unseen data — 0.999 / 1.00 / 0.910 (CWIL/DQL/DSS)** — vs **Arvada (SOTA formal grammar-induction, oracle-based): 0.025 precision on CWIL despite ~63k oracle calls / ~14.6 h** (the grammar rejects 97.5% of valid queries), and vs direct-LM baselines (LM-0 0.046/0.228/0.023; LM-40 0.074/0.510/0.115) — an order of magnitude below Autogrammar. Ablations: **execution data is crucial; documentation is largely dispensable** (no significant CWIL/DSS precision loss without docs; DQL only 1.00→0.975), and LTL performance constraints cut learning time 3.8× with no statistically significant precision loss. End-to-end: **a GCD loop using an Autogrammar grammar significantly improves LM success on 8/10 real CloudWatch tasks and matches or exceeds a professionally-maintained grammar** (6 LMs × 100 calls × 10 tasks). Implication: the GCD "grammar availability" constraint is removable — grammars can be learned from execution logs, so constrained decoding's coverage gap is now a *data-availability* problem, not a *grammar-authoring* problem; this is the supply-side complement to the efficiency results (XGrammar/PSC) and the enforcement-quality results.

**Fact (schema key wording is itself an instruction channel under constrained decoding; verified in full text).** Le (arXiv:2604.14862, Zhejiang Univ.) is a controlled ablation that holds model, prompt, output structure, and decoding engine (XGrammar) fixed and varies only *where* an instruction signal lives — in schema key wording, in the prompt, both, or neither (None = baseline constrained decoding) — across 7 open models on GSM8K/Math500. The finding: **merely rewording schema keys (semantically-loaded keys like explicit "step-by-step reasoning" vs neutral names, structurally identical schemas) significantly changes task accuracy under constrained decoding, in a model-family-dependent direction**: Qwen2.5-7B GSM8K 79.61→**86.50 under Key-only (Δ+6.89)** and Math500 37.20→41.0, Qwen2.5-Coder-14B best under Both (+4.93); but **Llama-3.2-3B drops 53.15→37.38 under Key-only (Δ−15.77)** while Prompt-only/Both improve it (+3.18/+4.55), and Llama-3.1-8B shows 0.00 Key-only change vs +3.94/+4.70 prompt channels. So **Qwen models read the schema as a task instruction; LLaMA models treat schema-level wording as distraction and prefer prompt-level guidance**. Interaction is non-additive: on Qwen2.5-7B Math500, "Both" falls *below* the baseline (25.20 vs 27.80), i.e., adding the schema channel can dilute or conflict with the prompt signal. Implication for this report: schema design is a *free reliability lever* orthogonal to decoding — identical JSON structure with different key names can move accuracy by ±15 pp depending on model family — so "schema-valid ≠ correct" (§3) and the enforcement-quality picture (§2) are partially determined by wording, not just structure, and the same key wording that helps one family can hurt another.

**Fact (the *token* format of constrained output is a free reliability lever; verified in full text).** "Lost in Space: Optimizing Tokens for Grammar-Constrained Decoding" (Hamilton & Mimno, Cornell, arXiv:2502.14969) extends the format-choice dimension one level down, from schema wording to the *token set* a grammar admits. On 1.28 million GCD classifications (4 model families × 8 sizes — Llama 3.1 8b/70b, Qwen 2.5 7b/72b, Gemma 2 9b/27b, Phi 3 3b/14b; llama.cpp GBNF; 4 benchmarks), five output formats that "appear semantically similar to humans" produce large, systematic accuracy differences: **real numbers in [0,1] perform best across all models (Spearman ρ 0.420–0.609) while integers/binaries are worst (integer ρ = −0.160 for Llama 3.1 8b)** — so *which* tokens the grammar admits moves classification correlation by ~0.5+; **leading-whitespace tokens improve performance 5–10%** (a leading newline/space is enough), because LW and non-LW token twins are *not exchangeable* in embedding space (cosine similarity only 0.369 (8b) → 0.386 (70b) vs ~0.008–0.016 for random token pairs) and **LW tokens were 2.5–2.7× more prevalent in pre-training data** (Dolma tokenization; Phi's smaller 1.66× ratio matches its non-response to whitespace); **word-form outputs are consistently worse than digits** (ρ −0.12 to −0.41). Format sensitivity is strongest for smaller models (large models show less differentiation) — the same capacity-dependence as the format tax. Best practices: evaluate multiple formats, keep leading whitespace in grammars, prefer numeric token ranges, prefer less-restrictive patterns (e.g., [0,100] over [1,10]), and use larger models. Implication: this is the *tokenization* level of the §2 format-choice finding — a grammar that admits the semantically-equivalent but differently-tokenized output can cost ~0.5 Spearman correlation in classification; complements the schema-key-wording lever [64] and the TOON format-choice result [72] as the third, most granular measured "format is not free" dimension.

**Fact (novel-format structural-correctness is capacity-dependent; verified in full text).** "Are LLMs Ready for TOON?" (Masciari, Moscato, Napolitano, Orlando, Perillo, Russo; Univ. Naples/Univ. Bergamo, arXiv:2601.12014) benchmarks the token-efficient TOON format against JSON/XML/YAML across **8 models (GPT-oss-20B/120B, Gemma 3 4B/12B/27B, Mistral 7B, Llama 3.3 70B, Qwen 3 4B), 50 paired generation instances, decode-only metrics (tokens, time, CodeCarbon emissions) + StructEval correctness (Render + Syntax + GCS)**. The format-without-native-support cost is quantified precisely: TOON cuts generated tokens **−26.4% vs JSON, −49.4% vs XML, −15.3% vs YAML** and estimated carbon emissions **−82.9%/−87.6%/−76.9%** (EES 0.98 near-ceiling), but **structural correctness collapses — GCS 0.513 vs JSON 0.840 (−38.9%), YAML 0.872 (−42.2%), XML 0.563 (−30.9%); Render Score 0.630 vs ~0.99 for baselines** — because TOON is enforced only via prompt instructions (not natively supported). The decisive finding for this report: **the correctness gap is model-capacity-dependent** — Llama 3.3 70B shows *no statistically significant* TOON-vs-baseline difference (p>0.05 vs all formats), GPT-oss-120B/20B eliminate the XML gap, while **Gemma 3 4B fails nearly completely (TOON GCS 0.045 vs JSON 0.779)** and Qwen 3 4B drops 0.769→0.334. Environment-aware GCS_env (γ=0.5) narrows but does not reverse the gap. Implication: novel/compact structured formats are only usable on models with enough capacity to internalize unseen structural constraints — the same capacity-dependence as the format tax (§2) and the schema-key-wording lever [64], and a measured argument that format *choice* (including TOON's ~50% token savings) is a deployment trade-off, not a free win.

**Fact (diffusion LLMs: structured-output collapse under stochastic sampling and its enforcement remedy; verified in full text).** Dang & Ermon (Stanford, arXiv:2607.07026) is the cleanest measurement of the *sampling-regime* dependence of structured-output reliability, on diffusion LLMs (Dream-7B, LLaDA-8B) across function calling (xLAM, BFCL), planning (Sudoku, Countdown), SQL (Spider) and math (GSM-Symbolic). Baseline finding: **switching from greedy to stochastic sampling destroys unconstrained dLLM structured-output accuracy — Dream BFCL-Live (JSON) 63.9% → 22.3%** (the collapse is constraint-satisfaction-driven), and unconstrained dLLMs are far behind same-size autoregressive models on BFCL (Dream non-live 36.3 vs Llama-3.1-8B 84.0). The **format gap is structural, not semantic**: Dream BFCL-Live JSON 63.9% → Python 22.4% (the models know the call but not the format). The remedy — exact constrained decoding over finite automata (constraint as a chain graphical model; guaranteed 100% constraint satisfaction by construction; log-depth tree sampler): **BFCL-Live Dream greedy 63.9→71.5 and stochastic 22.3→69.0 (near-greedy recovery); Python 22.4→69.7; xLAM JSON 74.6→76.6; Sudoku 36.4→92.4; Countdown 53.6→100** — narrowing the dLLM-vs-AR gap on BFCL (Dream non-live 36.3→78.3 vs Llama-3.1-8B 84.0). Overhead: tree sampler +12 accuracy points at only **+4% wall-clock** (chain variant +114% — the depth-reduction matters). Ablation: recomputing remasking confidence under the *constrained* marginals beats mean-field confidence, largest where the model's mean-field is misaligned with the constraint. Limitation: covers finite automata only (not CFGs; Spider uses a ~10k-state/100k-edge NFA). Implication for this report: enforcement value is **decoding-regime- and architecture-dependent** — the same model collapses under sampling and recovers under exact constraint inference; this is the dLLM complement to the AR-model constrained-decoding results (§2/§4) and to the sampling-stack corruption finding [73] (both show reliability is a property of the full decode path, not the model alone).

**Fact (a serving-stack sampler setting silently corrupts schema compliance; abstract-level, no HTML).** Hollows (arXiv:2607.09791, 8 pp) identifies a failure mechanism *outside* the model, prompt, and grammar: the **multiplicative repetition penalty shipped across HuggingFace, vLLM, llama.cpp, and a dozen further engines** divides positive raw logits by θ and multiplies negatives — but because softmax is invariant to adding a constant to every logit, the sign of each raw logit depends on the model's *arbitrary* logit zero-point, so the penalty's sign-branch reads a gauge-dependent quantity. Two measured consequences: (1) the penalty is ill-defined — recentering logits is a provable no-op at θ=1, yet at the routine θ=1.3 it **changes 58–96% of greedy tokens** (subtractive/normalized penalties change none), and real checkpoints sit at different zero-points, so a fixed `repetition_penalty` is a different operation per model; (2) **it corrupts structured output — on 200 real-world JSON schemas, θ=1.3 drops the rate of valid, schema-conformant output from 97% to 23%** (measurements on five ≤7B models base+RLHF over WikiText-103, plus two code models on HumanEval/JSONSchemaBench, replicated inside vLLM and llama.cpp samplers). Fix: apply the penalty to *normalized* log-probabilities instead of raw logits (HuggingFace already ships `LogitNormalization`, off by default and applied after the penalty). Implication for this report: a routine, default-on sampler hyperparameter can destroy 74 points of JSON compliance that neither constrained decoding nor retries can recover (the output is "valid under the penalty" but not schema-conformant) — so structured-output compliance measurements must pin the full serving stack (sampler settings, zero-point gauge) and not only the model/grammar; this is the sampling-side complement to the backend-dependence result in the Constraint Tax [65] and the TSCG serving-path point [66].

### 3. Schema-valid ≠ correct: semantic failure of enforced JSON

**Fact (frontier multimodal structured-output validity under a strict schema; verified in full text).** NeuroVLM-Bench (Trojachanec Dineva et al., Ss. Cyril and Methodius Univ.; arXiv:2603.24846) evaluates 20 frontier MLLMs (GPT-5/4o/4.1, Gemini 2.0/2.5, Claude Sonnet 4.5, Grok-4, Llama 3.2/4, Qwen2.5-VL, MedGemma 1/1.5, Nova) on 29,538 neuroimaging samples under a frozen Unified Neuro-Imaging Prompting Protocol: models must emit a 6-field structured JSON schema (modality, specialized sequence, plane, diagnosis, detailed diagnosis, confidence; controlled vocabulary preventing hallucinated labels), and are scored on discriminative performance + **JSON validity** + calibration + cost, in a four-phase (calibration→screening 20→11→6→held-out) protocol. Structured-output-validity findings: **valid-JSON was generally high, but Grok 4 and Claude Sonnet 4.5 exhibited significantly lower valid-JSON rates (84–87%)** — deployment-relevant failures "even when classification performance was moderate"; **MedGemma-1.5-4B, MedGemma-1-4B, LLaMA-4-Maverick, and Qwen2.5-VL-32B maintained perfect JSON validity with near-zero abstention** (and a 4B model reached strongest open-weight diagnostic performance under few-shot); **LLaMA-3.2-Vision (11B/90B) failed almost entirely via excessive abstention** (near-zero Macro-F1 driven by refusal, not wrong answers). The schema-valid≠correct split reproduces in the multimodal domain: **models differ far less in basic imaging-metadata recognition (modality/plane nearly solved) than in clinically meaningful diagnostic reasoning (subtype prediction)** — several open-weight models show strong metadata+validity but weak diagnosis, the same "scaffolding correct, content inside wrong" pattern as §3/SOB. Implication: at the frontier-multimodal scale, schema compliance is achievable by most models (perfect validity for many), but the residual failure is semantic (diagnostic reasoning), and two frontier models still fail validity at 13–16% — consistent with this report's theme that enforcement fixes syntax, not substance.

**Fact (verified in full text).** OrderBench (Li, arXiv:2607.18261; 2,400 Nebius Token Factory calls, 4 open models, 300 cases × 2 modes, temperature 0, deterministic verifier) quantifies the schema-valid-but-wrong gap precisely (Table 1): GPT-OSS-120B-fast achieves **100% JSON and schema validity in both modes yet semantic success is 83.0% (prompt) / 81.3% (JSON-schema)**; Qwen3-30B-A3B also 100% schema-valid with semantic success only 30.7–31.3% and unsafe acceptance ~14–15%; Llama-3.1-8B — the enforcement success story — sees schema validity rise 68.7%→100% and unsafe acceptance fall 13.3%→8.3% (McNemar p=0.001), but semantic success stays 31.7–36.0%; **Gemma-2-2B is the starkest counterexample: JSON-schema mode yields 100% schema-valid objects with 2.0% semantic success and 41.7% unsafe acceptance**. Category-level unsafe rates reach 35.8% (allergen-conflict), 25.8% (dietary-conflict), 51.7% (unavailable item) — all in schema-valid output. Paired comparison (Table 5): JSON-schema mode significantly reduces unsafe acceptance for the two weaker models but never eliminates it, and for the strongest model it slightly lowers semantic success (−1.7 pp, CI [−5.0,+1.7]). The paper's deployment rule is a four-layer contract: strict structured output → domain-catalog/safety validation → **fail closed on verifier errors, "using clarification rather than auto-repair for safety-critical fields"** → log model output + verifier decisions as paired regression artifacts. I.e., for safety-critical structured output, auto-repair is explicitly contraindicated in favor of fail-closed clarification.

**Fact (schema-breadth collapse; verified in full text).** ExtractBench (Ferguson, Pennington, Beghian, Mohan, Kiela, Agrawal, Nguyen; Contextual AI, arXiv:2602.12247, Tables 5–7) is the primary source behind the 4.6% figure cited in SOB: 35 PDF documents across 5 domains with JSON Schemas and human gold labels, 12,867 evaluatable fields (2,076 pages, 67.9 h annotation). Aggregate field-level pass rate **4.6% (844/18,516 field evaluations across 6 frontier models); best model (Gemini 3 Flash) 6.9%**; valid-JSON rate 51% (107/210), with valid-only field accuracy 72.9% (i.e., valid≠correct even when valid). "Performance degrades sharply with schema breadth, culminating in **0% valid output on a 369-field SEC 10-K/Q financial reporting schema across all tested models**" (0/2,583; the 369-field schema is 84% of all field evaluations); excluding 10-K/Q, pass rate is 28.0%. Complexity analysis: schema breadth is the dominant predictor, output volume (gold tokens; 10-K/Q needs ~24.4k output tokens) is the binding constraint, array complexity amplifies difficulty, and nesting depth is a weak predictor (Sports: depth 6 yet 90% validity but only 12.5% pass — valid-but-wrong again; Credit: 13 keys, 56.3% pass). Failure-mode breakdown (Table 7): empty response 40%, trailing commas 30% (Claude/Gemini-only, concentrated in 10-K/Q), PDF page limit 19% (Claude 100-page limit), truncation ~9% — so ~30% of failures are formatting issues potentially fixable by post-processing or constrained decoding. A second, larger ExtractBench (Zhang, Lyjak, Stewart, Li, Suo; LlamaIndex, arXiv:2607.29677, **verified in full text**) extends to 4,869 pages / 370 enterprise documents / 8 domains / 67 document types / 14 systems and shows the length-side of the same collapse: unified value F1 on long (>50 pp) documents collapses from short-document levels for commercial VLMs (Gemini 3.5 Flash **87.9% short → 27.9% long**; GPT-5.4 Nano 77.4 → 35.8) while coding agents/specialized APIs stay high (LlamaExtract Agentic Plus 96.6/93.3/94.4 across short/med/long; Codex GPT-5.5 95.7→78.9; Reducto Deep 94.2→92.0). The long-document failure is **recall-concentrated, i.e. truncation not misreading**: precision stays high while recall collapses (L3 P→R: Gemini 3.5 Flash 83.7→26.5, Δ+57.2; NuExtract3 50.1→5.8, Δ+44.3; GPT-5.4 Nano 71.2→33.7, Δ+37.5; Qwen3.6-35B 51.0→25.7, Δ+25.3; vs Codex 94.0→78.6, Δ+15.4), with the worst stress being a 26,725-row unclaimed-property list — "entire records are dropped rather than misread," attributed to single-pass context limits ("those without a strategy for iterating over it stop early, truncating the remaining records"). Enormous tables (S4) are the sharpest binary: specialized/coding systems score 78.9–95.9 (LlamaExtract Agentic Plus 95.9, Reducto Deep 95.3, Codex 78.9) vs ≤7.2 for every direct VLM (Gemini 3.5 Flash 1.5, GPT-5.4 Nano 7.2, Gemma4-26B 0.0, NuExtract3 3.7). Two **end-to-end zero-output failure patterns**: (a) Claude Code Opus 4.8 and Gemini 3.5 Flash score **0.0 on the T3.d W-14 twin-schema case and return nothing on the largest-schema Form 1040 bundles** — pipeline-level failures where no output is produced (the paper notes a controlled sweep would be needed to attribute to schema size); (b) all Claude one-shot VLM tiers **reject the Automotive and K-1 schemas outright before responding — 33 rejections (8.9% of the pool) score zero** and remain far behind even on completed docs (Haiku 4.5/Sonnet 4.6/Opus 4.8: 32.9/34.6/33.0 F1). Cost scaling is non-monotonic: within-family, GPT rises 74.9→88.7 F1 at 0.21→6.86 ¢/page, Gemini stays flat (79.6/79.8/78.2 F1 at 0.17/1.00/3.83 ¢), Claude non-monotonic (29.9/31.5/30.1 at 0.80/2.40/4.89 ¢) — "model tier alone does not predict extraction quality." Best quality–cost point: LlamaExtract Agentic Plus **95.6 F1 at 8.1 ¢/page beats Codex GPT-5.5 93.6 at 27.8 ¢/page**. Grounding gap: word-level grounding F1 only the specialized APIs return (best 46.4); every commercial VLM and coding agent scores 0.0 (no boxes). Together with SOB these establish that the semantic-value ceiling drops with schema breadth and context length, and that a different cost/accuracy point (coding-agent pipelines) is where the accuracy lives at scale.

**Fact (real-world production-scale validation of the schema-complexity failure thresholds; verified in full text).** ScrapeGraphAI-100k (Brach, Zuppichini, Vinciguerra, Padoan; arXiv:2602.15189) is the largest real-world schema-constrained extraction corpus: **93,695 opt-in production telemetry events (from ~9M, deduplicated to ≤5 per schema), 18,000+ unique JSON schemas**, each pairing real Markdown web content + prompt + schema + LLM response + per-example jsonschema-rs validity label. It independently confirms the §3/ExtractBench complexity-collapse findings at production scale with quantified thresholds: **average raw-corpus schema-validity is ~93%, but validation falls sharply and non-linearly at structural breakpoints — depth ≥7 drops validity 98%→20%; key count ≥200 drops it to ~65%; composite complexity score >1,000 drops it to ~55%** (with schema-complexity metrics near-perfectly multicollinear, r≥0.98, so key count alone is a sufficient complexity proxy; validation negatively correlates with complexity, r=−0.15 to −0.20). Corpus shape: median schema depth 5, median 37 keys, max 3,060 keys; responses median ~134 B but up to ~164 KB. Caveats: **87.4% of requests came from GPT-4o-mini** (behavior biased toward one model) and validation measures syntactic schema compliance only, "not semantic correctness — a response may be structurally valid yet factually incorrect." Distillation experiment (Qwen3-1.7B fine-tuned, GPT-5-nano teacher labels, N=2,714 eval): schema compliance 0.7954→0.9167 (+15 pp) and extra keys/sample 2.64→0.33 (below the 30B baseline's 0.57) — fine-tuning closes most of the *structural* gap (key F1 0.8866 vs 30B 0.8915) — **but the value score stays at 0.4624 vs the 30B's 0.4797: "correctly identifying which fields to extract is easier than accurately extracting what those fields contain"** — a production-scale restatement of the schema-valid-but-wrong value gap that all of §3 and §6 measure.

**Fact (origin of the format-tax finding; verified in full text).** Tam et al., "Let Me Speak Freely?" (arXiv:2408.02442, Tables 1–3/9–11) is the 2024 foundational measurement: format restrictions (JSON/XML/YAML) significantly degrade LLM *reasoning* while stricter constraints degrade more. Headline drops (exact-match): GSM8K **Claude-3-Haiku 86.5 → 23.4 under JSON (−63 pts)**; GPT-3.5-Turbo 75.99 → 49.25; LLaMA-3-8B 75.13 → 48.90; gpt-4o-mini JSON-Mode 94.57 → 86.95 (Gemini-1.5-Flash was already immune). Crucially, the degradation is **not parsing failures**: the Last-Letter JSON parsing error rate is 0.148% yet the performance gap is 38.15 points — format compliance succeeds while reasoning collapses. Task-dependence established: the same constraints *help* classification (Gemini DDXPlus 41.6 → 60.3 under JSON-mode), so "format restriction hurts reasoning, helps classification" — the origin of the capacity-competition analysis in the two studies below.

**Fact (the format tax is prompt-driven and capacity-dependent; two studies).** (1) "The Format Tax" (Lee, D'Antoni, Berg-Kirkpatrick; arXiv:2604.03616; **verified in full text, Tables 1–5**): across 6 open-weight + 4 API models, 4 formats, 4 tasks, structured output degrades every open-weight model (avg −5.8 to −8.7 pp; 76 of 144 cells significant, 72 in the tax direction), and the source decomposition is decisive: **of 39 cells with significant effects, 36 (92%) are already degraded by the format-requesting prompt alone, only 15 (38%) involve constrained decoding, and only 3 cells are GCD-only** (avg GET· delta −3.9 pp vs −1.6 pp for GCD); GCD lifts format compliance 55.7%→92.2% with accuracy unchanged (57.3% vs 55.7%) — so "sampling bias accounts for only a fraction of the degradation; the dominant cost enters at the prompt." Mitigations: **2-Turn freeform-then-reformat recovers most loss (42 of 72 cells improved, +6.8 pp avg, only 2 worsened ≈3% risk) at ~2× cost; thinking recovers more (+9.2 pp) but riskier (15% worsened)**; prompt enrichment (schema/few-shot) does not close the gap. Newer closed-weight models (claude-haiku-4.5, grok-4.1-fast, gpt-5.4-nano) show near-zero tax; the paper cites Banerjee et al. (2025) proving finite output grammars without reasoning tokens reduce expressivity to TC0 — formal justification for decoupling. (2) "Capacity, Not Format" (Fan, arXiv:2606.09410; **verified in full text, Tables 1–8**): with information-matched prose controls and 0% parse failures across 4 models/5 benchmarks, JSON constraints are capacity-dependent — Sonnet absorbs them (88.7±4.0% JSON vs 89.3±1.7% CoT on MATH-Hard, p=0.25), but near-limit models degrade via two mechanisms: Haiku −36.2 pp (p<0.0001; largely truncation) and GPT-4o-mini −28.0 pp (p=0.0002) even with extended budgets (pure capacity competition). The **format-specific component (JSON minus detailed-prose control) is −28.2 pp (Haiku) and −19.3 pp (GPT-4o-mini)** while the prompt-length component is only −0.3 to −8.0 pp — the harm is premature serialization, not instruction length. Penalty scales with schema complexity (dose-response; McNemar p<0.0001). **Production-mode comparison (GPT-4o-mini, MATH-Hard, Table 3)**: CoT 60% → API JSON mode 51% (−9 pp, ns, *fewer* tokens) → instruction-heavy JSON 34% → **forced function calling 10% (−50 pp)** because under tool_choice=forced models emit only tool-call arguments with no reasoning surface. Frontier immunity is qualified: Opus 4.7 on AIME drops 96.2%→91.0% under JSON (−5.3 pp). Think-first-format-later recovers 79.5% (Haiku) / 86.9% (GPT-4o-mini) of the lost gap; failure analysis shows the tax diverts effort (Haiku 57% reasoning omissions) rather than corrupting format. Combined with JSONSchemaBench's ~+3 pp and TOON's slight-plain-JSON-advantage, the measured consensus: schema *enforcement* (decoding) is roughly cost-neutral on quality, but the *format request itself* is a real, capacity-dependent reasoning tax on open-weight and near-limit models — with "think first, format later" / two-pass as the measured mitigations, and forced-tool-calling as a production hazard on hard reasoning.

**Fact (verified in full text).** SOB (Singh, Khurdula, Khemlani, Agarwal, arXiv:2604.25359; 21 models, 5,000 text + 209 image + 115 audio records, temperature 0, exact leaf-value scoring): best Value Accuracy is **0.830 on text (GLM-4.7)**, 0.672 on images (Gemma-4-31B), 0.237 on audio (Gemini-2.5-Flash). The structural metrics sit near-ceiling while value accuracy is not: every model has JSON Pass ≥84%, and the JSON-Pass-vs-Value-Accuracy gap is a consistent **15–25 percentage points**; GPT-5.4 reaches 99.7% JSON Pass but only 48.6% Perfect Response. 16 of 21 models score ≥96% on Path Recall/Structure Coverage/Type Safety while Value Accuracy spans 0.693–0.830 and Perfect Response collapses to 0.376–0.526 — "the scaffolding is correct; the content inside it is not." Model size does not predict value accuracy (Phi-4 14B 0.798 > GPT-5 0.795; Schematron-8B 0.754 > GPT-OSS-20B 0.693); GPT-5.4 beats GPT-4.1 by only +0.02. **Structured-decoding ablation (Table 3, audio, n=115)**: adding explicit schema-constrained decoding moves Value Accuracy only −0.007 to +0.033 across three models (Gemini-2.5-Flash +0.033, GPT-5.4 −0.007), while JSON Pass rises for two and *falls* for GPT-5.4 (0.869→0.808) — the cleanest controlled evidence that schema enforcement improves structural reliability but not value correctness. The paper also cites Park et al. (2024): naive grammar-constrained decoding "distorts the LLM's distribution toward syntactically valid but semantically degraded outputs."

**Fact.** CONSTRUCT (Goh & Mueller, arXiv:2603.18014): "Structured Outputs from current LLMs exhibit sporadic errors"; introduces a four-dataset ground-truth structured-output benchmark and an uncertainty score to route low-confidence outputs to human review (claim about errors being common enough to warrant routing; no single global rate).

**Fact.** IFEval-FC (Skripko, arXiv:2509.18420): format constraints embedded in a JSON schema's *description* field (e.g., "value must contain no punctuation", ISO date, lowercase) are **not enforced by constrained decoding**, and models fail them at high rates. On 750 function-calling test cases with algorithmic verification, "no evaluated model surpassed 80% accuracy" overall; frontier models fail specific basic constraints most of the time. Per-constraint adherence examples (Tables 2–4): Claude Opus 4.1 — "Letter Frequency" 28%, "N All Capital Words" 20%, "Spaces In Between" 8%, "N Commas" 52%, "Json Format" 68%; GPT-5 minimal — "Letter Frequency" 36%, "N All Capital Words" 76%, "Spaces In Between" 88%. Note these tables list only the studied models (Anthropic, OpenAI, GigaChat families); trivially-easy constraint types that hit 90–100% were deliberately excluded from the benchmark. Implication: schema-validity is only as strong as the *enforceable* subset of the schema — human-readable format rules in descriptions remain a prompt-following problem, not an enforcement problem, and are the dominant residual failure mode in function calling.

**Fact (nested/hierarchical output constraints are a large measured gap; verified in full text).** IFHierBench (Mao & Chen, TUM; arXiv:2607.27912) is the first benchmark to scope deterministic constraint checks to *nested output regions* (600 prompts, 4 constraint-tree depths d=0..3 with 150 each, 35 constraints, per-prompt deterministic Python checkers — no LLM judging). It derives 10 structure-level constraint types from an empirical analysis of **1,232 real LLM-application prompts** (GitHub; JSON 14.0%, labeled sections 15.0%, Markdown 8.9%, List 12.7%, String 50.8% of format-bearing prompts; **67.8% of format-bearing prompts carry ≥1 nested scope**, 28.2% declare two or more formats, and constraints occupy 46.4% of prompt text on average) — so nested structured output is the real-world norm, not an edge case. Results across 7 models (GPT-5.5, Claude Opus 4.6 high-thinking; Gemini-3-Flash, DeepSeek-R1, Kimi-K2.5; Qwen3.6-35B, Gemma-4-26B): **even the strongest model only marginally exceeds 50% prompt-level accuracy (GPT-5.5 53.7%; Claude 42.8%; others 14.7–33.2%)**, and **every model loses 37–53 absolute points from d=0 to d=1 (GPT-5.5 86.7→49.3, Claude 78.7→42.0)** — the "universal cliff at the very first level of nesting"; at d=3 only the two strongest retain >20% (35.3/22.7), all other models collapse to ≤6.0%. The two failure signatures matter for repair design: (a) four weaker models show scattered *content slippage* (instruction-level ≫ prompt-level — individual leaf constraints pass but rarely all in one response), while (b) Gemini-3-Flash shows the opposite — an outer-container failure marks every descendant leaf N/A, dragging whole subtrees down (instruction-level 24.1% < prompt-level 33.2%). Hardest constraint types are the *numeric* ones (exact string_length pooled 53.5%, num_words 67.3%, nth-paragraph-first-word 73.2%, num_sentences 81.4%) — GPT-5.5/Claude/Gemini pass these at 68–98% vs 24–66% for the other four. Implication for this report: this is the *structure-scoped* analog of IFEval-FC — the deeper a JSON/section constraint tree, the worse compliance, and the failure mode shifts from per-leaf slippage (repairable by local retry) to whole-subtree structural failure (requires re-parse + rerender, not value-level patching).

**Fact (constraint-stacking collapse — accumulating instructions silently break compliance; verified in full text).** "Instruction Stacking Collapse" (Anand & Chattaraj, arXiv:2608.02639) quantifies the *count* dimension that IFEval-FC and IFHierBench leave flat: a benchmark of 24 verifier-checked instructions (22 deterministic) across 6 categories (format/length/lexical/structural/reasoning/content), stacked uniformly at random into prompts of size 1–20, evaluated on Claude Sonnet 4.6, GPT-5-mini, and Gemini 2.5 Flash. **Follow rate falls from ~96% at one instruction to 0.60 (Sonnet), 0.43 (Gemini), and 0.20 (GPT-5-mini) at twenty** — non-linear (sigmoid) decay, and critically **"a single 'output JSON' constraint is jointly unsatisfiable with nine others"**: of 231 instruction pairs, 15 are logical impossibilities (valid JSON cannot carry markdown headers, exactly-5-bullets × Assumptions, ≤50 vs ≥150 words), and **~12% of the *satisfiable* pairs still fail far more than their parts predict** (e.g., "exactly 5 bullets" × "Assumptions section" joint rate 0.00; the JSON × title-length pair is −1.00) — the failure is *structured interference*, reproducible across models (cross-model interaction Spearman +0.23–+0.28) and tasks (+0.44), not uniform forgetting; "output JSON" is the dominant conflict hub. A training-free **instruction compiler** (one LLM call that clusters/merges by category, adds precedence notes, reformats as a checklist; reused across queries) gives a **capability-graded recovery: +11.0 pp for GPT-5-mini, +3.3 pp for Gemini, −1.2 pp for Sonnet** (cluster-robust; controls rule out extra tokens/reordering/headroom; within-family ladders show Spearman −0.85 between raw strength and recovery). Implication for this report: stacking a JSON-output requirement with other constraints is measurably harmful *even at the prompt level* — one JSON constraint silently invalidates up to 9 others — which bounds what any decoder-side enforcement can do (the 15 logical impossibilities set a prompt-only-recovery ceiling), and the compiler result matches the §2 capacity-dependence (the fix pays off exactly where compliance is weakest).

**Fact (formal limits of certifying structured output — a lower bound on what verification can promise; verified in full text).** "When Can Conformal Risk Control Certify LLM Outputs?" (Kotte, arXiv:2606.29054) gives the statistical ceiling for the "verifier" layer this report keeps returning to: risk-controlled abstention (conformal risk control, CRC) for NER / JSON extraction / QA / classification, evaluated across 6 open models (3B–72B), 8 datasets, 6 nonconformity scores, 656 configurations. First, **model confidence is miscalibrated for structured output**: models report 74–97% average confidence while actual risk ranges 3% (JSON) to 80% (NQ Open), ECE 0.05 (JSON) to 0.61 (QA) — so naive confidence thresholds are unreliable abstention signals (heuristic abstention misses user risk targets by **7.5–12.5%**). Second, a **closed-form impossibility bound**: whenever base risk μ > target risk α, *any* distribution-free certifier must abstain on ≥ (μ−α)/(1−α) of examples — e.g., CoNLL NER at 72B (μ=0.24, α=0.10) forces ≥16% abstention; at 3B (μ=0.42) ≥36%; NQ Open (μ=0.80) forces ~78% abstention at α=0.10, so **hard NER/QA/CLS are uncertifiable at α=0.10 (near-0% certified configurations)** and only relax to 47%/40%/60% certification at α=0.30–0.40; the path to certification is reducing μ (model scale: CoNLL μ 0.42→0.24 from 3B→72B), not tighter bounds. Third, the bound hierarchy is strict (Hoeffding 8.7% < Bernstein 11.9% < betting e-CRC 12.2% certified of 656; Bernstein is the default upgrade, e-CRC only wins with <20% calibration data). **JSON extraction is the easy case: μ≈0, so it certifies at all scales with zero abstention** (14B guarantees control at zero abstention) — consistent with this report's finding that schema compliance is near-100% under enforcement while *value* correctness is not. Under distribution shift, static guarantees fail (60–71% violation rates) and adaptive inference (ACI) restores control in the feasible regime (to 4–21%), with residual violations exactly where the impossibility bound predicts. Implication: verification-based reliability for structured output is **bounded by the base error rate of the task-model pair** — no verifier/retry layer can certify a 10% error target on a task whose base risk is 80%; the honest deployment rule is compute μ first, then choose the bound, score (Self-Consistency strongest, AUROC up to 0.82; Token Margin best for JSON, 0.82), and shift mitigation.

**Fact.** BFCL robustness (Rabinovich & Anaby-Tavor, IBM; arXiv:2504.00914, Table 2): beyond schema validity, function-calling *selection and slot-filling* degrade measurably when the tool context changes. On 200 BFCL-derived cases, AST-evaluated accuracy drops when the toolkit is expanded with semantically related tools (mean 2.7 → 5.6 tools): Llama-3.1-70B 0.965→0.825 (−15%), Llama-3.3-70B 0.945→0.785 (−17%), Qwen2.5-72B 0.975→0.850 (−13%), DeepSeek-V2.5 0.965→0.835 (−14%), Granite3.1-8B 0.945→0.770 (−19%), gpt-4o-mini 0.925→0.765 (−17%), o1-mini 0.905→0.770 (−15%), Claude-3.5-Sonnet 0.915→0.845 (−8%), Claude-3.5-Haiku 0.925→0.765 (−11%). Meaning-preserving query rephrasings cost 1–8% (mostly attributable, per the authors, to strict exact-match evaluation on parameter values — "70–90% of errors" in that condition are parameter-value mismatches, an eval artifact rather than a genuine failure). Failure mix under toolkit growth spans wrong function selected, wrong number of functions, wrong parameter assignment, and parameter hallucination. The same paper notes that adding tools occasionally made models "repair" a previously failed call — the stochastic flip-flop behavior relevant to retry-loop design (a retry with a perturbed context can both fix and break a call).

**Fact (the tool-schema *representation* is a function-calling reliability lever; verified in full text).** TSCG (Sakizli, arXiv:2605.04107) measures the protocol-mismatch hypothesis: production agent frameworks (OpenAI FC, Anthropic Tool Use, MCP) transmit tool schemas as JSON — "a format designed for machine parsing, not for interpretation by language models" — and for small models (4B–14B) this **JSON-schema volume causes a capability cliff: tool-calling accuracy collapses to 0–49% at >15 tools**. On TSCG-Agentic-Bench (~19,000 calls, 12–13 models incl. Phi-4 14B, Mistral 7B, Gemma 3 4B/12B, Llama 3.1 8B, Qwen3 4B/14B, plus frontier GPT-5.2/Claude Sonnet 4/Opus 4.7/GPT-4o), a **deterministic JSON→text schema compiler** (8 operators, ≥51% formal token-compression bound, <1 ms, model-agnostic) restores small models: **Phi-4 14B 0% → 84.4% at 20 tools (90.3% at 50 tools)**, Mistral 7B 35→80.1, Gemma 3 4B 49.9→67 (and 24.3→87.4 at 50); models exceeding 65% usability at 50 tools rise 4/7 → 7/7. Crucially, the mechanism is **format translation, not compression**: a format-vs-compression decomposition shows the R² of the accuracy-predictor drops **0.88 → 0.03 once a plain-text (uncompressed) baseline replaces the JSON baseline** — i.e., almost the entire small-model gain comes from writing the schema as text rather than JSON, and *no* small model shows genuine compression benefit (compression deltas are −7 to −23 pp for Class-1 models). On frontier models TSCG text also beats native function-calling API (mean **+10.9 pp** across Claude S.4/GPT-4o/GPT-5.2, Sc. A/B: GPT-5.2 Sc. A 51.9→81.6, Claude S.4 A 74.0→85.2) while saving 6–50% tokens; external BFCL validation +7.5 pp with 46.8% token savings. Deployment-relevant caveats: per-version operator inversion (operators that help one model version harm the next) and super-additive negative operator interactions mean no universal profile exists — a 4-class taxonomy (Format-dominated / Compression / Neutral / Conservative-only) gives per-model guidance, and aggressive compression *harms* strongly fine-tuned models (Qwen3 14B balanced −5 to −9 pp vs conservative +4.4 pp). Implication for this report: function-calling reliability has a third, previously-quantified-as-separate dimension beyond schema validity and semantics — **the serialization format of the schema itself**, where JSON (the universal production standard) is measurably the *worst* representation for small models and a plain-text render recovers 0→84% without any model change; this complements the PTC (code-schema) and NLT (natural-language) interface findings and the schema-key-wording lever [64].

**Fact (structured hand-off representation preserves decision constraints better than raw or summarized state; verified in full text).** "State Compression in Two-Agent LLM Relays" (Sharma, John, Kumar, Vijayababu; arXiv:2607.18265) measures the representation question at an agent hand-off bottleneck: a Researcher agent audits a fixed closed-world hotel/flight inventory (10×10, exact feasible/optimal labels by exhaustive enumeration) for 50 goal instances, then a Booker agent (both GPT-4.1-nano, temperature 0) picks a hotel–flight pair from only the compressed payload, with the inventory withheld. Four hand-off conditions, exact-McNemar paired tests: **schema-constrained JSON extraction achieves the highest feasibility accuracy 0.96 [0.90,1.00] and eliminates false-NONE (0/50)**, *outperforming the uncompressed control* (0.88, 3 false-NONE) — explicit structure beats raw context volume for a small downstream model; **a 250-word narrative summary, despite the smallest payload (compression ratio 0.333), collapses feasibility to 0.48 [0.34,0.62] with 8/50 false-NONEs** (the summarizer drops exact prices/distances/elimination evidence — semantic goal-alignment 0.676 does not preserve numeric/categorical facts; p<0.001 vs all others); embedding-based pruning matches control (0.88) without a generative compression call. JSON also leads optimal-match accuracy (0.74) and lowest feasible optimality gap ($15.12). Implication for this report: it is the relay/agent-state complement to the tool-schema-representation finding [66] — **the serialization format of inter-agent state is a measured reliability lever: normalized, auditable structured JSON preserves constraint-critical evidence that brevity-oriented compression destroys, and structured evidence can beat raw long context for small downstream models** (consistent with the §6 harness-is-the-reliability pattern, and the "wrong-valid" theme: preserving the *right* facts matters more than payload size).

**Fact (multi-hop relay format effects are tier-dependent — structure is faithful, not corrective; verified in full text).** "Faithful, Not Corrective: Message-Format Effects in Multi-Hop Agent Relays" (Shawn, arXiv:2607.09678) resolves the interface-format debate (§7: NLT's anti-structure [31] vs PTC/relay pro-structure [57],[74]) in the regime neither side measured: multi-hop copy-fidelity. Controlled testbed: 12 programmatic atomic facts re-encoded hop-by-hop over 6 hops in 5 formats (free NL, precision-instructed NL, JSON, triples, key-value), graded by a fixed strong model against programmatic ground truth, across two relay tiers (strong DeepSeek-v4-flash; weak Qwen2.5-1.5B 4-bit). Results: (1) **at the strong tier the "telephone-game" collapse does not occur — every format retains QA recall ≥0.973 after 6 hops** under faithful-relay instructions (the loss concentrates in the *first encoding step*, not in transit; free NL shows only a small chronic drift slope −0.295); (2) **format effects are tier-dependent: under the weak relay the across-format dispersion of hop-6 recall grows 8.7× (2.3→20.5 points range)** — every format decays, with two opposing mechanisms: an *encoding toll* paid by rigid formats (hop-1 recall Kv 0.765 / Json 0.800 vs Constr 0.962) versus *drift resistance specific to the fixed-key JSON schema* (Json loses only 4.7 raw points over hops 1–6, retains 0.94 of its hop-1-correct facts vs 0.74–0.85 for all others — survivor-controlled — flipping its rank from 4th at hop 1 to 2nd at hop 6); (3) **causal injection adjudicates the folklore**: once a wrong value is present, it persists to the final hop in **83–100% of chains in every format** (direction-blind — the true value survives at the same rate), with no detectable collateral cascade (per-format damage bounds 0–13 points) — so **"structure is a faithful, error-localizing channel, not an error-correcting code"**: it preserves whatever it is given and keeps damage local, but does not repair. Deployment guidance: choose the format for the *weakest relay* in the pipeline (frontier choice is nearly free); precision-instructed NL matches schema fidelity at 26% fewer message tokens (and ~63% fewer billed tokens, since strong relays spend ~4× hidden reasoning tokens emitting JSON). Implication: this unifies §7 — the NLT anti-structure result measures the *encoding* mechanism, the PTC/pro-structure results measure cost at saturated fidelity, and only the relay regime exposes the *drift-side* mechanism that rewards fixed-key structured schemas for weak models on long chains.

**Fact (evaluation scale/design).** The BFCL V3 multi-turn & multi-step dataset (Mao, Yan, Ji et al., UC Berkeley; https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html) defines the reference design for measuring multi-step function calling: 800 human-labeled multi-turn cases (200 Base + 4×200 augmented: missing-parameter, missing-function, long-context, composite), state-based + response-based (subset-matched) evaluation where a call is correct only if it passes both in all turns; a turn is force-terminated and marked wrong after 20 steps (the "stuck in a loop" guard). Notably, the design *rewards* error recovery: a trajectory that fails then retries with corrected parameters (e.g., resolving a symbol, then retrying the call) passes state-based evaluation — so "retry after error feedback" is treated as correct behavior, not as a failure. The full V3 leaderboard scale is 4,441 entries (Non-Live 1,390; Live 2,251; Multi-Turn 800; hallucination-measurement 240).

**Fact (agent-level reliability).** τ-bench (Yao, Shinn, Razavi, Narasimhan; arXiv:2406.12045) measures end-state reliability of tool-agents against domain policies (retail + airline) and introduces pass^k for reliability over multiple trials. Abstract headline: "even state-of-the-art function calling agents (like gpt-4o) succeed on <50% of the tasks, and are quite inconsistent (pass^8 <25% in retail)" — i.e., the best function-calling agent fails more than half of tasks, and in retail 8 independent attempts still fail on >75% of tasks. **Verified pass^k curves from the official repo leaderboard** (sierra-research/tau-bench; note: the repo flags these airline/retail tasks as the outdated first version, superseded by τ³-bench): airline tool-calling — claude-3-5-sonnet-20241022 Pass^1/2/3/4 = 0.460/0.326/0.263/0.225; gpt-4o = 0.420/0.273/0.220/0.200; retail — claude-3-5-sonnet Pass^1..4 = 0.692/0.576/0.509/0.462; gpt-4o = 0.604/0.491/0.430/0.383. The monotone pass^1→pass^4 decay (e.g., gpt-4o airline 0.42→0.20) quantifies the retry-reliability problem: more independent attempts buy proportionally less reliability, and the abstract's pass^8 <25% (retail) is consistent with the observed curve — retry-via-resampling is largely exhausted by k≈4–8. Successor benchmarks confirm the reliability gap persists in harder settings: τ²-bench (Barres et al., arXiv:2506.07982) adds a dual-control Telecom domain (both agent *and user* act in a shared environment) and reports "significant performance drops when agents shift from no-user to dual-control"; the current τ³-bench adds a banking domain and a voice modality (repo note).

**Fact (live BFCL V4 numbers, 2025-12-16 archive).** The BFCL-Result archive's `data_overall.csv` (HuanzhiMao/BFCL-Result, score snapshot 2025-12-16; evaluation checkpoint commit f7cf735) provides current per-model function-calling reliability. Overall accuracy (unweighted average across non-live AST, live, multi-turn, web-search, memory, relevance/irrelevance): top model **Claude-Opus-4-5-20251101 (FC) 77.47%** (cost $86.55 for the full eval, mean latency 4.38 s), then Claude-Sonnet-4-5 (FC) 73.24%, Gemini-3-Pro-Preview (Prompt) 72.51%, GLM-4.6 (FC thinking) 72.38%, Grok-4-1-fast (FC) 69.57%. Even the best current model therefore **fails ~23% of function-calling tasks**. The hardest sub-category is multi-turn: best is Opus-4-5 68.38%, but GPT-5.2 (FC) 28.12%, o4-mini (Prompt) 16.62%, GPT-4.1 (FC) 38.88%, and most open models 0–50%. Irrelevance detection (correctly refusing to call a function) is a persistent weak spot: Opus-4-5 84.72%, Sonnet-4-5 86.61%, but several strong models <40%. Format-sensitivity (prompt-mode models, max accuracy delta across format changes) ranges from 8.5 (Gemini-3-Pro, o3) to 23.5 (GPT-4.1) to 81.5 (Phi-4), i.e., prompt-based function calling can lose up to ~80 points when the output format shifts — a strong argument for native FC mode / structured outputs for prompt-based models. Full-evaluation cost spans $1–355 across models (Grok-4-0709 $355.17; Gemini-3-Pro-Preview $298.47; Qwen3-32B $153; open 1–6B models $0.5–6).  **Fact (counterpoint to structured tool calling; verified in full text).** The Natural Language Tools (NLT) replication study (Somma, Plante, Premji; arXiv:2607.03953; replicating Johnson et al. 2025) measured, across **14 models and 8,560 trials**, that letting the model emit tool calls as free-form natural language beat structured tool calling: overall accuracy 62.3% vs 47.4% (**+14.9 pp for NLT**), **93% fewer critical errors (51 vs 755)**, and **25.2% lower token usage** (3.38M vs 4.52M tokens). Per-model detail: Claude-Sonnet-4 +43.1 pp (61.9 vs 18.8 — a frontier model with a weak structured implementation), Mistral-7B +39.4 pp (39.4 vs 0.0 — **complete structured collapse, 320 errors**), DeepSeek-R1 +24.0 pp (reasoning models conflict with structured formats), Qwen3-VL +33.8 pp after correction (307/320 structured trials errored); **the advantage reverses only for structured-optimized frontier models — Gemini-2.5-Pro −33.7 pp (48.3 vs 82.1), GPT-OSS-120B −6.4 pp, Kimi-K2 −0.6 pp** — while GPT-5 is near-parity (+1.6 pp). The study's survivorship-bias correction (any condition with ≥70/80 errors → 0% accuracy) is methodologically important: raw structured accuracy of 51.9% is inflated by near-total-failure conditions. The authors' retry-cost interpretation: "a structured failure triggers retries, fallback routing, and coordination overhead, while NLT avoids most of that cost at the source." This is the strongest measured caveat to "always use schema enforcement" for tool calling: enforcement guarantees parseability, but on this benchmark the enforced structured path had 15× more errors and higher retry-triggering than free-text output — except for models specifically fine-tuned for structured tool calling.

**Fact (programmatic-vs-JSON tool calling; verified in full text).** "The Bitter Lesson of Tool Calling" (Patel, Sen, Lumer, Subbiah; PwC, arXiv:2608.06370) directly measures the *interface* dimension that NLT opens: replacing native JSON tool calls with **programmatic tool calling (PTC — the model writes a typed-Python-stub script executed in a subprocess, one agent turn)** across **14 models (Nov 2024–Jul 2026, temperature 0, deterministic scorer) on a 309-entry BFCL v4 subset**. Main result: PTC **matches or exceeds JSON tool calling in 11/14 models**; the GPT-5.6 family gains the most (**+10.6 pp absolute over its own JSON baseline**, GPT-5.6-Sol 72.2→82.8, Terra 73.5→84.1), while **three older OpenAI models (GPT-4o, GPT-4.1, GPT-5.4-mini) fall 19.7–26.9 pp below their JSON baseline** under PTC — a single mechanical failure: they emit literal `\n` escape sequences instead of real newlines in multiline scripts, so the subprocess syntax-errors (a capability gap, not a prompt issue: GPT-5-nano produces correct multiline code while GPT-5.4-mini does not). Overall macro-average is near-parity (JSON 78.6 vs PTC 77.0), and the aggregate hides the per-category split: **PTC loses 14.1 pp on average in parallel categories but gains 10.0 pp in live_multiple** (multi-call scripts). Three ablations give the mechanism-level numbers: (1) **chaining (n=52, lengths 2–20): PTC's advantage scales with chain length, reaching +18.8 pp at length ≥12** (Claude Sonnet 5 80.8→96.2, Opus 4.8 80.8→94.2) because JSON pays an extra inference turn per link while PTC computes intermediates in-script; GPT-4.1 collapses 98.1→40.4 via the same `\n` bug. (2) **parallelism (n=32, fan-out 7–48): PTC matches/exceeds baseline in 13/14 (GPT-5 71.9→96.9)**; JSON tool calling drops calls outright above a model-specific fan-out threshold — probing Claude Sonnet 5 at N∈{60,70,72,75,100}, enumeration is 100% at N≤70, drops to 75% at N=72, and **0% at N=100, while PTC holds 100% at N=100** — a hard structural limit of the native JSON paradigm (though model-specific: GPT-5.6-Sol holds 100% JSON enumeration through N=100). (3) **context rot (n=31/condition, flood = 128 decoy schemas): JSON degrades −2.3 pp average under flooding; PTC is stable or improves (+5.5 pp)**, vs −32.0 pp for a filesystem-based reference. Cost/latency: token cost crosses over at fan-out N≈26 (at N=30 JSON 3,559 vs PTC 3,380 tokens; at N=48 5,097 vs 3,535), though PTC carries a fixed system-prompt overhead (1.5× input tokens on chaining); PTC runs chaining in ~half the wall-clock time for 13/14 models (ratio 0.32–0.96; GPT-5 exception at 2.8× due to extended reasoning). Limits the authors state: echo-return stubs measure *argument serialization*, not end-to-end tool-use correctness; ablation n is small (31–52) so only cross-model aggregates are reliable; and BFCL v4's LLM-judge mode has a documented ~20% evaluator-human misalignment (their deterministic scorer sidesteps it). Implication for this report: **the JSON format itself is not the only (or best) structured interface — PTC matches JSON accuracy for all current-generation models and removes a structural fan-out ceiling that JSON tool calling hits at N≈70–100; the interface decision is a measurable reliability lever separate from schema enforcement.**

### 4. Retries

**Fact (agents under tool-environment unreliability — recovery is the bottleneck, not volume; abstract-level, no HTML).** ToolBench-X (Tian, Shi, Zhou, Zhao; arXiv:2606.25819) is a benchmark that moves beyond function-call accuracy to *task completion under recoverable tool-environment hazards*: executable multi-step tasks (sequential/parallel/mixed workflows) with deterministic tools and canonical answers, from which **five structured hazard types are injected — Specification Drift, Invocation Error, Execution Failure, Output Drift, Cross-source Conflict** — each instance deliberately left solvable via at least one valid recovery path (retrying, fallback, verification, cross-checking). Findings: **agents that perform well with reliable tools often fail under recoverable hazards** (a substantial reliability gap); **failures are driven less by tool-use volume or inference budget than by limited hazard diagnosis and ineffective recovery**; **targeted recovery hints recover many failed tasks, while test-time scaling yields more limited gains** — i.e., telling the agent *what* is wrong and *how* to recover beats simply giving it more attempts/tokens, the same conclusion as §5's feedback-content results (VeriHarness, AgentTether) applied to the retry regime. Implication for this report: the §4 retry-pressure arithmetic (1/compliance draws) measures *what* to retry but not *how well agents retry*; ToolBench-X measures the latter — that recovery quality, not retry quantity, is the binding constraint when the tool environment itself misbehaves.

**Fact (refining beats resampling at fixed test-time compute — with a measured diversity-saturation mechanism; verified in full text).** "Refining Over Resampling" (Bilal, Mohsin, Umer, Trigg, Subhan, Ali, Hougen; Oklahoma/Stanford/UPF/Air Univ., arXiv:2608.05643) quantifies why "just retry by resampling" (§4's pass^k arithmetic) plateaus: **sampling diversity saturates** — on AIME-24 the number of unique semantic reasoning clusters grows only from 1.2 (N=2) to 2.5 (N=32), so additional rollouts repeat dominant patterns; and each i.i.d. rollout shares the same per-trace hallucination mechanism (an analytical latent-accuracy bound shows first-pass accuracy systematically underestimates latent accuracy). The remedy is **breadth–depth refinement** (verifier-free, training-free): sample N=8 rollouts, run D=4 rounds of generator→self-critique→self-correction on each, then majority-vote — no reward model, no learned stop policy. Across 4 models × 5 math benchmarks (AIME24/25, AMC, OlympiadBench, MATH500): **consistently beats greedy, Maj@N, verifier-based best-of-N (RM@8 with Qwen2.5-Math-RM-32B), beam search, and lookahead** — e.g., **Qwen2.5-1.5B MATH500 29.6 (RM@8) → 58.0%; AMC 25.0 → 32.5%; average accuracy 13.21→25.67 (η=17.1 compute-normalized gain over Maj@8)**; Qwen2.5-Math-7B OlyBench 41.0→47.2, AIME25 13.33→16.67; Ministral-8B AMC 30.0→42.5. The explicit self-critic stage is necessary (weak-model gains largely from critique: Qwen2.5-1.5B AMC 27.5→32.5, AIME25 0.0→6.67), and refinement preserves breadth through depth 4 (rollout diversity 0.80–0.97). Implication for §4/§5: **this is the measured mechanism for why retry-by-resampling is exhausted at k≈4–8 (τ-bench) while refinement keeps adding**: the retry budget should be split into breadth (independent starts) + depth (self-correction before aggregation), and the deterministic-verifier-independent majority-vote aggregation is what makes noisy self-corrections net-positive — the aggregation is the external stabilizer that raw self-correction (§5's Huang et al. degradation) lacks.

**Fact + estimate.** JSONSchemaBench defines retry pressure precisely: when compliance < 1, surviving failures need post-processing or retry. On the benchmark's numbers, expected draws to first compliant output = 1/compliance: LM-only on GitHub-Hard ≈ 7.7 (from 0.13) — **estimate**, derived from their reported compliance; Outlines on JSONSchemaStore ≈ 4.2 (from 0.24); Guidance on GitHub-Hard ≈ 1.45 (from 0.69). The provider "no retries" claim holds only where declared coverage is non-zero; on GitHub-Hard, OpenAI's declared coverage of 0.09 means 91% of schemas would be rejected/unsupported rather than retried against.

**Fact (validation-framework note).** The two retry-relevant failure classes are measured separately and can diverge sharply. In the lm-evaluation-harness integration of JSONSchemaBench (EleutherAI/lm-evaluation-harness, `lm_eval/tasks/jsonschema_bench/README.md`), `json_validity` (syntax, Python `json` package) and `schema_compliance` (Python `jsonschema` package) are independent binary metrics. The README's own worked example for Llama-3.2-1B-Instruct on `jsonschema_bench_medium`: **json_validity 1.0, schema_compliance 0.2** — i.e., 100% parseable JSON but 80% of outputs violate the schema, so a syntax-level "retry on parse error" loop would not trigger while a schema-validator retry loop would fire on 80% of draws. This is exactly the JSON-mode-vs-Structured-Outputs gap (§1) made measurable. The harness also defines an independent leaderboard (`epfl-dlab/jsonschemabench-leaderboard`) for LM-only native structured-output ability — the frontier-model compliance numbers that JSONSchemaBench itself did not produce are now publicly measurable on the github_easy/medium/hard splits (2K/3K/10K context windows).

**Fact (test-time-compute economics of retries/resampling).** Two primary sources quantify what "just retry by resampling" costs and buys. (1) Self-Consistency (Wang et al., ICLR 2023; arXiv:2203.11171; **verified in full text, Tables 2–3**): sampling N diverse paths + majority vote (a retry-with-aggregation pattern) yields large accuracy gains over a single greedy pass — PaLM-540B GSM8K 56.5→74.4 (+17.9), GPT-3-code-davinci-002 GSM8K 60.1→78.0 (+17.9), SVAMP +11.0, AQuA +12.2, StrategyQA +6.4, ARC-c +3.9. Two findings matter for retry-loop design: (a) self-consistency **beats sample-and-rank, beam search, and prompt-ensembles at the same sample count** (Table 6–7), so aggregation beats selection when retrying; (b) answer consistency across the sampled paths **correlates with accuracy**, giving a cheap "know-when-it-doesn't-know" signal — usable to stop a retry loop early when outputs already agree, or to escalate when they diverge. (2) Scaling LLM Test-Time Compute (Snell, Lee, Xu, Kumar; arXiv:2408.03314; **verified in full text**, §5.3/Fig 4): a compute-optimal, per-prompt (difficulty-binned) allocation of best-of-N / beam search against a process reward model "can nearly outperform best-of-N using up to **4× less test-time compute (e.g. 16 versus 64 generations)**"; and in a FLOPs-matched evaluation test-time compute lets a smaller base model "outperform a 14x larger model" on prompts where it has non-trivial base accuracy. Two caveats from the paper itself, relevant to retry/verify loops: verifier search **over-optimizes on easy questions** (beam search degrades as the generation budget grows because it amplifies spurious verifier features), while best-of-N is better at high budgets / easy questions and search better at low budgets / hard questions; and **difficulty estimated from the verifier's own scores (model-predicted) nearly matches oracle difficulty**, so adaptive allocation is deployable without ground truth. Interpretation for JSON retry loops: uniform retries are up to 4× more expensive than difficulty-adaptive retry budgets — matching the per-prompt difficulty sensitivity that SchemaBench's per-subtask numbers (84%/62%/37%) show for JSON itself.

**Fact (rate-limit / failover economics; verified in full text).** ContinuityBench (Pandey & Singh, Metriqual; arXiv:2607.15899) is the one located study quantifying retry backoff behavior at the infrastructure layer. Controlled design: 150 synthetic multi-turn conversations (7–11 turns, mean 9.1) with embedded factual anchors, deterministic fault injection (TIMEOUT / 5xx API_ERROR / 429 RATE_LIMIT) at the probe turn, GPT-4o LLM-as-judge, and baseline-vs-treatment differing in exactly one line (whether the failover payload forwards the full `messages[]` or only the last user message). Across N=750 failover events, the stateful History-Forwarding proxy preserved context in **99.20% (95% Wilson CI 98.27–99.63%)** vs near-0% for stateless failover. Two systems failure modes documented under C=100 concurrency: (a) a race condition where parallel failovers corrupt shared proxy state, and (b) a **retry-storm (thundering-herd) vulnerability** where naive fixed-interval retries against a rate-limited fallback self-sustain and "permanently lock out the fallback endpoint"; the authors state exponential backoff with jitter is "necessary and sufficient" to resolve it — the measured justification for the standard "retry with jittered exponential backoff" cost control. (Single-team system study, not independently replicated; production latency claims are a separate Rust data-plane contribution not evaluated in the benchmark.)

**Fact (dollar/token cost of retries — four independent measurements).** (1) Token Budgets (Khan, arXiv:2606.04056) catalogs **63 confirmed production budget-overrun incidents across 21 orchestration frameworks (2023–2026)**, each with a quoted GitHub issue, noting "a single retry loop can spend thousands of dollars before an operator notices"; its central failure mode is the delegation-fanout race where retries multiply spend. (2) Runtime-Structured Task Decomposition (Asthana et al., arXiv:2605.15425) measured retry *token* cost in agentic coding: static task decomposition forced full-workflow reruns on failure (root-cause analysis: 1,632±145 tokens vs 904±17 monolithic), while rerunning only the failed subtask cut retry cost to 436±132 tokens — **up to 51.7% lower retry cost than monolithic and 73.2% lower than static decomposition**. (3) Communication-Theoretic framework (Omidvar & Akhlaghi, arXiv:2605.09121) frames retry/voting/self-consistency as one tunable reliability layer; measured on 69 hard tasks across 6 channel configs, a cost-aware router achieves **~56% lower normalized cost than the strongest fixed technique at matched quality** (and +7% quality at matched cost, +26% over single-shot), with a contractivity criterion showing generator-critic refinement turns contractive→divergent between 3B and 14B models. (4) Agentic energy accounting (Panigrahy et al., arXiv:2605.22883): agentic workflows consume **4.33× mean energy per successful goal vs linear baselines (888.1 J vs 205.3 J)**, driven by orchestration/retry structure rather than inference compute. Together: retry cost is not a fixed multiplier of base inference — it depends on where in the workflow you retry (subtask vs full), whether you aggregate, and whether you route per-prompt; a "retry loop" can be a $thousands incident or a ~50% cost reduction depending on structure.

**Fact (retry consistency and selective-repair economics).** Two more measured mechanisms. (1) STED/Consistency Scoring (Wang et al., arXiv:2512.23712; **verified in full text**): measures *consistency across repeated generations* — the property that determines whether retries converge. On 75 samples × 10 generations per temperature (0.1–0.9) across six LLMs: Claude-3.7-Sonnet shows near-perfect **structural consistency 0.999±0.037 even at T=0.9** with only **19% degradation from T=0.1→0.9** (mean consistency 0.658±0.240); Claude-3-5-Sonnet-V2 structural 0.946±0.227 but semantic 0.459±0.318; **Claude-3.5-Haiku is the most temperature-fragile (46% decline)**; Nova-Pro is structurally moderate (0.728±0.430) with erratic temperature response (peaks at T=0.5). Deployment rule from the paper: T=0.1–0.3 maximizes consistency, T≥0.7 causes >30% semantic drop. STED itself scores 0.86–0.90 similarity for semantic-equivalent JSON and 0.0 for structural breaks (with 5.2% degradation for semantic vs 1.9% for expression changes). Implication for retries: if a model is temperature-fragile (Haiku-class), retries sample from a moving target and expected-draws math understates the true budget; the structural-vs-semantic gap (0.999 vs 0.658 for Sonnet) means format stays stable while content drifts — retry-on-schema alone won't converge content. (2) StepCache (Nouri, arXiv:2603.28795) shows the cheapest "repair" is selective patching of the failed region rather than full regeneration: step-level reuse + lightweight verification + patch-only regeneration cut mean latency 2.13 s→0.67 s and tokens 36.1k→27.3k, and raised end-to-end correctness 72.5%→100% under task-specific checks, with 79.7% of requests on a reuse-only fast path, 5.4% requiring patching, 14.9% skip-reuse. This is the serving-layer embodiment of the "repair only the failed subtask" result (Asthana et al.) applied to JSON structured outputs.

**Fact (patch-based repair of JSON instead of full regeneration — with a measured *array-indexing* failure mode; verified in full text).** "JSON Whisperer" (Duanis, Greenstein-Messica, Habba; Lightricks/Hebrew Univ., arXiv:2510.04717) is the editing-side counterpart to StepCache and Asthana et al.: instead of regenerating an entire JSON document for a small edit, have the LLM emit an **RFC 6902 JSON Patch** expressing only the modifications (add/remove/replace with JSON Pointers). The paper documents two *measured* failure modes that make naive patch generation unreliable — (1) **missing related updates**: "the fragmented nature of patch generation causes models to miss necessary updates" (editing a character's attributes across scenes updates some occurrences but overlooks others — a failure full regeneration naturally avoids), and (2) **array index arithmetic**: "even state-of-the-art models frequently miscalculate these shifts or conflate zero-based and one-based indexing" (removing an element shifts subsequent indices; e.g., removing "Bob" at index 2 then addressing the old index 3). The fix **EASE (Explicitly Addressed Sequence Encoding)** replaces positional arrays with dictionaries of stable two-letter keys plus a `list_display_order` string, making element identity and operation execution order-invariant — "eliminating index arithmetic complexities." Measured on a synthetic film-scene JSON editing dataset (~400 examples, 4 complexity classes — simple/creative/complex/list-manipulation; GPT-4o-mini and Claude Sonnet, zero-shot vs DSPy-optimized synthetic few-shot): **patch generation with EASE matches full-regeneration edit quality within 5% while cutting token usage 31%** (Claude in/out 918/918→1,890/529 full→diff — note the diff *input* is larger, output 42% smaller; 4o-mini 677/677→1,500/464), and the economics table shows **42.3% lower latency (11.62→6.70 s Claude) and 42.5% lower cost ($13.8→$7.94 per 1K requests)**; the gains concentrate on complex instructions and list manipulations, and few-shot (synthetic examples) is what makes patch generation work at all (zero-shot much weaker — "synthetic few-shot examples provide substantial performance improvements"). The paper's own caveat: synthetic-only training/eval data, and the in-context few-shot approach raises *input* tokens as JSON grows (could offset savings / hit context limits — fine-tuning would remove the few-shot need). Implication for §4/§6: this is the third independent measurement that **minimal-diff repair beats full regeneration on JSON** (with StepCache and Asthana et al.), and it isolates a repair-specific failure class — structured *edits* (index arithmetic, cross-field consistency) have their own failure modes distinct from structured *generation*, which is why regeneration-free repair needs schema-aware encoding rather than a plain retry.

**Fact (cost of schema-heavy prompts under caching; verified in full text).** CAPC (Song, PayPal; arXiv:2607.15516) measures the real caching economics of long-schema workloads on Anthropic Sonnet 4.6: prompt caching is not the ideal rho=1.0 — the cache is **two-tier with a sharp threshold near 3,500 tokens** (below: hit rate plateaus at 0.833 exactly, σ=0; above: ρ=1.0 from the first call); billing reconciles to <1% at $3.00/MTok in, $3.75/MTok cache-write, $0.30/MTok cache-read. Derived crossover: at compression ratio r≥6, cache-only **never beats** query-aware compression (ρ_cross(6)=0.942 > empirical plateau ~0.89), reversing conventional wisdom. CAPC (query-agnostic compression + explicit cache_control + tier-preserving ratio bound floor(|D|/3,500)) is cheapest in 16/16 configs: mean savings 49% over cache-only, 64% over query-aware, 90% over vanilla, quality within 0.05. Production: enterprise tool-using assistant with a **94k-token tools= schema prefix → 51.7% cost reduction at r=3**; τ-bench retail: CAPC cheapest with reward identical to vanilla (36/50, p=1.00) while query-aware compression was +40.1% more expensive. Over-compression failure mode is quantified: on a 12,191-token doc, r=3 keeps the compressed prefix in the persistent tier (4,067 tok, $0.0057/query) but r=4 pushes it into the hot tier (3,119 tok) and per-query cost *rebounds 77%* to $0.0101. Implication: for schema-heavy structured-output workloads, the schema prefix dominates per-call cost, and naive per-query prompt variants silently invalidate the cache — the retry-cost-structure theme extended to prompt engineering.

### 5. Repair patterns (self-correction / self-repair loops)

**Fact.** Self-Refine (Madaan et al., arXiv:2303.17651; verified in full text, Table 1): a single LLM acting as generator + critic + refiner, iteratively, improved performance "~20% absolute on average" across 7 tasks (GPT-3.5/ChatGPT/GPT-4) vs one-shot generation. The task-level breakdown is highly uneven and the paper's own analysis qualifies the headline: **math reasoning gains are essentially zero** (GSM8K: GPT-3.5 64.1→64.1, ChatGPT 74.8→75.0, GPT-4 92.9→93.1) because "the model cannot accurately identify whether there is any error" — ChatGPT's feedback is "everything looks good" on 94% of instances — and gains only appear (5%+) when an *external* source flags incorrectness. In contrast, preference/constrained tasks gain 20–49 pp (Dialogue Response GPT-4: 25.4→74.6; Constrained Generation: 15.0→45.0). Iteration curves show diminishing returns (Constrained Generation 29.0→40.3→46.7→49.7 over iterations); feedback *quality* matters (specific feedback 43.2 vs generic 31.2 vs none 0 on Sentiment Reversal); and of self-refine failures, 61% come from feedback suggesting an inappropriate fix, 33% from wrong error location, only 6% from the refiner misapplying good feedback. This is the strongest positive result for LLM-internal repair — and its near-zero math numbers align exactly with the intrinsic self-correction failure measured in Huang et al. below: repair succeeds where the model can verify, fails where it cannot.

**Fact (multi-agent pipelines fail on 7B models specifically via JSON communication; verified in full text).** "Two Calls Beat Five Agents" (Prajapati & Mohite, arXiv:2607.26922) measures how *structured communication* degrades in small-model pipelines: Parishad (five-role pipeline: Refiner→Planner→Worker→Checker→Judge) run on Qwen2.5-7B-Instruct (GGUF Q4_K_M, llama.cpp). **With JSON inter-role communication the pipeline drops GSM8K accuracy from 75.0% (direct) to 45.0% and HumanEval from 96.3% to 56.0%** — a 7B model produces malformed JSON 30–40% of the time under a complex system prompt; the engine's parse-failure fallback (pass raw text downstream) cascades: "by the third or fourth role, the chain has strayed far from its starting point" (error accumulation). **Switching only the communication format to plain text — no architecture/model change — restores GSM8K to 82.0% and HumanEval to 81.7%** (+37 points), a direct 7B-scale confirmation of the schema-representation lever [66]/PromptPort [82]/Palabrita [70]. On repair: **two-call self-refinement beats the pipeline on math (86.2% at 7.4× fewer tokens) but the same ungated implementation destroys HumanEval (Call-1 95.1% → 66.5%, fixing 4 and breaking 51)** — the forced-rewrite Call-2 prompt rewrites working code, and at 95.1% initial accuracy there are only 8 fixable problems but 156 chances to break working ones; a **task-aware gate (skip Call-2 on complete code blocks; conservative "respond CORRECT if no bug") restores 95.1%** (skips 163/164). Ablation isolates the mechanism: no-gate + non-coercive prompt = 96.3% (better than gated); gate + force-rewrite = 94.5% — the forced-rewrite instruction, not the gate, caused the regression. Authors' deployment rule: **start from direct prompts; add self-refinement only when direct accuracy <85%; never use structured JSON communication in multi-step pipelines for sub-10B models.** Implication for this report: this is the *agent-orchestration* face of the format tax — for small models, JSON as an inter-agent contract is measurably worse than plain text (a 37-pp swing with identical reasoning), and it quantifies the §5 gating rule with a clean boundary (near-ceiling tasks: refinement breaks more than it fixes).

**Fact.** "LLMs Cannot Self-Correct Reasoning Yet" (Huang et al., ICLR 2024; arXiv:2310.01798), Tables 2–4 — *intrinsic* self-correction (no external signal) consistently *degraded* accuracy while multiplying cost (1 → 3 → 5 calls):
- GPT-3.5: GSM8K 75.9 → 75.1 → 74.7; CommonSenseQA 75.8 → 38.1 → 41.8; HotpotQA 26.0 → 25.0 → 25.0.
- GPT-4: GSM8K 95.5 → 91.5 → 89.0; CommonSenseQA 82.0 → 79.5 → 80.0; HotpotQA 49.0 → 49.0 → 43.0.
- Llama-2: GSM8K 62.0 → 43.5 → 36.5.
- With oracle labels (external signal), the same loop *gains*: GPT-3.5 GSM8K 75.9 → 84.3; GPT-4 95.5 → 97.5.
- Multi-agent debate at equal inference cost is worse than self-consistency: debate 9 responses 83.0 vs self-consistency 9 responses 88.2 on GSM8K.
- Prompt-design artifact: on CommonGen-Hard, Self-Refine's apparent gain (44.0 → 67.0) disappears when the initial prompt is strong: plain prompting with a proper instruction reaches 81.8 and then applying self-correction *drops* it to 75.1.

**Fact.** "Is Self-Repair a Silver Bullet for Code Generation?" (Olausson et al., ICLR 2024; arXiv:2306.09896) — cost-aware repair for code:
- Repair gains are modest at equal budget and sometimes negative: GPT-3.5 on HumanEval ≤ +3%; Code Llama on HumanEval ≤ +10%; GPT-4 on APPS ≤ +8% over i.i.d. sampling at the same sample budget.
- Sample-budget allocation matters: on APPS, GPT-4 with 10 diverse initial samples + 1 repair each (≤20 samples) = 1.05× pass@20; but 2 initial + 10 repairs each (≤22 samples) = 0.97× vs pass@22 — over-investing in repair *loses* to plain resampling.
- Repair is bottlenecked by feedback quality: replacing GPT-4's own feedback with a human programmer's feedback raised the fraction of repaired programs that pass from **33.3% to 52.6% (1.58×)**; GPT-4 feedback was judged inaccurate in 32/80 cases vs 7/80 for humans (Table 1, §4.3).

**Fact (counterpoint: external-signal repair that works; abstract-level).** Self-Debugging (Chen et al., arXiv:2304.05128) shows the *same* loop structure (generate → execute → feedback → repair) is effective when the feedback is a deterministic execution signal (rubber-duck debugging: the model inspects its own execution results and explains its code). Measured (per the paper's abstract; full text was not verifiable — no HTML version exists, ar5iv conversion errors out): on Spider (no unit tests; self-explanation) +2–3% overall and **+9% on the hardest problem level**; on TransCoder and MBPP (unit tests available) **up to +12%**; and by reusing failed predictions with feedback, Self-Debugging "can match or outperform baseline models that generate more than 10x candidate programs" (~10× sample-efficiency). This is the one repair pattern with strong, cost-honest numbers, and it matches the condition that separates productive from counterproductive repair across all sources above: a *reliable external verifier* (execution/tests here; oracle labels in Huang et al.; a stronger or human feedback model in Olausson et al.). For structured JSON, the analogous reliable verifier is a JSON-Schema validator + the inverse-compliance retry loop in §4.

**Fact (offline/training-based repair).** Schema Reinforcement Learning (SRL; Lu et al., arXiv:2502.18878) is the "repair" variant that moves the validator *into training*: RL with a fine-grained schema-validator reward lifts native valid-JSON generation without any decoding-time constraint — Llama-3.1-8B 36.45% → **79.67%** (SRL) vs 60.59% (SFT); Llama-3.2-3B 28.51% → **72.50%** (SRL) vs 56.48% (SFT); the paper claims "up to 16% improvement in valid complex JSON generation rates compared to supervised all baselines." It generalizes to tool calling: BFCL-Live overall for Llama-3.1-8B rises 24.08% → 70.10% with SRL (vs 52.69% SFT). Ablation (Llama-3.2-3B complex subset): outcome-reward RL 28.51→31.15%; + Thought-of-Structure reasoning →44.89%; + fine-grained schema validator →35.59%. Relevance: this is the only measured route that improves the *native* rate (what retries resample from) — everything in §5 above operates on the sampling distribution; SRL changes it. Trade-off noted by the authors: SFT without collected JSON data degrades reasoning (generalization), whereas SRL preserves it.

**Fact (training-side format collapse is a *sharp threshold*, not a gradual knob; verified in full text).** "The Extrapolation Cliff in On-Policy Distillation of Near-Deterministic Structured Outputs" (Li, Jiang, Wang, Zhang, Yuen; NTU, arXiv:2605.08737) is the training-side complement to SRL: on-policy distillation with reward extrapolation (λ>1) — used to lift a small student past its teacher — **silently collapses the structured-output contract above a closed-form threshold λ*(p,b,c)** (teacher modal probability, warm-start mass, IS-clip strength). Measured on Amazon Fashion K=8 listwise-JSON (Qwen3 1.7B→4B, N=212, strict parser): **parse rate 94.8% at λ=1.15 → 65.1% at λ=1.25 → 8.5% at λ=1.50** — the cliff localizes inside the predicted [1.18,1.28] bracket (5-seed CI [1.204,1.228]; cross-clip c=1.5 prediction λ*=1.070 vs observed midpoint 1.069, below grid resolution), and **NDCG@1 on *parsed* outputs is statistically flat across the sweep (p=0.61)** — "the λ effect is concentrated in format-adherence, not ranking quality." Operating just below λ*, the same training lifts a 1.7B student to **94.8% parse / useful=0.86, matching an 8B-SFT baseline at one-fifth the parameters and ~5× lower seed variance**; decoder constraints add only +0.009 parse on top of unconstrained ListOPD's 0.943 (constrained-SFT parse 0.325→0.783; all 46 constrained-SFT failures are duplicate review_ids, a strict subset of the 138 unconstrained failures). Implication for §2/§5: **the "training-side repair" (RL/SFT toward schema adherence) has its own failure mode with a quantitative boundary** — beyond a computable λ*, training moves the model from format-preserving to format-collapsing, and a parse-only evaluation (the common one) can hide this because semantic quality stays flat while the contract breaks; training-side and decoder-side fixes are complementary (SRL raises the native rate, constrained decoding enforces it, and this paper bounds the RL hyperparameter that can undo both).

**Fact (diagnosis-guided runtime repair of agent runs; verified in full text).** AgentTether (Zhao et al., Microsoft Research; arXiv:2607.06273) is the clearest measured comparison of repair *patterns* for failed multi-step tool-use runs: it explicitly contrasts "blind retry [which] adds no diagnosis," "outcome feedback [which] says whether a run failed but not where or why," and "self-reflection [which] often lacks grounded evidence," against its own graph-localized diagnosis + behavior-scoped guidance + repair memory. Measured on 261 τ-bench tasks (Qwen3.7-max) with a ≤3-iteration repair budget (Table I): **overall (n=123) Blind-retry 43.09% → Outcome-feedback 39.02% (−4.07 pp, *worse than blind retry*) → Reflexion 44.72% (+1.63) → AgentTether-post-run 60.16% (+17.07) → AgentTether 69.11% (+26.02)**; on the hardest Banking domain (n=83): blind 26.51% → AgentTether 59.04% (**+32.53 pp**), and guarded run-time intervention adds **+12.05 pp** over post-run-only where compliance decay is severe; cross-model: 65.12% of failed GPT-5.4 Banking runs repaired. The graph-guided diagnosis is what makes the difference, with quantified mechanism: the root cause precedes the symptom by a **median of 4 required steps (up to 26), upstream in 79% of runs**, one root error cascades into 3.2 further violated checks, and a one-shot diagnosis's adherence **decays below 50% by step 13** (step 8 on Banking) — so diagnosis must be carried and re-applied at run-time. AgentTether also reduces agent turns (66.5→56.4) and end-to-end tokens (1,376K→1,197K), i.e., repair is cheaper than re-executing. This is the strongest direct evidence that diagnosis-guided repair of structured-output-driven agent runs roughly doubles final success and beats blind retry — and that outcome feedback alone can be counterproductive (worse than blind retry) in policy-constrained domains.

**Fact (inference-time reviewer loop with a quantified help/harm trade-off; verified in full text).** "Reinforced Agent" (Ta, Zhu, Shayandeh; Apple, arXiv:2604.27233) measures the *external-feedback* pattern in the form most deployable for tool calling: a **separate reviewer agent evaluates provisional tool calls before execution** (progressive-feedback loop up to N revisions, plus best-of-N selection/grading variants), base agent GPT-4o, reviewers GPT-4o / o3-mini / GPT-5-mini, on BFCL (single-turn) and τ²-bench (multi-turn stateful). The paper's distinctive contribution is the **Helpfulness–Harmfulness decomposition** — helpfulness = % of base-agent errors the reviewer corrects; harmfulness = % of previously-correct responses the reviewer degrades: **o3-mini corrects 36.8% of errors while introducing new errors in 11.7% of correct cases (3.1:1 benefit-to-risk), vs GPT-4o 34.9%/12.9% (2.7:1)** — so even a good reviewer *breaks ~12% of correct tool calls*, exactly the measured price of an LLM-driven repair loop. Net effects: **BFCL irrelevance detection 84.9→90.4% (+5.5%), relevance suite 90.9→92.5%; τ²-bench average 48.7→55.8% (+7.1%)**, with progressive feedback beating best-of-N (+3–8%); τ² failure-mix shift: policy-constraint violations −13%, missing context-awareness −9%, but **over-verbalization +17%** (the reviewer's over-skepticism, seen also on BFCL where 23%→8% of cases had redundant review loops after an explicit "tool-only responses are complete" guideline). Reviewer improvements are cheap: GEPA automated prompt optimization adds +1.5/+2.8 pp (v3 prompt 4.5× longer, 358→1,599 tokens). Cost is the binding constraint: **latency 6.2× on single-turn BFCL (1.27→7.87 s) but only 2.4× on multi-turn τ² (158.7→384.3 s/episode, amortized over ~40 turns)** — so a reviewer loop is ROI-positive only where errors are costly and latency amortizes. Implication for §5: this is the *quantified* external-verifier repair pattern — it works (+5–7 pp) but (a) requires a *reasoning* reviewer (3.1:1 vs 2.7:1), (b) always pays a ~12% harmfulness tax that a deterministic verifier (the §6 pattern) does not, and (c) is latency-bound; it complements VeriHarness's feedback-content finding and the Counsel judge-cap results.

**Fact (structured feedback content determines repair success; verified in full text).** VeriHarness (Ray & Goyal, arXiv:2607.14167) directly measures *what the repair feedback must contain* in a generate-validate-retry agent loop (50 paired TextWorld games, four-call cap). Feedback carrying three fields — failure location, observed value, and admissible alternatives — raised terminal success from **14/50 to 36/50 for Qwen2.5-Coder-14B (+44 pp, CI 28–60, p=3.15e-5)** and from 8/50 to 29/50 for Llama-3.1-8B (+42 pp, CI 28–56, p=3.81e-6). The ablation is decisive: prose with the same repair values (SameNL) gains the same +42 pp, and **TypedFields (keyed JSON record + label) differs from matched prose by only +2 pp (Qwen) / 0 (Llama), p=1.0 both — "no evidence that JSON syntax itself improves repair"**; while LocObs (location+value, no alternatives) stays at the raw-diagnostic baseline, so **admissible alternatives account for most of the gain (+36/+40 pp)**. Budget dynamics: the gap grows from budget 2 (20/27) to budget 4 (47), and raw-diagnostic retries are flat from 4 to 8 calls while structured feedback keeps gaining — extra calls are only useful when the retry receives new information; typed feedback also uses fewer calls (−0.34/−0.24 calls/game) and 14%/10% fewer total prompt words. HumanEval scope check (15 tasks): feedback only helps when the validator exposes a usable failure — it cannot fix what the visible validator does not test.

**Fact (cross-query repair memory — a positive, measured repair pattern; verified in full text).** MERIT (Vo, Chu, Dinh, Bui, Quan; MBZUAI/HCMUT, arXiv:2608.05906) measures whether *retaining* successful corrections improves later repair episodes, on Text-to-SQL (Spider dev 1,034, BIRD dev 1,534; frozen Qwen2.5-7B-Instruct, greedy shared initial predictions, repair budget K=7, execution-accuracy oracle). The training-free agent stores oracle-verified corrections as positive memory and observed unsuccessful directions as negative memory, with a deterministic error-type classifier (Result Mismatch / Schema Linking / Aggregation / Filter-Value / Execution / Syntax / Unknown; ~48% accuracy, Macro-F1 0.32–0.36) conditioning a hybrid dense+BM25 retriever (causal: only finalized earlier episodes are retrievable). Main result: **cross-query memory improves repair over stateless iterative repair — Spider 66.34→69.79 (MERIT), paired Δ+3.45 pp, 95% CI [+1.97,+4.96]; BIRD 47.35→48.44, Δ+1.09 pp, CI [0.00,+2.17] (weaker evidence)** — the memory gain is real but modest and dataset-dependent. However, **MERIT is NOT reliably better than untyped dynamic retrieval (tie on Spider, +0.28 pp on BIRD)** — the added structure (polarity separation, hard type conditioning) is worth ≈0 — and **Reflexion-style verbal memory beats MERIT on BIRD (51.24 vs 48.44, Δ−2.80, CI [−4.15,−1.46]) at ~2.4× the token cost** (22.4M vs 17.6M tokens; 13.6k vs 7.3k calls). Ablations: negative memory contributes little (−0.13/−0.09 pp); type filtering helps only on Spider (+0.58) and dense reranking is its main engine (removing it −1.12 pp Spider); **schema-local experience is the most consistent benefit (cross-database-only retrieval costs −0.93 pp Spider, −2.74 pp BIRD)**. Cost reality: memory does **not** reduce total tokens vs stateless (Spider 5.27M vs 2.53M, BIRD 17.6M vs 9.3M) — it repairs more failures with marginally fewer calls but longer prompts. Implication for §5: cross-episode repair experience is a genuine, *measured* positive-leverage repair pattern (+3.5 pp on the controlled Spider comparison), but its benefits are (a) modest, (b) driven mainly by schema-local episodic experience rather than clever memory structure, and (c) bought with token overhead — it should sit beside, not replace, the deterministic-verifier+retry pattern.

**Fact (parse-then-repair loops reach ~100% within scope).** Two primary system reports quantify the JSON parse → retry-repair pattern. (1) FEniCS natural-language interface (Upadhyay & Reinhart, arXiv:2606.10928): 15-prompt parser benchmark — **9/15 valid on first pass (60%), all remaining repaired after retry → 100.0% final valid parse rate**, with 100.0% problem-class and 97.1% field-extraction accuracy; one unrecovered invalid-geometry failure in a separate 10-case benchmark (90% final). (2) PCN-Rec (Dixit & Dixit, arXiv:2601.09771): verifier-accepts-only certificates with deterministic constrained-greedy repair raise constraint pass rate to **98.55% (feasible users, n=551) vs a one-shot no-verification LLM baseline**, at a 0.021 absolute NDCG@10 cost. Both support the §6 pattern: deterministic verifier + scoped repair closes most of the residual gap (to 98–100%) without closing the semantic-value gap.

**Fact (LLM-as-judge reliability limits — the verifier that many repair loops rely on; verified in full text).** Two primary measurements bound how much an LLM judge can be trusted to drive repair. (1) Merge-conflict resolution judge (Shen, arXiv:2607.27674, Tables 1–4): an LLM-as-judge calibrated against human labels (n=292) reached **100% precision (zero false accepts) at 64.6% recall (accuracy 78.1%)** for accepting resolutions, and — decisively — "the LLM judge accepted 4 of the 5 resolutions that fail the deterministic structural check, **evidence that structural correctness must not be delegated to an LLM**." Same study's solver is itself a generate-validate-retry loop (deterministic gates: parses, no leftover markers, no duplicate declarations; up to 4 retries feeding validator errors back) that reaches **95.8% structural validity** on true conflicts — a clean instance of the §5 rule: deterministic validator + bounded retries hits ~96% structurally-valid output, and the residual 4% is the LLM-judge-unreliable zone. (2) Counsel (Pisupati et al., arXiv:2606.21627; **verified in full text**): process-level LLM-judge critiques on τ-bench/DA-Code, human meta-evaluated (Krippendorff α≈0.78, 1,131 annotations); the strongest judge reached ~88% agreement on *error location* but only ~65% on *reasoning quality*, and — the deployment-relevant number — even the best judge's critiques are "spot on" (correct location + correct reasoning) only **58–63% of the time on τ-bench retail** (Qwen3 63%, GPT-OSS-120B:high 58%) and 43–60% on DA-Code; higher reasoning effort improves critique quality. Implication for §5: when a repair loop's feedback is LLM-generated (as in Self-Refine, VeriHarness's human alternative, or SRL's reward model), the judge's own reliability caps the repair ceiling — 65% reasoning agreement, ~40–63% spot-on critiques, and 4-of-5 structural mis-acceptances explain why execution/schema verifiers (Self-Debugging, SQLQE's ignore-LLM-self-assessment, OrderBench's deterministic fail-closed verifiers) outperform LLM-judged repair.

**Fact (supplying the *error location* is the dominant lever for repair reliability — measured at agent-trace scale; verified in full text).** "AgentDebugX" (Zhu et al., UIUC/Toronto/Google/Stanford, arXiv:2607.18754) closes the loop Detect→Attribute→Recover→Rerun and provides the cleanest measured confirmation of the Tyen et al. principle ("LLMs cannot find reasoning errors, but can correct them given the error location") on real agent failures: its multi-turn root-cause agent DeepDebug reads a whole trajectory (Stage 1), investigates structure-guided (handoff-cascade walk for multi-agent, bisection for single-agent; Stage 2), cross-examines the two candidate steps (Stage 3), and emits an auditable report with the responsible agent+step, evidence, and one concrete fix (Stage 4) — all read-only over the trace. On the Who&When benchmark (n=184, every method given the reference answer but not the gold label, diagnosis on gemini-2.5-flash, debugged policy qwen3.5-9b): **DeepDebug 56.0% responsible-agent accuracy vs 47.8% for the best single-pass strategy; strict agent-and-exact-step 28.8% vs 21.7%; agent-and-±1-step 32.1% vs 23.9%** — the multi-turn margin concentrates on traces >40 events (the regime its two readings target; only 26 traces there, so the authors flag it descriptive). On end-to-end recovery (GAIA validation, 165 tasks, official scorer; vanilla qwen3.5-9b solves 55.8%, fails 73): **DeepDebug's localized fix repairs 13/73 failed tasks in a single rerun vs 4/73 (CRITIC), 5/73 (AutoManual), 6/73 (Reflexion)** run as decoupled baselines (same failed-task context + generic judge-produced failure summary, without DeepDebug's localization/evidence/authored fix) — "more than double the one-rerun repairs," raising overall accuracy 55.8→63.6% (+7.9 pp) with the largest gain on Level-2 multi-hop tasks (48.8→61.6). Cost: DeepDebug ~5 model calls / 12.8K tokens vs 8.1K for one whole-trace pass (1.6×); the pipeline escalates only ambiguous cases, and every attributor returns ranked hypotheses with provenance rather than one blame claim. Two caveats the authors themselves make: the gain is model-dependent (on their hosted backbones a single global reading is already stronger and adjudication does not help — motivating per-model routing, not unconditional multi-call) and swapping the structure-aware reading for a second global searcher costs 4.8 strict points on gpt-5.4-mini. Implication for §5: **localization quality (who/when the run went wrong) is the measurable bottleneck separating repair loops that fix 2–3× more failures from decoupled self-correction — and the fix is authored from the attributed root cause, matching Counsel's "~88% error-location agreement" and Self-Refine's "33% wrong error location" failure share as the same underlying signal.** (System report; single toolkit, no third-party replication yet.)

**Fact (the judge's *interface* matters: freezing evidence degrades it; verified in full text).** "Evidence Lock Before Commitment" (Singh, arXiv:2608.05353) tests whether persisting a judge's extracted evidence and making it the *exclusive* input to the verdict call helps or hurts — the design used by modular/auditable judge pipelines and repair loops. Across **24,000 judgments** (1,500 comparisons × 4 protocols × 2 answer orders × 2 judges — Claude Sonnet 4.5, GPT-5; HelpSteer3/FeedbackQA/CoVal, human-preference gold): **evidence-locking reduces preference agreement by 4.3 pp (Claude) / 5.6 pp (GPT-5) relative to structured one-call judging** (71.7/70.0% vs 76.0/75.6%) and **increases answer-order inconsistency by 9.5 / 8.0 points** (18.9% vs 10.9%; 15.9% vs 8.3%); pointwise locking is worse still (67.3/69.2% agreement); **structured one-call evidence elicitation stays close to standard judging** (75.3–76.0%) — so the harm is the *frozen, exclusive record*, not asking for evidence. The negative effect transfers across all six judge×dataset cells, and locked judging costs far more (mean completion tokens 1,279 → 4,183 evidence-lock → 6,825 pointwise; 1/2/3 calls) while also reducing decisive-criterion recall (−8.2/−11.3 pp) and raising right-for-the-wrong-reason cases (+1.7 pp). Author's interpretation: "the evidence record is not a sufficient interface" — omissions/compressions/order-dependent framing in the persisted artifact become the evaluator, and the final call "cannot repair those choices" without source access. Implication for §5 repair loops: this is the interface-level complement to VeriHarness's feedback-*content* finding — when a judge/verifier artifact is persisted between calls (as in cascaded agents or audit-trailed repair), **removing source access degrades the downstream decision by 4–6 pp and doubles order sensitivity**, so auditability should be additive (record + source), not a frozen replacement.

**Fact (when-to-repair is a measured design lever: selective correction beats correct-all; verified in full text).** GGC (Yang, Nguyen, Chen, Nguyen; NTU/A*STAR, arXiv:2607.28082) isolates the *repair-triggering decision* from the repair itself on Text-to-SPARQL (MCQA, 31,570-test; fine-tuned Llama-3.2-3B). Baseline composition: on 3,085 generated-query errors, **77.70% are semantic (executable-but-wrong: wrong relation, missing constraint, incorrect variable binding) vs only 21.07% syntax errors** — i.e., execution-based correction triggers (the common retry-on-error pattern) miss ~78% of the true failures, the same valid-but-wrong split as §3. The gate is a binary risk classifier (RoBERTa, trained on question+initial-query pairs): **accuracy 98.95%, recall 92.11% (finds most queries that truly need repair), FPR 0.31% (almost never flags a correct query), triggering the corrector on only 9.31% of queries**. End-to-end: **Generator-only 90.23% → correct-all (Gen+Corr) 92.34% → selective (Gen+Gate+Corr) 98.33% query accuracy** (item F1 99.16%), with inference time ~33h vs ~60h for correct-all (**~45% less** for the higher score) — correcting *everything* not only costs 2× but lands 6 pp *below* selective correction, because unnecessary rewriting corrupts originally-correct queries. Threshold-robust (τ 0.25–0.75: F1 stays ~94%, trigger ~9.3%); KG-execution feedback adds little (98.27→98.70) — the question-query pair already carries enough error signal; corrector training benefits from including correct samples (preserves good queries; 98.27→98.80). Implication for §5: the *when-to-repair* gate is as important as the repair — consistent with SQLQE's early-accept ("never re-evaluate a correct query") and the Omidvar & Akhlaghi routing result (~56% cheaper at matched quality), and it is the direct measured counterexample to blanket "retry everything on error".

**Fact (the *when-to-act* gate: filtering uncertain function calls beats guessing — and exposes the limits of consistency as an uncertainty proxy; verified in full text).** "The 'I Don't Know' Filter" (Broecker, del Rosario, Selitser, Strohmer; UC Davis/Okareo, arXiv:2607.04034) attacks function-call hallucination from the abstention side: benchmarks "encourage models to make positive claims even when the answer is uncertain" (an incorrect answer weighs the same as a non-answer, so guessing improves accuracy). It introduces **IDKS = (C−I)/N** — correct minus incorrect calls over total, abstentions neutral, ranging −1..1 — a metric that *penalizes* confident-but-wrong calls instead of ignoring them; and a **consistency-based filter**: run the agent K times on the same input (K=2..5), feed cross-run feature dispersion (semantic volume, variation ratio, pairwise distances from whitebox activations / graybox logprobs / blackbox text embeddings) into a trained random forest, and replace outputs above a threshold with "I don't know." Measured on three 3B-class SLMs (Llama-3.2-3B, Qwen2.5-3B, Phi-4-mini) on BFCL subsets + APIGen (10k) + Irrelevance: **IDKS gains from filtering are consistent and often large — e.g., APIGen 0.342→0.541, Irrelevance 0.025→0.229, Parallel Multiple 0.320→0.490, Multiple 0.700→0.760, Simple Python 0.710→0.743 (blackbox→+gray→+white feature tiers; whitebox helps most but marginal over gray, so "the core uncertainty signal is largely captured at the output and probability levels"); Simple Java is the clear counterexample (−0.100→+0.050 baseline-to-blackbox but *negative* with gray/white — the Llama agent's generally poor Java performance leaves no reliable signal)**. Cross-LM portability holds ("performance drops only slightly" when the classifier trains on a different agent's outputs — Llama is the exception, best filtered by Phi-trained features). Two measured failure modes bound the method: **(1) confident incorrectness** — low variance across repeats is read as reliability (observed: asked for average of floats, the agent emitted an int-list call on all five repeats — the filter has "no signal with which to intervene"; needs external type verification); **(2) superficial formatting inconsistency** — semantically-identical calls differing only in surface form ("3x^2" vs "3*x^2" vs "3*x**2") are filtered as uncertain (remedy: canonicalize before feature extraction). Also a temporal measurement: **baseline IDKS declines as K rises (more repeats → more chances to be wrong once), yet filter gains grow with K** — and the authors note consistency has improved since τ-bench (degradation ~10% by the 5th repeat vs τ-bench's ~half by the 4th). Training data is synthetically generated via *constrained* prompting (gpt-4.1-mini rewrites user questions given fixed functions + expected calls; open-ended prompting produces misaligned questions). Implication for §5/§4: abstention is the *cheapest repair* (no second generation) and the filter quantifies when it is safe — but consistency-based uncertainty fails exactly on the confident-error population that §3 shows dominates semantic failures, so abstention gates must be paired with content-level checks, not variance alone.

**Fact (the *which-procedure* lever: generic retry reproduces the failure mode, procedure-directed repair rescues it — measured on solver-verifiable reasoning; verified in full text).** "The Tell-Tale Trace" (Sourav & Balwani, arXiv:2608.03291) studies whether the *dynamics* of visible chain-of-thought (CoT) — sequencing, repetition, timing of tagged reasoning roles (planning/assignment/verification/backtracking/finalization) — can detect and correct reasoning failure without assuming the CoT faithfully reflects internal computation. Setup: five LLM configurations (Qwen3-8B/14B, Llama3-8B/70B, OLMo2-13B) on solver-certified SAT/UNSAT CNF formulas, each model at its own capability frontier (30–90% accuracy band); 127 matched problem–condition pairs, 91 divergent (wrong vs correct on the same problem+prompt). Findings: (1) **SAT failures show "premature verification collapse"** — wrong traces are half as long, more verification-heavy and cyclic, lower-entropy, finalizing earlier (77.1% of the trace vs 89.8%), yet *clause coverage is unchanged* (p=0.206) — "the failing trace settles into a repetitive verification mode before sustaining enough exploration" (robust signature: cycling up + transition entropy down hold within-family; length/verification effects are cross-family style-dependent); (2) **UNSAT failures substitute assignment search for contradiction proof** — Llama3-70B's frontier accuracy falls 0.526 (SAT) → 0.159 (UNSAT) with false-SAT claims = 0.800 of completions; wrong-SAT traces show less contradiction-search/proof construction and more assignment-verification; separation persists after removing answer-related features (AUROC 0.800/0.795/0.905) but is only modest pre-final (0.507–0.570), so it explains but cannot early-flag; (3) **early-warning is model-dependent, not universal** — 80.2% of Llama3-8B wrong traces flagged before the answer (median lead 23 sentences) and 78.2% for OLMo2-13B (17.5), but only 35.7% for Llama3-70B with zero median lead. The repair result is the decisive one for §5 (Table 2, Llama3-70B, 52 original wrong-SAT completions): **generic retry ("try again carefully", no strategy) → 10.0% accuracy, correcting 6/52 (11.5%); a targeted proof-search prompt (split into cases, propagate forced consequences, derive contradictions) → 85.0% accuracy, correcting 44/52 (84.6%)** — a paired +73.1 pp (bootstrap 95% CI [61.5,84.6]), McNemar-significant, with trace-level confirmation the fix worked by changing procedure (SAT-commitment density 0.0263→0.0105, contradiction-search 0.0658→0.1097). Honest caveats: the intervention is post-hoc and oracle-assisted (solver labels select which failures to rerun), the generic-retry baseline is unmatched in prompt length, and early-warning "is not a general failure detector" (no reported FPR/precision/threshold sensitivity). Implication for §5/§4: **this is the controlled measurement that "retry harder" and "retry smarter" are different mechanisms — the identical model on the identical instances goes from 11.5% to 84.6% corrected solely by replacing a strategy-free retry with a procedure-directed one**, the reasoning-trace analogue of Feedback Loops' and VeriHarness's feedback-*content* findings and of Melo's verbalized retry-hints; it also quantifies that confident wrongness is often a *procedure-selection* failure rather than missing knowledge, and that trace-level monitoring can sometimes catch it before the answer.

**Fact (inference-time weight intervention as a repair mechanism, measured fixes vs harms; abstract-level — PDF only, no HTML).** "Amplitude-Only FFN Intervention for Tool-Structured LLM Inference" (Xu et al., arXiv:2607.11183) positions *inference-time feed-forward (FFN) intervention* as a repair route for tool-structured outputs that needs no retraining: "small format, argument, or function-call errors can invalidate otherwise plausible responses," and a previous direction-changing intervention (Orthogonal Residual Projection) "produced more regressions than repairs." The proposed Amplitude Gating (AG) preserves FFN weight directions and only modulates activation magnitudes, with a gated candidate-generation → ranking → acceptance/fallback pipeline, and a paired-reporting protocol (**Per-Sample Fix-Harm Evaluation, PFHE**) that reports fixes, harms, preserved-correct, and preserved-wrong separately instead of one accuracy number. On the only cross-position union passing their source-alignment audit, an exploratory offline mixed selector raises Qwen3.5-9B tool-route micro-average 38.66% → **42.92% (+4.27 pp)**; two Hermes function-call endpoints improve **+7.64 and +7.62 points**. The same-output PFHE view over 2,556 units: **48 fixes vs 26 harms (≈1.85:1 fix:harm), 294 preserved-correct, 2,188 preserved-wrong**, with positive paired bootstrap intervals for native and strict effects — i.e., *even a successful intervention harms ~1 case for every ~2 it fixes and leaves the overwhelming majority untouched*. Critically, the authors report **negative transfer across models/endpoints: protocol-separated Qwen3-8B and Qwen2.5-7B analyses "retain oracle headroom but no positive train-selected fixed tool route,"** and a grouped five-fold RF diagnostic "is not deployment evidence." Their conclusion: "results support model- and task-specific selection with strict fallback, not a universal AG switch." Implication for §5: this is the *weight-space* analogue of the selective-correction finding — the repair's net value is model- and task-specific, its benefit/latency trade must be measured with paired fix/harm statistics (a single mean hides a 26-harm tail), and a fallback path is required because the intervention is not uniformly beneficial. (Honest tag: all numbers above come from the abstract text; the 30-page PDF was not retrievable as HTML — confidence in the fix/harm counts is high as they are stated directly in the abstract.)

Synthesis across §5: repair loops are only reliably productive when an external, trustworthy signal (tests, oracle labels, a stronger model, a human) drives them; purely intrinsic repair reliably *degrades* correctness. The one measured *intrinsic-but-external-verified* exception is cross-episode repair memory (MERIT): retaining oracle-verified corrections from earlier episodes improves later repair by +3.5 pp (Spider), driven mainly by schema-local episodic experience, though at token overhead and without beating untyped retrieval. **Correcting everything is worse than correcting selectively**: on the controlled GGC comparison (SPARQL, 3.1k generated-query errors), routing only ~9.3% of queries through a corrector (learned gate) reached 98.33% vs 92.34% for correct-all at 45% less inference time — unneeded correction is itself a failure source, so a *gate* deciding *when* to repair is as important as the repair itself. For structured-JSON output specifically, the reliable "repair" equivalent is the deterministic verifier + retry/regenerate loop, and its cost is the inverse-compliance arithmetic in §4.

### 6. Production retry + validation pipelines (measured system reports)

These are single-system reports (not peer-reviewed benchmarks) but they are the only primary sources found that report *end-to-end* numbers for the exact pattern in question: schema-guided prompting + validation gate + local retry/self-heal, applied to structured output extraction.

**Fact (system report; verified in full text).** TCMIIES (Zhao, arXiv:2605.07507): a schema-guided-prompting extraction platform (no constrained decoding; commercial LLM APIs) with a concurrent batch engine carrying up to three automatic retries (1 s delay) per record. Measured on 500 CNKI TCM papers × 3 providers (Tables 1–3): **structured-output compliance average 94.2%** (DeepSeek v4-flash 95.8, Qwen turbo 94.2, GLM-4 flash 92.5) — the ">94%" claim; **field-level extraction accuracy 81.6%** (Research Topic 89.3% down to Research Limitations 73.5%), i.e., even with prompt+retry the semantic-value accuracy plateaus at ~82%, the same schema-valid-but-wrong gap as §3; and retry economics: **first-attempt success 88.4% → 97.1% after the three-retry mechanism**, with 100% completion under 10% injected API failures. Cost anchor (Table 4): ~$0.38/1,000 papers (DeepSeek v4-flash) to ~$3.41 (Qwen max) at ~2,000 input + 500 output tokens per paper — a rare measured per-task API cost figure (for extraction, not retry cost specifically).

**Fact (system report; verified in full text).** SQL Query Engine (Ijaz, arXiv:2604.16511): a two-stage NL→PostgreSQL pipeline with a "multi-strategy response parser" (five-strategy cascade: JSON → embedded JSON → code block → SELECT regex → raw text; tolerant parsing instead of schema enforcement) and an execution-grounded self-healing loop that feeds full PostgreSQL SQLSTATE diagnostics back to the LLM. Measured (three-config ablation across five backends): on the synthetic benchmark (75 questions, 3 DBs), **Config C (generation only) 48.0% → Config A (up to 5 repairs) 57.3% for Llama 4 Scout 17B (+9.3 pp, zero regressions)**; on BIRD mini-dev (437 questions, 11 DBs) the full pipeline reaches **49.0% execution accuracy (GPT-OSS-120B), +4.6 pp** from self-healing. Latency cost of repair is visible: Scout 1.67 s → 4.19 s mean. The design validates §5's rule with three explicit mechanisms: **early-accept** (never re-evaluate a query that executed correctly — prevents the LLM "fixing" a good query into a bad one), **best-result tracking** (return the best result seen when retries exhaust — a bad retry cannot regress), and **ignoring the LLM's own isValid self-assessment** (always False by design; only execution outcome determines success).

**Fact (system report; verified in full text).** xmemory / schema-grounded memory (Petrov, Gusak, Mukha, Korolev, arXiv:2604.27906): iterative, schema-aware extraction with "validation gates, local retries, an LLM judge-in-the-loop, and stateful prompt control." §8.2 measured (10 runs, mean±std), its single-pass frontier baselines (Sonnet 4.6, Opus 4.7, GPT-5.4, GPT-5.5, Gemini 3.1 Pro) hit near-saturated **field-level F1 95–97%**, but collapse at aggregate levels: **object-level accuracy 79.24–89.24%** (all fields exact within one object) and **output-level accuracy 34–62%** (all objects in a claim fully correct; GPT-5.4 34.0±7.0, Sonnet 4.6 42.0, Opus 4.7 42.7, GPT-5.5 high-reasoning 44.0, Gemini 3.1 Pro 61.7). xmemory's judge-in-the-loop configuration reaches **90.42% object-level and 62.67% output accuracy, above all tested frontier structured-output baselines**; end-to-end memory benchmark **97.10% F1 vs 80.16–87.24% for third-party baselines**; 95.2% on an application task. The paper also states an illustrative compounding model (not measured): at per-field accuracy 0.97 with 20 fields, single-pass record-correct probability is 0.97^20≈0.54, recovering to ≈0.98 with two retries per field. Interpretation: the near-saturated field-level numbers (95–97%) yet collapsed output-level numbers (34–62%) for single-pass frontier models are the *same* compounding-collapse measured in §3 (SOB 15–25 pp JSON-pass-vs-value gap; OrderBench 100% schema-valid / 2–83% semantic); an LLM-judge + retry loop raises whole-output exactness from ~34–44% to ~63% — validation closes part of the compounding gap but the plateau remains well below field-level saturation.

Cross-pattern synthesis for §4–§6: when the verifier is deterministic (schema validator / SQL execution / exact check), a retry+validation loop reliably lifts structured-output success to ~90–97% and never regresses; the residual failure is not syntax or schema but *semantic leaf values*, which deterministic validation cannot catch — the measured plateau is ~63% (leaf) to ~80% (transaction semantics).

**Fact (system report: constrained JSON extraction at EHR scale; verified in full text).** MOUD medication extraction (Fei et al., UC Riverside/UCLA, arXiv:2510.21027): an open-source-LLM pipeline that forces generation directly into a fixed Pydantic JSON schema (constrained generation, vLLM) to extract prescription attributes from five heterogeneous EHR systems, then applies post-processing (type normalization, **rule-based cross-field validation** — e.g., total_quantity ≥ daily_quantity — and MOUD-days computation). Measured on 10,369 manually-annotated ground-truth records (776 patients, from 25,605 total): **Qwen2.5-32B achieves 93.4% coverage / 93.0% record-level exact-match accuracy overall; MedGemma-27B 93.1%/92.2%** — i.e., even at ~93% coverage, only ~93% of those fully match on all 5 attributes + computed metric, the recurring valid-but-wrong tail. Two production-relevant findings: (a) **clinic heterogeneity dominates model choice** — Qwen2.5-32B scores 100/100 on Clinic A while Qwen3-32B scores 0% there (42.9% coverage); smaller models are coverage-unstable (Qwen3-8B overall coverage 48.0%, Qwen3-4B 2.2% on Clinic C), so "model family matters as much as size" for schema-constrained extraction; (b) the repair loop is *human-analyst-driven*: a domain-expert error review identified three recurring fix classes applied as rule-based post-processing — **imputing missing dosage fields from within-drug norms (Clinic B ~20% of records had key missing fields), handling monthly/weekly injectables (e.g., Vivitrol ~5% of Clinic C/E prescriptions) by setting duration from the documented schedule, and unit normalization to stop mass units ("250 g") being misread as daily counts** — the same "residual semantic errors need domain rules, not more retries" pattern as §6. Constrained JSON generation eliminates parse failures so the residual gap is value correctness + missing-data handling, and the authors explicitly note human-in-the-loop review is essential for high-stakes clinical use.

**Fact (system report: on-device SLM structured output; verified in full text).** Palabrita (Oliveira, arXiv:2604.24636) is a practitioner case study with a commit-level evidence trail (204 commits/5 days, ~90 AI-related) of running on-device SLMs (Gemma 4 E2B 2.6B; Qwen3 0.6B; LiteRT-LM) to generate structured JSON (word + category + difficulty + hints). It documents five on-device failure categories with measured rates: **F1 format violations** — markdown code-fence wrapping of valid JSON (majority of early calls, dropped to ~20–30% after "no code fences" prompt; a structural parser needed for 15–20% of Qwen3 0.6B parses), JSON *keys* translated into the prompt language ("palabra"/"dicas"), and UTF-8 replacement-char corruption (<5% but fatal); **F2 constraint violations** — wrong word length (**30–50% of early generations — the 600M model cannot reliably count characters**; dropped to ~10–15% after prompt hardening with concrete rejection examples + "CRITICAL" emphasis tokens, but "still too high for production reliability"), wrong-language words, within-batch repetition, hints containing the target word; **F3 context quality degradation** — output quality collapses after ~3 generations (Qwen3 0.6B) / ~5–7 (Gemma 4 E2B) in a chat session due to limited on-device KV cache, mitigated by session rotation; **F4 latency** — a full puzzle took 15–30 s (30–35 tok/s CPU), so 7 puzzles × avg 2.5 retries > 2 min of UI block; **F5 model selection instability** — 6 models each needing a different prompt profile; cut to 2. The resolution is the report's §5 rule applied at the architecture level: **defensive parsing as a pipeline (UTF-8 sanitize → code-fence strip → direct decode → regex extract → structural type-based field inference), contextual retry feeding the specific rejection reason back into the prompt (word length errors were the main trigger), and the "progressive simplification" arc — the LLM's job was reduced from 7 output fields to 0 for word generation (curated word lists) and 2 fields for hints only, with a deterministic fallback so "the LLM enhances the experience; it does not gate it"**. The authors' explicit arithmetic matches the compounding-collapse theme: "for n fields with independent violation probability p, expected success is (1−p)^n; reducing from 5 to 2 fields approximately doubled the success rate." Implication: at SLM scale the *measured* reliability of structured output is dramatically lower than frontier models (0–50% constraint compliance without heavy engineering), and the reliable design is minimal-schema + defensive parse + feedback-retry + deterministic fallback.

**Fact (system report: reflective retry in production, with measured trigger/recovery/latency arithmetic; verified in full text).** Melo (Wang et al., NetEase Cloud Music, arXiv:2607.23718; RecSys '26) is a production LLM music-recommendation agent behind Muse Mix (100M+ user platform, >1M cumulative users) built as a deterministic five-node state graph (UNDERSTAND→PLAN→EXECUTE→REFLECT→SYNTHESIZE) over heterogeneous tools — deliberately *not* a free-form ReAct loop, because "across a free-form chain, intent-parsing, argument-extraction, and tool-side errors compounded across steps." Two named-node defenses: **inference-time entity grounding** (three layers: L1 catalog reverse-lookup as verification primitive, L2 prompt-level consumption rules, L3 plan-time guards) and **reflective retry** (REFLECT→PLAN back edge, capped at two rounds, verbalizing failure causes; REFLECT picks among proceed / retry_rewrite / retry_relaxed / fallback). Measured on an internal 298-query evaluation set stratified to over-sample the two failure modes, each config replayed 3× at temperature 0.3 (Kimi K2.5 backbone; ~10³ measurements), with explicit caveats: rates are properties of the stress-test set, "not estimates of raw production frequency." Retry numbers (Table 3): **retry fires on 5.8% of sessions; process-level recovery 59.1%** (retry_relaxed 63% recovering 52% of triggers, retry_rewrite 56% recovering 48%); **constraint preservation after recovery 77%** (23% recovered-but-degraded, degradation concentrated in retry_relaxed 29.4% vs retry_rewrite 14.3%; intent-preserving recovery ≈46% of triggered sessions) — the paper's central caution: "retry must not hide what it gives up," so candidate recovery and constraint preservation are evaluated as two metrics in tension. Retry cost: **+15.9 s P50 / +29.2 s P99 per triggered session, amortized over all traffic just +4.1 s P50 / +13.6 s P99** (paired retry-on/off ablation: P50 32.5 s vs 28.4 s; avg song count +0.21 over all queries but +17.5 candidates on the tail queries it materially improves) — "retry is cheap on the median session because it does not run, and high-leverage on the tail sessions where it does." Grounding ablation (Table 2): **entity misidentification 17.4% → 9.6% (−7.8 pp) with full defense, at +2.5 s UNDERSTAND / +1.8 s PLAN P50 latency** (L3 alone −1.2 pp, +L2 −3.8 pp, +L1 −7.8 pp cumulative — catalog evidence alone is not enough, the LLM needs explicit weighting rules). Online A/B (1M users, April 2–May 10): >2 pp primary playlist-retention lift, >1 min core engagement lift (no CIs/significance; novelty and product-surface effects not fully ruled out — reported as lower bounds). Node-level cost: LLM reasoning, not tool dispatch, dominates (UNDERSTAND 8.0 s + PLAN 8.2 s + SYNTHESIZE 10.3 s P50 of 26.0 s end-to-end; EXECUTE 0.04 s, non-retry REFLECT fast-path ~0 s; triggered-session REFLECT adds a 6.4 s P50 LLM call). Implication for §4/§6: this is the *retry-economics* anchor the literature otherwise lacks — the retry loop's true cost is the latency arithmetic (a rare +4.1 s amortized / +15.9 s triggered measured pair), its benefit is converting otherwise-empty sessions into usable ones, and its failure mode is silent constraint degradation (23% of recoveries), so a production retry must be evaluated on recovery AND preservation, not recovery alone.

**Fact (system report: generation-pipeline decomposition vs monolithic — measured structural and semantic rates across 2,784 runs; verified in full text).** "Evaluating LLM Trade-offs for Enterprise Automation" (Wrenn, Raykov, Angelov, Kitahara, Watanabe, Sailer; IBM, arXiv:2608.03311; IC2E '26 Industry) benchmarks six LLMs (granite-4-h-small 32B/9B-active MoE, llama-3.3-70B dense, llama-4-maverick 400B/17B-active, mistral-small-24B, mistral-medium ~70B, gpt-oss-120B/5.1B-active) for generating low-code workflow JSON (Concert Workflows schema) across 29 real compliance/IT prompts, 8 runs per cell, two pipeline architectures — **2,784 runs, 232 attempts per model per pipeline**. The v1 monolithic pipeline (generate the whole workflow in one call) got **structural success (JSON-schema valid + UI-renderable) of just 31.5–82.8%** (gpt-oss-120b best 82.8%; granite-4-h-small 31.5%, mistral-small 33.2%) — "for most models, this cognitive load exceeded their structured output capacity, resulting in malformed JSON, incorrect block references, and type mismatches." A redesigned **piecewise pipeline** (v2: deterministic early Planner → retrieve evidence → generate workflow *variables* → *base blocks* → *nested blocks* separately, then a programmatic-fix step before LLM JSON-Patch correction, ≤2 retry rounds) raised structural success to **74.1–97.8%, with four of six models >90% (zero under v1)** — mistral-small 95.7% at $0.010/workflow, gpt-oss-120b 97.8% at $0.016, mistral-medium 96.1% at a **19× cost premium** ($0.197; 0.4 pp gain), llama-4-maverick 90.5% at $0.024 and fastest (33.6 s). Latency is the piecewise cost: input tokens and generation time rise (e.g., mistral-small 34.4→42.6 s, llama-3.3-70B 76.2→151.4 s with its generation rate *declining* 95.3%→81.5%); gpt-oss-120b is the sole exception (99.3→66.2 s). The decisive measurement is the **structural-vs-semantic gap** (independent Claude Sonnet 4.5 judge at temperature 0, 0–100 rubric + majority-vote "prompt satisfied" over 3 gradings × 1,044 total): **even the strongest model, llama-4-maverick on v2, satisfied only 55.2% of prompts (mean 71.5); the next-best 44.8%** — "no benchmarked model achieved reliable correctness" and "human review of generated workflows before execution remains necessary." And a model-specific failure only semantics can see: **gpt-oss-120b regressed 58.9→44.9 semantic (−14.0) and 24.1%→6.9% satisfaction on v2 despite being #1 structurally (97.8%)**, because v2 caused it to emit *stub* workflows — a single comment block declaring integrations unavailable — which pass schema validation but are non-executable ("uniquely treacherous: first on structural metrics, last on whether outputs do what users asked"). Cost anchors: $0.008–$0.20/workflow; annualized 1,000/day: mistral-small ≈$3,700/yr vs mistral-medium ≈$71,900/yr. Implication for §1/§6: this is the strongest production measurement that (a) **decomposing the generation task (piecewise, not monolithic) is a more reliable fix for complex-schema JSON than any single-model choice** — it took the worst v1 model (33.2%) past the best v1 model's ceiling, and (b) **structural validity and semantic correctness are nearly orthogonal at production scale — 97.8%-structural/6.9%-satisfaction in the extreme case — so a schema-pass gate cannot substitute for semantic review**, the exact §3 collapse at enterprise workflow scale. (Point estimates only — no per-cell CIs/significance reported by the authors.)

### 7. Tool-position claims and evaluation-validity caveats

**Fact (empirical fault taxonomy of real agentic-AI systems; verified in full text).** "Characterizing Faults in Agentic AI" (Shah, Morovati, Rahman, Khomh; Dalhousie/Polytechnique Montréal, arXiv:2603.06847) grounds the failure landscape behind this report's numbers in real production data: 13,602 closed issues/merged PRs from 40 open-source agentic-AI repositories (>1,000 stars), stratified-sampled to 385 faults, analyzed by grounded theory into a taxonomy (5 architectural dimensions, 13 symptom classes, 12 root-cause categories), validated by a 145-practitioner study (mean relevance 3.97/5, Cronbach's α=0.904, 83.8% had personally encountered the covered faults). **The structured-output link is quantified directly: "Data & Validation Errors" is the single most common observable symptom (75 occurrences, 20.0% of all faults)** — ahead of installation/dependency issues (13.3%) and runtime failures (10.7%); the two dominant root causes are **Dependency and Integration Failures (19.5%)** and **Data and Type Handling Failures (17.6%)**, which the authors interpret as "systematic contract violations between probabilistically generated artifacts and the deterministic interface, type, and runtime constraints enforced by external software systems." Concrete fault examples relevant to §1–§6: **LLM Integration faults include "invalid JSON responses"** (MetaGPT producing invalid JSON when its RAG module misinteracted with the Ollama provider); **API Parameter Mismatch includes tool-calling failures from "null values where structured parameters were expected"** (SWE-agent); token handling/tracking faults (different tokenizers between framework and provider causing context overflow/truncation). Association-rule mining gives high-lift propagation pathways (e.g., authentication failures ← token-refresh mishandling, lift 181.5; wrong time values ← datetime-conversion errors, lift 121.0), showing faults "do not fail transparently — weak error handling and limited logging obscure their underlying causes." Implication for this report: 20% of real agentic-AI faults manifest as data/validation errors and ~37% stem from dependency/data-type causes — the "schema-valid ≠ correct" and interface-mismatch themes are not benchmark artifacts but the top failure classes observed in 40 production frameworks (e.g., LangChain, AutoGen, MetaGPT, SWE-agent, crewAI).

**Fact (eval-validity caveat; verified in full text).** "Do LLMs Know They Are Being Tested?" (Ahmed, Zaman, Saleem, Hassan; arXiv:2510.08624) runs six paired A/B scenarios on GPT-OSS-20B holding task content and decoding fixed while varying evaluation-vs-real-world framing: evaluation framing inflates chain-of-thought length (hundreds to >1000 chars) and reduces answer-only compliance, and "in structured outputs, it improves wrappers (e.g., fenced blocks, enumerated lists) but not regex-validated substance" — a direct instance of specification gaming (e.g., a `<fixed>` fenced code block present while the regex-validated fix is wrong). Incentive wording reweights the error mix (praising caution reduces wrong-but-confident errors at the cost of hedging; praising competence yields terser but riskier outputs); Urdu rubric headers reproduce the signatures and can lower accuracy at high reasoning depth. Implication for every number in this report: benchmark prompts that demand strict formatting can inflate *wrapper-level* schema compliance without improving substantive value correctness — one more reason the schema-valid-vs-correct gap (§3) is measured with honest, substance-checking validators (JSONSchemaBench's jsonschema validation, SOB's leaf-value match, OrderBench's deterministic verifier). (Single-model study; the framework, not the model ranking, is the contribution.)

**Fact (tool-calling benchmark evaluators are themselves error-prone; verified in full text).** "Benchmarking the Benchmarks: A Validity Audit of Tool-Calling Evaluation" (Vaghasiya, Bhat, Mohsin, Aali; CoreThink AI/Stanford, arXiv:2607.02577) is the most direct check on the *measurement instruments* behind the §3 function-calling numbers: a trace-level audit of 496 tasks across four benchmark families, with expert adjudication of benchmark-assigned labels vs human PASS/FAIL (89 annotator-hours). Aggregate evaluator–human misalignment **18.5% (92/496)**; per-benchmark error rates: **BFCL v4 (AST + simulator-state) 20.0% (40/200)**, τ²-bench Retail (DB-hash + NL assertions) 9.8% (11/112), MCP-Atlas (LLM claim coverage) 13.5% (12/89), **LiveMCPBench (LLM judge) 30.5% (29/95)**. Mechanism detail — deterministic evaluators fail by **brittle state matching, trajectory lock-in, incorrect ground truths, substring-based assertions, and reward-basis misalignment**: in the inspected BFCL v4 multi-turn export, 80% of official failures are `instance_state_mismatch`, which "conflates genuine task failures with evaluator artifacts" (task-irrelevant state diffs, punctuation-level discrepancies, full-object comparisons when only a subset of fields matters, premature termination before a later corrective action); a τ²-bench false negative shows a correct $708 answer rejected because the final response lacks the substring "1628" — "an incorrect semantic target implemented as a substring check" — and a false positive shows inaction passing because unchanged DB state looks successful. LLM-judge benchmarks fail by **rubric drift, hallucinated completion, answer-only scoring, and run-to-run variance**: **23 repeated LiveMCPBench runs of the same setup score 57.9–76.8% (mean 69.4%, σ=5.4 pp, spread 18.9 pp)** — larger than most leaderboard margins, because the judge regenerates task key-points per run (default judge gpt-4.1-mini, weaker than the paper's recommendation). Implication for this report's §3 function-calling numbers: **BFCL V4's quoted overall/multi-turn percentages (e.g., 77.47% top model) carry an ~20% evaluator-error band and should be read as relative rankings, not absolute success rates** — matching the existing BFCL audit caveat (20% LLM-judge evaluator misalignment) that the PTC paper (source [57]) cited; deterministic-first scoring (Tool-Veritas: state gates + restricted LLM fallback, bounded repair window) raised expert agreement to 95.5% (401/420) vs 69–90% for the audited families, with all 19 disagreements being *stricter* (false negatives, no unsupported passes) — the recommended direction for repair-loop-relevant evaluation.

**Fact (the benchmark's *error budget* is itself a masking instrument — final score can be blind to 2.5× per-step failure amplification; verified in full text).** "Flat Score, Amplified Failures" (Jang, Yang, Lim, Park; Korea Univ., arXiv:2607.27275) is the most direct demonstration that §4/§5's retry-and-recover loop can hide damage from *every* aggregate metric: on τ²-bench, across two open-weight families (Gemma-4, Qwen-3.6) × {dense, MoE} × two domains (ten cells, 456 episodes per arm, 16/8/4-bit weight-only AWQ), 4-bit quantization produces a statistically flat final score in every cell (no change survives multiple-comparison correction; seven cells TOST-equivalent at ±7.5 pp) — yet **in the damaged cell (Gemma-4-31B, telecom) quantization raises tool-name hallucination from 19.51% → 38.26% of the agent's tool calls (+18.75 pp, CI [14.0,23.6]) — a 2.5× growth in event volume (649→1,646)** — while creating essentially no new failures (BF16/INT4 hallucinated-name distributions correlate 0.97; only 0.18% of INT4 events name a tool never invented at BF16; 23/24 invented names are real *user-side* tools — "role-boundary confusion," amplified not invented). The score stays flat because **the benchmark allows ten failed tool calls per episode and per-error recovery is equally reliable at both precisions (55% recovery rate after a failure, unchanged)** — "the loop actively repairs the errors quantization introduces before they reach the outcome," at the cost of 2.5× more failed calls per episode (1.45→3.64) and 29% more tool calls (7.3→9.4). The falsifiable proof: **shrinking the error budget K re-exposes the damage — the BF16−INT4 gap grows from 1.3 pp (K=10) to 7.5 (K=5) to 16.7 pp (K=2), ~13× wider**, and only in the one volume-adding cell (15.4 pp there, ≤0.2 elsewhere); cost side: budget-exhausting terminations rise 9× (5→46 of 456). Mechanism: logit-margin account — quantization noise flips only thin-margin argmax decisions, so **full-precision failure propensity gates susceptibility** (near-zero baseline Qwen cells are not amplified at all; checkpoint identity, not size/architecture, decides). The repair arm closes the loop for this report: a **reflexive error-repair loop (on a failed call, append "ERROR: {err} Reissue this tool call with corrected, schema-valid arguments.", regenerate, up to 3 attempts; runs for five telecom models at every precision) collapses the tool-name channel 38.26% → 2.90% (INT4), cuts out-of-list events 1,646→82 (20×), eliminates budget exhaustions (46→0), shortens trajectories (17.9→15.9 turns), and raises the INT4 final score 65.35 → 71.27 (+5.9, CI [+1.1,+10.8], p=.017) — above unmitigated BF16 (66.7%) — while every other cell's repair interval includes zero** ("the mechanism is prevention rather than cure," and MoE suppresses only 4× vs dense 20×). Implication for this report: **(a) any end-of-episode reward on an agentic benchmark with an error budget can certify a system whose per-step reliability has halved — report per-channel error rates and success-vs-budget alongside task reward** (the paper's explicit recommendation); (b) the measured repair-recovery loop is *recovery-into-the-budget*, not correctness — it converts budget slack into eventual success; (c) a mechanism-targeted repair (feed the validator error back, re-issue corrected, bounded attempts) is cheap and recovers score exactly where damage lives — consistent with §5's feedback-content rule and §4's bounded-retry-with-validator-feedback economics.

**Claim.** JSONFormer (1rgs/jsonformer): "bulletproof JSON generation… ensures that the generated JSON is always syntactically correct and conforms to the specified schema" by generating only content tokens and filling fixed tokens; asserts prompt-engineering/fine-tuning/post-processing "still fail to generate syntactically correct JSON in many cases" — no measured rate. Guidance (guidance-ai/guidance): "guarantee output syntax with constrained generation"; claims token fast-forwarding reduces forward passes (lower latency/cost). Outlines/EGG paper (Willard & Louf, arXiv:2307.09702): index-based guided generation "guarantees the structure of generated text," "adds little overhead," and "significantly outperforms existing solutions" — the quantitative cross-framework validation is in the JSONSchemaBench tables above rather than this paper.

**Claim + position (survey synthesis; abstract-level — no HTML/ar5iv full text).** "Small Language Models for Agentic Systems: A Survey of Architectures, Capabilities, and Deployment Trade-offs" (Sharma & Mehta, arXiv:2510.03847) is the survey-level statement of the report's §2/§4 pattern: **SLMs (1–12B, sometimes up to 20B) "are sufficient and often superior for agentic workloads where the objective is schema- and API-constrained accuracy rather than open-ended generation,"** and guided decoding + strict JSON Schema outputs + validator-first tool execution "close much of the capability gap with larger models and often let SLMs match or surpass LLMs on tool use, function calling, and RAG at 10x–100x lower token cost." Its contribution to this report is the *engineering metric set* it proposes to replace single accuracy numbers, which is exactly the reliability-measurement agenda of §1–§8: **cost per successful task (CPS), schema validity rate, executable call rate, p50/p95 latency, and energy per request**, plus the SLM-default/LLM-fallback system design with uncertainty-aware routing and verifier cascades (design patterns: schema-first prompting, type-safe function registries, confidence scoring with verifier rollups, LoRA/QLoRA adaptation). It explicitly delineates where fallback to LLMs remains valuable (open-domain reasoning, some long-horizon planning). Implication for this report: the surveyed design (schema-first + validator-first + verifier cascades + routing) is the deployment-level form of the measured findings here — each of the survey's proposed metrics maps to a measured number elsewhere in this report (schema validity rate ↔ JSONSchemaBench compliance; executable call rate ↔ the tool-call executable gaps in §3; CPS ↔ the retry/token economics of §4; verifier cascade ↔ §5's external-verifier rule). ## Verdict

**Established (measured).** (a) Without enforcement, schema compliance on complex schemas is low even for frontier models: JSONSchemaBench (small open model, github splits) 13–46% compliance; SchemaBench (~40K schemas, depth 16.7) **GPT-4o 61.06%** overall valid-JSON (84.47% complex / 61.56% custom / 37.14% escape), GPT-4o-mini 43.98%, and 8–36% parser-error rates on open models — so native generation fails on roughly 40–90% of complex schemas. Enforcement (constrained decoding) brings per-schema compliance to 63–98% for open grammar engines and ~100% for closed providers — but only on the subset of schemas each engine declares support for (closed providers support as little as 6–9% of hard real-world schemas). (b) Enforcement eliminates syntactic parse failures; its *quality* effect is layered and now well-characterized: constrained decoding itself is roughly cost-neutral (JSONSchemaBench +3 pts GSM8K; TOON finds plain JSON marginally more accurate), but the format *request* is a real, capacity-dependent reasoning tax on open-weight/near-limit models — Tam et al. GSM8K Haiku −63 pts under JSON; Format Tax: 92% of degraded cells lost to the prompt alone, 3 GCD-only; Capacity: Haiku −36.2 pp, GPT-4o-mini −28.0 pp, Opus 4.7 AIME −5.3 pp, and forced function calling collapses hard-reasoning to 10%. Three measured remedies exist: reasoning-augmented grammars (CRANE, +10 pp), trigger-gated single-call decoding (In-Writing, +27% on classification, though small models can emit the trigger prematurely and lose the reasoning — a documented failure mode, so trigger choice matters), and prompt-level decoupling (two-pass +6.8 pp / thinking +9.2 pp). (c) Schema-validity does not imply correctness: even at 100% schema validity, semantic/value accuracy plateaus near 80% on text and far lower on image/audio (SOB best 83.0/67.2/23.7%; OrderBench 100% schema-valid with 2–83% semantic across models); the gap *compounds* with schema breadth and context length — single-pass frontier output-level exactness collapses to 34–62% even at 95–97% field-level F1 (xmemory §8.2), and to 0% valid output on a 369-field enterprise schema (ExtractBench); "sporadic" content errors persist; unenforceable format rules embedded in schema *descriptions* fail at 8–70% adherence even for GPT-5/Claude Opus 4.1 (IFEval-FC), and nested/hierarchical output constraints are far worse — the best model reaches only 53.7% prompt-level on a deterministic nested-constraint benchmark and every model drops 37–53 pp at the first nesting level (IFHierBench); and function-calling selection accuracy drops 8–19% when the toolkit grows with semantically related tools and 1–8% on rephrased queries (BFCL robustness). (d) Enforcement overhead is an implementation property, not an inherent cost: with mask-cache + CPU/GPU overlap (XGrammar) mask generation drops to <40 µs/token ("up to 100×" vs regex/CFG baselines, ~zero end-to-end overhead), though the fastest configuration can be the most permissive (XGrammar's highest under-constraint count on the JSON Schema Test Suite); and enforcement can *disable* a different capability — under joint tool-calling + JSON-schema constraints, grammar masks silently suppress tool calls (TIR 100%→0% for 6 open-weight models; two-pass decoupling restores it) — so in agent stacks the compliance win can hide an action-taking loss (Constraint Tax). (e) Repair loops: intrinsic self-correction without an external signal consistently *lowers* accuracy (measured drops of up to ~25 pts for Llama-2 GSM8K) while multiplying call cost 1→5×; repair only reliably helps with external feedback — oracle labels, execution/unit-test signals (Self-Debugging: +2–9% to +12%), or stronger/human feedback (1.58× more repaired programs pass) — and at equal budget repair often ties or loses to plain i.i.d. resampling (Self-Consistency's +3.9–17.9% is the baseline to beat). The most-cited positive loop, Self-Refine, verifies with a crucial caveat: its headline ~20% is driven by preference/constrained tasks (+20–49 pp), while math gains are ~0 (64.1→64.1, 92.9→93.1) because the model cannot tell its own math is wrong — the same verifiability boundary as Huang et al. Its own failure analysis confirms the feedback stage, not the refiner, is the bottleneck (61% bad fix, 33% wrong location, 6% refiner error). The one cost-honest exception (Self-Debugging) shows ~10× sample-efficiency when a deterministic verifier drives the loop; difficulty-adaptive retry budgets are up to 4× more compute-efficient than uniform best-of-N (Snell et al.), and test-time compute can match a 14× larger model under FLOPs matching. (f) Production retry+validation pipelines (deterministic verifier + local retry) reliably reach ~90–97% success and never regress (TCMIIES >94% compliance; xmemory 97.1% F1, 90.4% object-level; SQLQE +9.3pp with zero regressions), but they cannot close the semantic gap: xmemory's leaf-level output accuracy stays at 62.7% and OrderBench/SOB put semantic success at 80% / 83% — the residual failure is always the schema-valid-but-wrong value. The enforcement→hidden-error shift is quantified: on sub-3B models hard schema decoding raises validity 61.5→100% while *raising* wrong-valid-schema outputs 49.5→88.9% and cutting answer accuracy 19.7→11.0%, and even a deterministic calendar tool-call loses 43.5 pp executable accuracy at 100% schema validity (102/104 failures = one wrong field) — so "wrong-valid-schema rate" is the first-class reliability metric that counts failures passing parsers, which retries do not fix (Ray's constraint tax). (g) The native rate can also be improved offline: RL with a fine-grained schema validator (SRL) raises valid-JSON generation 28.5→72.5% (Llama-3.2-3B) and 36.5→79.7% (Llama-3.1-8B) — the only measured route that improves what retries resample from. (h) At the agent level, reliability plateaus lower: τ-bench's gpt-4o succeeds on <50% of policy-compliant tool tasks and pass^8 is <25% in retail — 8 retries still fail on >75% of tasks, so pure resampling is exhausted; live BFCL V4 confirms even the top model (Claude-Opus-4-5, FC) is at 77.47% overall, with multi-turn the weak category (best 68.4%). The measured fixes are diagnosis-guided runtime repair (AgentTether repairs 59–65% of failed runs on the hardest domain, beating blind retry, plain outcome feedback, and self-reflection, at lower turn/token cost) and feedback *content* (VeriHarness: adding admissible alternatives to repair feedback gains +44/+42 pp, and JSON-vs-prose presentation is neutral — "no evidence that JSON syntax itself improves repair"); at the infrastructure layer, retry storms from rate limits are preventable with jittered exponential backoff (ContinuityBench: 99.20% continuity, N=750). (i) Retry cost is structurally determined, not a fixed multiplier: rerunning only failed subtasks cuts retry token cost by 51.7–73.2% vs monolithic/static-decomposition reruns (Asthana et al.), a cost-aware reliability router achieves ~56% lower cost at matched quality than any fixed retry/voting technique (Omidvar & Akhlaghi), and unchecked retry loops are a documented $-thousands production failure class (63 incidents, 21 frameworks — Khan). Agentic orchestration multiplies energy per successful goal 4.33× vs linear (Panigrahy et al.). (j) One large measured counterpoint to "always enforce": on 8,560 trials across 14 models, free-text tool calling (NLT) beat structured tool calling 62.3% vs 47.4% accuracy with 93% fewer critical errors and 25.2% fewer tokens — enforcement guarantees parseability, not task success, and for tool calling can add retry cost rather than remove it (Somma et al.). The interface dimension extends beyond free-text vs JSON: replacing native JSON tool calls with programmatic (code) tool calling matches or exceeds JSON accuracy on 11/14 models on a BFCL v4 subset and removes a *structural* JSON limit — native JSON tool calling drops calls outright at fan-out N≈70–100 (Claude Sonnet 5: 100% enumeration at N≤70 → 0% at N=100) where code-based calling holds 100% — so the serialization interface itself is a measurable reliability lever (Patel et al., PwC). The *schema representation* is a further, independent lever: for small models the JSON format of tool schemas itself is the dominant failure driver (accuracy collapses to 0–49% at >15 tools), and deterministically rendering the same schemas as plain text restores 0→84% (Phi-4 14B) — with the mechanism being format translation, not token compression (R² 0.88→0.03; Sakizli's TSCG) — so JSON, the production standard, is measurably the *worst* representation for small-model tool use. Retry loops must also key on the *right* verifier: syntax-validity and schema-compliance diverge sharply (worked example: 1.0 vs 0.2), so a parse-only retry loop can pass while the true failure rate is 80%.

**Uncertain / not verifiable from reached sources.** There is no single canonical "JSON failure rate"; published numbers depend on model, schema complexity (SchemaBench depth ~16.7 vs JSONSchemaBench splits), and validation method. The two big benchmarks disagree on the no-enforcement regime (13–46% vs 27–61%) precisely because of schema-depth and model differences — both are measured, but neither generalizes to "the" rate. The vendor guarantee statements (OpenAI, Anthropic) are first-party claims: OpenAI publishes one measured ladder (prompting <40% / trained-only 93% / strict 100%) on its *own* complex-schema eval and explicitly limits the guarantee to its supported JSON-Schema subset; whether closed-provider compliance stays ~100% on arbitrary schemas outside that subset is undefined and unverified here. IFEval-FC's format-adherence tables, the BFCL-robustness table, and the production/system reports (TCMIIES, SQLQE, xmemory, ContinuityBench, AgentTether) are each limited to specific models/domains at one point in time and mostly lack independent replication; τ-bench's and SchemaBench's headline numbers are for 2024-era model versions. The BFCL live numbers quoted here are the 2025-12-16 archive snapshot (evaluation commit f7cf735); the leaderboard page reports a later 2026-04-12 update whose per-model table is JS-rendered and unextractable, so the two could differ slightly — and an independent expert audit puts the *evaluator's* own error rate at ~20% for BFCL v4 (state-mismatch artifacts dominate) and 30.5% for the LLM-judged LiveMCPBench (score spread 18.9 pp over 23 reruns), so all function-calling leaderboard numbers should be read as ranking-level, not point-accurate (source [59]). Rate-limit-specific dollar-per-retry costs for commercial APIs were not located in primary literature; per-task cost anchors do exist but none isolates the retry increment (TCMIIES $0.38–3.41 per 1,000 papers; BFCL full-eval $1–355 per model; both include non-retry spend).

**Established (measured), format side.** Beyond enforcement and repair, the *representation and serving stack* are now measured as first-order reliability variables, not constants. (i) Serialization format of the schema/tool contract: for small models JSON-schema tool definitions are the dominant failure driver (accuracy collapses to 0–49% at >15 tools) and a deterministic JSON→text render recovers 0→84.4% (TSCG, [66]); for inter-agent state, schema-constrained JSON hand-off achieves feasibility 0.96 vs narrative summary 0.48 (relay compression, [74]); for multi-hop relays format effects are tier-dependent — a strong relay is near-lossless in every format (≥0.973 recall after 6 hops) while under a weak relay JSON's fixed-key schema is drift-resistant (retains 0.94 of facts vs 0.74–0.85), yet structure is "faithful, not corrective": injected errors persist 83–100% in every format with no cascade ([77]). Token-level: the *token set* a grammar admits moves classification correlation ~0.5 (real numbers ρ 0.42–0.61 vs integer ρ=−0.16; leading-whitespace tokens +5–10% because LW/non-LW twins are non-exchangeable — Lost in Space, [79]); schema *key wording* alone moves accuracy ±16 pp by model family ([64]); novel formats without native support pay a capacity-dependent correctness cost (TOON GCS 0.513 vs JSON 0.840; zero gap at 70B, near-total failure at 4B, [72]); cross-model format collapse means the same prompt yields clean JSON on GPT-4 but fenced/malformed on Llama (strict-parse ROS 0.116 vs semantic CSS 0.246 for Gemma-2B; PromptPort, [82]); and in small-model *multi-agent pipelines*, JSON as the inter-role contract drops GSM8K 75.0→45.0% while plain text restores 82.0% (Two Calls, [84]). (ii) Serving stack: a routine repetition-penalty sampler setting (θ=1.3) drops schema compliance 97%→23% on 200 real schemas — a gauge-dependent, per-model corruption neither constrained decoding nor retries recover ([73]); diffusion-LLM structured output collapses under stochastic sampling (Dream BFCL-Live 63.9→22.3%) and recovers only under exact FA-constrained decoding ([75]). (iii) Enforcement cost is now effectively solved in the autoregressive case: parser-stack classification gives O(1) vocabulary-independent masks with end-to-end throughput ≈ unconstrained (PSC, 700×/30× mask speedups, [76]), and the grammar-scarcity bottleneck is removable — learned CFGs from execution logs reach 0.91–1.00 precision vs 0.025 for formal induction, enabling GCD for previously-unsupported DSLs (Autogrammar, [85]). (iv) Production fault data confirm these are the dominant real-world failure classes: Data & Validation Errors is the top observable symptom in agentic-AI systems (20.0% of 385 faults across 40 repos) with ~37% of root causes being dependency/type-contract violations ([80]). (v) Retry/refinement economics: sampling diversity saturates (only 1.2→2.5 unique reasoning clusters from N=2→32 on AIME-24) and refining each sampled trajectory (self-critique→self-correct→majority vote, no verifier) beats both plain resampling and verifier-based best-of-N (Qwen2.5-1.5B MATH500 29.6→58.0; [86]); and under tool-environment unreliability, recovery quality beats retry quantity — targeted recovery hints recover more than test-time scaling (ToolBench-X, [81]). (vi) The *enforcement guarantee itself* is approximate: the standard locally-constrained stack (Outlines/XGrammar/OpenAI) is distribution-biased (renormalizing over locally-valid tokens distorts sampling from p(x|constraint)) and can fail validity within a finite token budget — LCD constraint-satisfaction 95.26–99.20% at fixed budgets vs 100% for budget-aware GCD, at 1.08–1.10× unconstrained latency (P-GCD adds probabilistic look-ahead at 3.11–10.2×; [92]) — and the *training side* has its own quantitative cliff: on-policy distillation reward-extrapolation collapses the JSON contract above a closed-form threshold (parse 94.8→65.1→8.5% across λ=1.15→1.50 while ranking quality on parsed outputs stays flat; below-λ a 1.7B matches 8B-SFT at 1/5 the parameters; [89]). (vii) *Deployment structure, not model choice, is the dominant lever*: decomposing a complex workflow-JSON generation task into piecewise stages raises structural success 31.5–82.8% → 74.1–97.8% across six models (4/6 above 90%, zero before; [96]); minimal-diff repair (RFC 6902 patches) matches full regeneration within 5% at 31% fewer tokens (JSON Whisperer, [97]) — the third independent confirmation of selective-repair economics after StepCache/Asthana; and production reflective retry quantifies the cost-benefit: 5.8% trigger rate, 59.1% recovery, +15.9 s P50 per triggered session but only +4.1 s amortized (Melo, [93]). (viii) *Repair mechanics are now measured at the mechanism level*: supplying the error *location* is the dominant lever — attribution-based repair fixes 13/73 GAIA tasks vs 4–6 for decoupled self-correction, and strict agent+step attribution 28.8% vs 21.7% single-pass (AgentDebugX, [91]); procedure-directed retry corrects 84.6% of UNSAT failures where a generic retry corrects 11.5% (Tell-Tale Trace, [95]); a consistency-based abstention filter raises function-calling IDKS 0.342→0.541 (APIGen) at the price of confident-incorrectness blind spots (IDK Filter, [94]); and inference-time FFN gating repairs at ~1.85:1 fixes:harm with model-specific transfer (Amplitude Gating, [90]). (ix) *Aggregate scores can mask per-step damage*: on an error-budgeted agentic benchmark, 4-bit quantization is statistically lossless on the final score yet amplifies tool-name hallucination 2.5× (19.5→38.3%) with unchanged 55% recovery — the budget absorbs the failures (K=10→2 widens the gap 1.3→16.7 pp) — and a validator-feedback repair prompt collapses the channel 38.3→2.9% (+5.9 pp score; [98]); the survey-level prescription is to report cost-per-successful-task, schema-validity rate, and executable-call rate alongside accuracy, with validator-first execution and verifier cascades (SLM survey, [99]).

**What would settle it.** (1) An independent run of the JSONSchemaBench coverage protocol against OpenAI/Anthropic/Gemini structured-outputs endpoints with declared supported subsets reported explicitly, so the vendor "100%"/"no retries" claims are compared against coverage and compliance on the same real-world schemas. (2) A frontier-model pass of the same coverage protocol — already actionable via the lm-eval-harness `jsonschema_bench_easy/medium/hard` tasks and the `epfl-dlab/jsonschemabench-leaderboard`, which report `json_validity` and `schema_compliance` separately for models without constrained decoding. (3) The direct malformed-JSON production gap is now *partly* closed: ScrapeGraphAI-100k gives 93,695 real extraction events with per-example jsonschema-rs labels and quantified complexity thresholds (validity 98→20% at depth ≥7, ~65% at ≥200 keys; [67]), and Palabrita documents on-device JSON-format violation rates with retry/parse fixes (code-fence 20–30%, word-length 10–15%; [70]); production workflow-JSON numbers exist for enterprise platforms (structural success 31.5–97.8% by pipeline architecture, semantic satisfaction ≤55.2%; [96]); what is still missing is the same measurement on *frontier closed models in production* (ScrapeGraphAI is 87.4% GPT-4o-mini; Palabrita is 0.6–2.6B), i.e., retry counts and repair-loop accuracy for malformed/schema-violating JSON with a real JSON-Schema validator as verifier on frontier endpoints. (4) Any verification/certification claim should be read against the CRC feasibility test: with base risk μ above the target α on the task-model pair, *no* verifier or abstention layer can certify the target without abstaining on ≥(μ−α)/(1−α) of outputs (Kotte, source [69]) — so "guaranteed ≤X% error" claims for high-base-risk tasks are only meaningful with an explicitly stated abstention rate. (5) Any aggregate agentic-benchmark number (this report's included) should be read with the error-budget audit in mind: an end-of-episode score with a per-episode error budget can certify a system whose per-step failure rate has halved — report per-channel error rates and success-as-a-function-of-budget alongside the headline score, and where feasible a shrinking-budget counterfactual (Flat Score, Amplified Failures, [98]).
