# What makes a CI verification gate non-vacuous? How do production systems design verifier commands that cannot pass on an empty or wrong target?

## Findings

### A. The term "vacuous" — origin and the transferable definition

1. **Fact** — The formal notion of *vacuity* in verification comes from temporal model checking. Beer, Ben-David, Eisner, and Rodeh "formalize the notions of vacuity and interesting witness, and show how to detect vacuity and generate interesting witnesses in temporal model checking" ("Efficient Detection of Vacuity in Temporal Model Checking", Formal Methods in System Design 18(2):141–163, 2001, DOI 10.1023/A:1008779610539; abstract via Springer link.springer.com/article/10.1023/A:1008779610539 and metadata via Semantic Scholar API `api.semanticscholar.org/graph/v1/paper/DOI:10.1023/A:1008779610539`). The paper body is paywalled and its abstract is elided by the publisher on Semantic Scholar — the exact formal definition (subformula-replacement semantics) could **not** be verified from the sources I reached.
2. **Fact** — A production CI/agent system operationalizes the same idea without model checking: mini-agi's kernel defines a declared verifier as **VACUOUS if it passes on an empty target** and refuses to trust it. Its audit runs the verifier twice — on the known-good `verify_target` ("gold" check) and on an empty temporary directory ("counterfactual" check) — and only reports PASS when the gate accepts the real target **and** rejects the empty one (`crates/mini-agi-core/src/verifier.rs:163–239`). A verifier "that passes an empty directory accepts non-work and is a fake gate" (same file, lines 165–170).
3. **Analysis (opinion)** — Generalizing A1–A2: a gate is vacuous when **its verdict does not depend on the thing it claims to check** — replacing the target (or a subformula of the claim) with an empty/wrong one leaves the verdict unchanged. Non-vacuity = the verdict is *sensitive* to the target.

### B. The counterfactual mechanism: mutation / falsifier

4. **Fact** — Mutation testing is the canonical "inject a fault and require the gate to detect it" technique: "Mutation Testing is a fault-based software testing technique" whose core operation is that deliberately injected faults (mutants) must be **killed** by the test suite; surviving mutants mean the tests failed to detect an injected fault (Jia & Harman, "An Analysis and Survey of the Development of Mutation Testing", IEEE TSE 37(5):649–678, 2011; abstract via ieeexplore.ieee.org/document/5487526, author-hosted PDF at www0.cs.ucl.ac.uk/staff/mharman/tse-mutation-survey.pdf).
5. **Fact** — mini-agi encodes the falsifier as its proof discipline: "1 focused falsifier for one changed runtime contract, migration, authority boundary, parser, or reproduced bug" — a test that fails when the changed behavior is wrong (AGENTS.md, section "Proof and completion"). Its `audit_verifier_vacuous` refuses to trust a verifier it could not test against a counterfactual: if the empty-dir run cannot even be set up or executed, the audit errors rather than trusting the gate (`crates/mini-agi-core/src/verifier.rs:246–278`).

### C. Empty-input footguns in the toolchain (why naive verifiers pass vacuously)

These are documented behaviors of the exact tools CI verifiers are written in:

6. **Fact** — Bash `for` loop: "If there are no items in the expansion of words, no commands are executed, and the return status is zero." A verifier that loops over matched files silently passes with zero iterations (GNU Bash Reference Manual §3.2.5.1 "Looping Constructs", gnu.org/software/bash/manual/bash.html).
7. **Fact** — Bash pipeline exit status without `pipefail`: "the exit status of a pipeline is the exit status of the last command in the pipeline." With `pipefail` enabled it becomes "the value of the last (rightmost) command to exit with a non-zero status" (Bash Reference Manual §3.2.3 "Pipelines"). So `find … | verify` hides a failing/failed middle stage unless `pipefail` is on.
8. **Fact** — Bash `set -e` (errexit) does *not* abort when a failing command "is part of the command list immediately following a `while` or `until` reserved word, part of the test in an `if` statement, part of any command executed in a `&&` or `||` list except the command following the final `&&` or `||`, any command in a pipeline but the last (subject to the state of the `pipefail` shell option)…" (Bash Reference Manual §4.3.1 "The Set Builtin"). A verifier relying on `set -e` alone can therefore exit 0 despite a failed intermediate check.
9. **Fact** — GNU `xargs`: "If the standard input is completely empty, do not run the command. **By default, the command is run once even if there is no input**" (describing `-r`/`--no-run-if-empty`) (GNU Findutils 4.11.0 manual §8.4.1, gnu.org/software/findutils/manual/html_node/xargs-options.html). A gate built as `… | xargs verify` executes its verifier once on an empty input and reports whatever that verifier returns.
10. **Fact** — GNU `find -exec command {} +` / `-execdir`: "The result is always true" — `find`'s exit status does not reflect whether the executed command succeeded (GNU Findutils 4.11.0 manual §3.3.2 "Multiple Files"). A gate ending in such a `find` is green whenever `find` runs.
11. **Fact** — GNU `grep` exit status: "0 if a line is selected, 1 if no lines were selected, and 2 if an error occurred" (GNU Grep 3.12 manual §2.3 "Exit Status", gnu.org/software/grep/manual). This is the *anti*-footgun: `grep -q` as the last stage of a chain **fails on an empty match set**, which is exactly what makes "assert that something exists" gates non-vacuous.
12. **Fact** — `pytest` treats a zero-test run as an error: exit code 5 = "No tests were collected" (pytest docs "Exit codes", docs.pytest.org/en/stable/reference/exit-codes.html).
13. **Fact** — Jest's `--passWithNoTests` flag "Allows the test suite to pass when no files are found" (Jest CLI docs, jestjs.io/docs/cli). **Inference (opinion)** — the flag exists precisely because the default is to *fail* on a test run that finds nothing; opting in recreates the vacuous pass.
14. **Fact** — GNU `make` explicitly supports recipes that do nothing: "It is sometimes useful to define recipes which do nothing. This is done simply by giving a recipe that consists of nothing but whitespace… `target: ;`" (GNU Make manual §5.9 "Using Empty Recipes", gnu.org/software/make/manual/html_node/Empty-Recipes.html).

### D. Production design patterns that cannot pass on an empty or wrong target

15. **Fact** — *Counterfactual audit at gate-authoring time* (mini-agi, this repo): the kernel re-runs the declared `verify_command` in an empty directory before trusting it and requires exit ≠ 0 there; it also requires PASS on the real known-good target (both directions checked in `audit_verifier`, `crates/mini-agi-core/src/verifier.rs:176–239`). The empty-directory counterfactual is wired into iteration, not just a one-off audit (`audit_verifier_vacuous`, lines 246–285).
16. **Fact** — *Require exit 0 AND non-empty output*: mini-agi's gate treats a silent target as a failure — "every target must exit 0 AND produce output; a silent target is a failing target" (`scripts/verify.sh:3–4`), enforced in `step()` which fails if the command's output is empty (`scripts/gate-lib.sh:12`).
17. **Fact** — *Bind the verifier to the specific target and make execution observable*: mini-agi executes `verify_command` via `sh -c` with `current_dir` set to `verify_target` (`crates/mini-agi-core/src/verifier.rs:87–94`) and errors if `verify_target` is not a directory (lines 81–86). It also reports three-way status (`verified` / `disagrees` / `unverified`) so a verifier that contradicts the run's own claim is surfaced, not absorbed (lines 137–148; ADR-0011, `docs/adr/ADR-0011-verifiable-reward-layer.md:18–34`), and treats a hung gate (>120s) as a disagreement rather than a pass (`verifier.rs:24–26, 95–127`).
18. **Fact** — *Platform defaults that propagate mid-pipeline failure*: GitHub Actions runs `run:` steps on Linux/macOS with the default shell `bash -e {0}`, and with `shell: bash` as `bash --noprofile --norc -eo pipefail {0}`; the docs state "fail-fast behavior is enforced using `set -e` for both `sh` and `bash`" and that `-o pipefail` is applied "to enforce early exit from pipelines that generate a non-zero exit status" (GitHub Actions "Workflow syntax for GitHub Actions", `jobs.<job_id>.steps[*].shell` table and "Supported shells" guidance, docs.github.com/en/actions/using-workflows/workflow-syntax-for-github-actions; a container `run` step defaults to `sh`, not `bash`).
19. **Fact** — *Binding the verification to the correct artifact (wrong-target defense) in supply-chain verification*: SLSA v1.0 "Verifying artifacts" prescribes the verifier verify the provenance signature, "verify that statement's `subject` matches the digest of the artifact in question," look up the builder identity against a configured root of trust, and compare `buildType` / `externalParameters` / canonical source repository against expectations — "Any unrecognized `externalParameters` SHOULD cause verification to fail" (SLSA v1.0 spec, slsa.dev/spec/v1.0/verifying-artifacts). This is the "wrong target" analog: verification is bound to a cryptographic digest of the exact artifact, not to a name.
20. **Fact** — *Coverage floors as a weak guard*: `pytest-cov --cov-fail-under MIN` → "Fail if the total coverage is less than MIN" (pytest-cov 7.1.0 docs, pytest-cov.readthedocs.io/en/latest/config.html). **Opinion** — this only bounds *quantity* of execution, not whether the executed code is the code under review; combined with an empty suite it is not a strong non-vacuity guarantee (a coverage threshold cannot detect that the wrong branch was checked out).

## Verdict

**Established.** (1) Vacuity originates in model checking, where the danger is a specification that passes for the wrong reason (Beer et al. 2001); (2) the transferable, operational definition for CI is: **a verifier is vacuous if it passes on an empty or wrong target** — mini-agi enforces this with a gold-pass + empty-counterfactual-fail audit (verifier.rs); (3) the shell toolchain has documented, recurring empty-input holes — bash `for` loops returning 0 on no items, pipelines hiding failures without `pipefail`, `set -e` skipping failures in `&&`/`||`/`if` contexts, `xargs` running once on empty input, `find -exec … +` always-true results, and `make` empty recipes — plus the *guards*: `grep` exit 1 on no match, `pytest` exit 5 on no tests, Jest failing on no tests by default; (4) production defenses that bind the gate to the real target exist: execute in the target directory, require target to exist, require output + exit 0, treat timeouts as failure, propagate pipeline failures (GitHub Actions `bash -e` / `-eo pipefail` defaults), and bind verification to a cryptographic subject digest + builder identity (SLSA).

**Uncertain.** The exact formal subformula-replacement definition of vacuity from Beer et al. could not be quoted — the paper is paywalled and the abstract is publisher-elided; I only verified the paper's title, authorship, venue, and abstract sentence. Mutation testing is cited from its abstract and metadata (Jia & Harman), not from full-text reading.

**What would settle it.** (1) Reading the full Beer et al. FMSD text (via institutional access) to quote the definition of vacuity / interesting witness verbatim; (2) running an experiment: take a set of candidate `verify_command`s, run each against (a) a known-good target, (b) an empty directory, (c) a deliberately corrupted target, and record pass/fail in all three cells — a gate is non-vacuous iff it passes (a) and fails (b) and (c); (3) measuring mutation-kill rates (Jia–Harman methodology) on real gate test-suites to quantify how much of a gate's "pass" is insensitive to injected faults.
