## Findings

### 1. The baseline: naive materialization recomputes everything

- **PostgreSQL** defines a materialized view as a query result stored as a table; `REFRESH MATERIALIZED VIEW` "completely replaces the contents" and "the backing query is executed to provide the new data" — i.e., stock PostgreSQL has no incremental path, only full recomputation. **fact** — PostgreSQL 18 Documentation, `CREATE MATERIALIZED VIEW` / `REFRESH MATERIALIZED VIEW`, https://www.postgresql.org/docs/current/sql-creatematerializedview.html, https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html
- PostgreSQL's `REFRESH MATERIALIZED VIEW CONCURRENTLY` still re-executes the full backing query; the option only avoids locking concurrent readers, requires a plain UNIQUE index covering all rows, and works only when the view is already populated. **fact** — same `REFRESH MATERIALIZED VIEW` doc.

### 2. Mechanism A — capture and replay the delta (change logs / triggers)

- **Oracle**: "Specify `FAST` to indicate the fast refresh method, which performs the refresh according to the changes that have occurred to the master tables. The changes for conventional DML changes are stored in the materialized view log associated with the master table." `COMPLETE` is "implemented by executing the defining query of the materialized view"; `FORCE` (the default) "will perform a fast refresh if one is possible or a complete refresh if fast refresh is not possible." **fact** — Oracle Database SQL Language Reference, `CREATE MATERIALIZED VIEW` (Oracle Database 26), https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/CREATE-MATERIALIZED-VIEW.html
- Oracle fast refresh requires a materialized view log: "If you specify `REFRESH` `FAST`, then the `CREATE` statement will fail unless materialized view logs already exist for the materialized view master tables." Fast refresh is a property of the *definition*, not intent: "When you specify `FAST` refresh at create time, Oracle Database verifies that the materialized view you are creating is eligible for fast refresh." **fact** — same Oracle doc.
- Oracle offers three refresh *timings*: `ON COMMIT` (refresh as part of the commit on a master table, "may increase the time taken to complete the commit"), `ON DEMAND` (manual via `DBMS_MVIEW`, the default), and `ON STATEMENT` (refresh on every DML, only for fast-refreshable star/snowflake views that include the fact table ROWID). **fact** — same Oracle doc.
- Oracle real-time materialized views avoid refreshing at all by combining stored rows with logged changes at query time: "Instead of modifying the materialized view, the optimizer writes a query that combines the existing rows in the materialized view with changes recorded in log files... This is called on-query computation." **fact** — same Oracle doc.
- **pg_ivm** (PostgreSQL extension): "only incremental changes are computed and applied on views rather than recomputing the contents from scratch as `REFRESH MATERIALIZED VIEW` does." It implements immediate maintenance: "materialized views are updated immediately in AFTER triggers when a base table is modified." **fact** — pg_ivm README, https://github.com/sraoss/pg_ivm
- pg_ivm keeps incremental maintenance efficient via an automatically-created unique index (on GROUP BY columns, DISTINCT target list, or base-table primary keys) used as scan keys to locate affected rows: "An appropriate index on IMMV is necessary for efficient IVM because we need to look for tuples to be updated in IMMV." The README's example shows the same single-row update costing ~20.6 s via full refresh vs ~15 ms base-table write for an IMMV. **fact** — pg_ivm README (figures are doc-reported example timings).
- pg_ivm documents the cost crossover: "IVM is not effective when a base table is modified frequently. Also, when a large part of a base table is modified or large data is inserted... the cost of maintenance can be larger than refresh from scratch." **fact** — pg_ivm README.

### 3. Mechanism B — maintain the view as an index over a B-tree, update only affected rows

- **CouchDB** views (incremental MapReduce): "it only runs through all documents once, when you first query your view. If a document is changed, the map function is only run once, to recompute the keys and values for that single document." **fact** — CouchDB Docs, "Guide to Views — Introduction to Views", https://docs.couchdb.org/en/stable/ddocs/views/intro.html
- CouchDB invalidates per-document rows via back-references and batches the replay: "usually multiple documents are updated between view queries. The mechanism... gets applied to all changes in the database since the last time the view was queried in a batch operation." Reduce results are cached in B-tree interior nodes, so range-aggregate queries are answered from cached partial reductions and "recalculating the reduction values for a minimum number of nodes." Changing a view definition invalidates the index: views that change often and share a design document with others "will invalidate those other views' indexes when the design document is written, forcing them all to rebuild from scratch." **fact** — same CouchDB doc.

### 4. Mechanism C — make the view physical storage and let DML maintain it

- **SQL Server**: an indexed view is a view with a unique clustered index; "The view doesn't have to be referenced in the query for the optimizer to consider that view for a substitution," and "When you execute `UPDATE`, `DELETE` or `INSERT` operations... those referenced indexed views have to be updated as well," so DML can degrade significantly. **fact** — Microsoft Learn, "Create Indexed Views", https://learn.microsoft.com/en-us/sql/relational-databases/views/create-indexed-views
- SQL Server indexed views are gated on *determinism and precision*: the definition must be deterministic, and "only precise deterministic expressions can participate in key columns and in `WHERE` or `GROUP BY` clauses"; plus fixed `SET` options, `WITH SCHEMABINDING`, and a restricted SQL dialect (e.g., `AVG` must be expressed via `COUNT_BIG` + `SUM`; `LEFT/RIGHT/FULL OUTER JOIN`, subqueries, `SELECT DISTINCT`, window functions, set operators are excluded). **fact** — same SQL Server doc.

### 5. Mechanism D — batch incremental pipelines over append-only feeds

- **dbt** incremental models: "The first time a model is run, the table is built by transforming *all* rows of source data. On subsequent runs, dbt transforms *only* the rows in your source data that you tell dbt to filter for." The `is_incremental()` macro is true only when the target table already exists, `full-refresh` is not passed, and the model is `materialized='incremental'` — so one SQL definition serves both full and incremental runs. **fact** — dbt docs, "Configure incremental models", https://docs.getdbt.com/docs/build/incremental-models
- The standard filter is a **high-watermark** against the derived table itself: `where event_time >= (select coalesce(max(event_time),'1900-01-01') from {{ this }} )` — new rows only, which suits append-only sources directly. **fact** — dbt docs, same page.
- A `unique_key` turns pure append into upsert semantics (update or ignore on match, insert on new), which is required "to ensure you don't bring in modified records as duplicates"; without it "most adapters will result in `append`-only behavior." `incremental_predicates` push predicates into the merge to limit scans of the existing table. **fact** — dbt docs, same page.
- **When incremental derivation diverges, rebuild**: "If your incremental model logic has changed, the transformations on your new rows of data may diverge from the historical transformations, which are stored in your target table. In this case, you should rebuild your incremental model" via `dbt run --full-refresh`, which drops and rebuilds the table "for all-time." Schema drift is handled either by `on_schema_change` policies or, by default, ignored — the default `ignore` means a removed column makes the run fail and "whenever the logic of your incremental changes, execute a full-refresh run." **fact** — dbt docs, same page.

### 6. Mechanism E — continuous (streaming) incremental maintenance

- **Materialize** distinguishes views (results "recomputed from scratch each time the view is accessed") from indexed views and materialized views, whose "results are persisted in durable storage and, as new data arrives, incrementally updated." Indexed views keep the incrementally-maintained result in cluster-local memory. **fact** — Materialize Docs, "Views" and "CREATE MATERIALIZED VIEW", https://materialize.com/docs/concepts/views/, https://materialize.com/docs/sql/create-materialized-view/
- On restart, Materialize rehydrates materialized views from its own storage layer, not from the upstream sources: "hydration refers to the reconstruction of in-memory state by reading data from Materialize's storage layer; hydration does not require reading data from the upstream system." **fact** — Materialize Docs, "Views".
- **BigQuery** has two materialized-view classes; only *incremental* views avoid full refresh: "BigQuery precomputes materialized views in the background when base tables change. BigQuery automatically adds incremental data changes from base tables to materialized views," whereas non-incremental views are "Every refresh runs the full query." Freshness is served by merging: "BigQuery reads the rest of the data from the materialized view and reads only the changes from the base tables." **fact** — Google Cloud Docs, "Introduction to materialized views", https://cloud.google.com/bigquery/docs/materialized-views-intro
- BigQuery incremental eligibility is strict: incremental views "support a limited set of features"; `AVG`, `ARRAY_AGG`, and `APPROX_COUNT_DISTINCT` results are stored as intermediate *sketches* rather than final values; and a deletion in a base table can force a full refresh (notably for BigLake sources) because the view's partition layout is what permits update-in-place. **fact** — same BigQuery doc.

### 7. The key-state the systems must keep (and the price of the trade)

- To compute aggregates incrementally, systems store auxiliary state beyond the visible columns: pg_ivm adds hidden `__ivm_count__` / `__ivm_count_avg__` / `__ivm_sum_avg__` columns, and recomputes `min`/`max` from base tables when the extreme tuple is deleted (a documented slow path). BigQuery stores `AVG`/`APPROX_COUNT_DISTINCT` as sketches. CouchDB caches partial reduce values in B-tree nodes. **fact** — pg_ivm README; BigQuery intro doc; CouchDB views intro.
- Consistency has a price on the write path: SQL Server "DML query performance can degrade significantly" on tables referenced by indexed views; pg_ivm immediate maintenance slows base-table writes and raises errors in `REPEATABLE READ`/`SERIALIZABLE` for multi-base-table views under concurrent updates; Oracle `ON COMMIT` "may increase the time taken to complete the commit." **fact** — SQL Server, pg_ivm, and Oracle docs respectively.
- Staleness is an explicit knob: BigQuery `max_staleness` (30 minutes to 3 days) bounds how long the derived result may lag; Materialize's reaction time = freshness + latency; Oracle real-time MVs trade stored-freshness for on-query computation; dbt's default is batch staleness bounded by run cadence. **fact** — BigQuery intro doc; Materialize "Reaction Time" concept page referenced from the views doc; Oracle doc. *(The Materialize reaction-time page was not fetched directly; its framing is cited only via the views/concepts pages I did read — treat the reaction-time formula as doc-reported.)*

### 8. Patterns that transfer to regenerating derived documents from append-only sources

Synthesis anchored to the above sources:

1. **Determinism is the enabler of replay.** Oracle query-rewrite eligibility requires all user-defined functions be `DETERMINISTIC`; SQL Server requires deterministic, precise expressions; CouchDB map functions must be "side effect–free." Replaying a log or re-deriving a document is only safe if the derivation function is pure. **fact (the source constraints); opinion (that this is the general principle).**
2. **Keep a durable change/append log and a position (high-watermark).** Oracle MV logs + dbt's `max(event_time)` over `{{ this }}` + CouchDB's changes-since-last-query are the same shape: record what changed, remember where you stopped, apply only the tail. **fact (per-source mechanics); opinion (the common shape).**
3. **Use a key for upsert, not blind append**, so re-applying a delta is idempotent: dbt `unique_key` (merge/delete+insert), pg_ivm's auto unique index used as scan keys, Oracle primary-key/ROWID materialized views, SQL Server's unique clustered index. **fact (per-source mechanics); opinion (generalization).**
4. **Store incremental state next to the output** (hidden aggregate columns, B-tree cached reductions, sketches) — the visible document is not enough to update itself cheaply. **fact + opinion**, as in §7.
5. **Provide an explicit full-rebuild path for when the *logic* changes**, because an incrementally accumulated state diverges from a clean rebuild: dbt `--full-refresh`, Oracle `COMPLETE`/`FORCE`, PostgreSQL `REFRESH` (the only path), CouchDB design-doc invalidation. **fact (per-source); opinion (that this is why a rebuild path is required).**
6. **Bound staleness explicitly** (batch runs, `max_staleness`, on-query merge, `ON COMMIT`), and accept a write/commit-time cost in exchange for lower read latency. **fact + opinion**, as in §7.
7. **Swap or merge in place to keep readers unblocked** (PostgreSQL `REFRESH ... CONCURRENTLY` via unique index, dbt merge / `insert_overwrite`, Materialize replacement views via `CREATE REPLACEMENT MATERIALIZED VIEW ... APPLY REPLACEMENT`). **fact (per-source); opinion (generalization).**

## Verdict

**Established (from primary docs):** Five distinct mechanisms for avoiding full recomputation exist and are well-documented: (1) delta-capture + replay via a change log or triggers (Oracle fast refresh + MV logs, pg_ivm AFTER triggers), (2) index-structured materialization updated per-row/per-changed-document (CouchDB B-tree views), (3) view-as-physical-index maintained by DML (SQL Server indexed views), (4) batch incremental pipelines with high-watermark + upsert keys (dbt), and (5) continuous/streaming maintenance with durable or in-memory storage (Materialize, BigQuery incremental MVs). All require eligibility constraints on the derivation (deterministic, restricted SQL), all keep auxiliary state for incremental correctness, and all expose a full-rebuild escape hatch and an explicit staleness/write-cost tradeoff. For append-only sources, the transferable pattern set is: pure/deterministic derivation, a durable log plus high-watermark position, keyed upsert for idempotent replay, adjacent incremental state, an explicit rebuild path for logic changes, and bounded staleness with in-place swap/merge.

**Uncertain:** Apache Kafka's log-compaction documentation could not be fetched (the site served only a JS redirect) and EventStoreDB's projections docs were unreachable, so the "compacted-topic as derived state" and "projection over an event stream" mechanisms are **not verified here** — do not attribute those claims to primary sources until fetched directly. Oracle and BigQuery figures (refresh times, cost claims) are vendor-reported and unbenchmarked here. Materialize's reaction-time formula and BigQuery's `max_staleness` numeric range come from doc statements, not from measured data.

**What would settle it:** fetching Kafka's "Log Compaction" section (https://kafka.apache.org/43/documentation/ — the site's redirect currently blocks the anchor) and EventStoreDB's projections guide would add primary sources for append-only-log-derived state; a benchmark comparing incremental-maintenance cost vs full refresh across update volume would turn the "when incremental stops paying" claims into measured facts.
