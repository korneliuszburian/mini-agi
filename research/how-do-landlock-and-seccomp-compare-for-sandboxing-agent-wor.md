## Findings

### What each mechanism is

- **Seccomp** is a syscall filter: a BPF program evaluated on `struct seccomp_data` (syscall number, `arch`, `instruction_pointer`, up to 6 raw register arguments) deciding KILL/TRAP/ERRNO/USER_NOTIF/TRACE/LOG/ALLOW. BPF cannot dereference pointers, which the kernel docs credit with making the *filter itself* immune to the TOCTOU problems of syscall interposition frameworks. — *Documentation/userspace-api/seccomp_filter.rst* (https://docs.kernel.org/userspace-api/seccomp_filter.html); *seccomp(2)* man page (https://man7.org/linux/man-pages/man2/seccomp.2.html). [fact]
- **Landlock** is a stackable LSM restricting operations on *objects* (file hierarchies via filesystem access rights; TCP/UDP ports via network access rights since ABI v4/v10; IPC via scope flags since ABI v6), enforced on a thread and its descendants. — *Documentation/userspace-api/landlock.rst* (https://docs.kernel.org/userspace-api/landlock.html); *landlock(7)* (https://man7.org/linux/man-pages/man7/landlock.7.html). [fact]

### How they compare for sandboxing agent workers

- The kernel docs explicitly frame the division of labor: "System call filtering isn't a sandbox… It is meant to be a tool for sandbox developers to use. Beyond that, policy for logical behavior and information flow should be managed with… potentially, an LSM of your choosing." — *seccomp_filter.rst*. [fact] Direct corollary: seccomp alone is insufficient as a worker sandbox; an LSM layer (Landlock is one) is the documented complement. [opinion, derived directly from that statement]
- Seccomp reduces the *kernel syscall surface* but cannot express path/object policy (no pointer deref); Landlock expresses path-based filesystem and port-based network policy but does not filter syscalls at all. — *seccomp_filter.rst*; *landlock.rst*. [fact]
- **Capability gating:** installing a seccomp filter requires `prctl(PR_SET_NO_NEW_PRIVS, 1)` or `CAP_SYS_ADMIN`; Landlock is documented as usable by *unprivileged* processes ("Landlock empowers any process, including unprivileged ones, to securely restrict themselves"). — *seccomp(2)*; *landlock.rst*. [fact]
- **Irreversibility:** both are one-way. Seccomp filters survive `execve` and can only be added to; Landlock: "Once a thread is landlocked, there is no way to remove its security policy; only adding more restrictions is allowed." — *seccomp(2)* ("existing filters will be preserved across a call to execve(2)"); *landlock.rst*. [fact]
- **Compatibility/availability:** Landlock is kernel 5.13+ and opt-in at boot (`lsm=…landlock…`); its API is ABI-versioned (v1..v8+ as of 7.0), and features silently shrink per kernel unless the sandbox layer degrades explicitly. Seccomp BPF is CONFIG-gated (`CONFIG_SECCOMP_FILTER`) and has its own per-arch and kernel-version surface (e.g. the x32 `nr` fix in 5.4). — *landlock(7)* VERSIONS table; *seccomp(2)*. [fact]
- **Repo precedent (context):** this repo's ADR-0012 chose Landlock write-containment for the worker (read+execute on the tree, write confined to workdir/state) over a full namespace sandbox, citing "no root, no user namespaces, no external binary" and the binding risk being filesystem writes rather than network egress. — `docs/adr/ADR-0012-worker-sandbox-landlock.md`. [fact that this is the documented decision; the threat-model ranking ("writes are the real risk") is repo opinion]

### Landlock: documented limits and escape vectors

- **Unmediatable operations:** "It is currently not possible to restrict some file-related actions accessible through these syscall families: `chdir(2)`, `stat(2)`, `flock(2)`, `chmod(2)`, `chown(2)`, `setxattr(2)`, `utime(2)`, `fcntl(2)`, `access(2)`." A worker can still stat/read metadata, chdir, lock, and chmod what it can reach — Landlock does not gate these. — *landlock.rst* (filesystem flags Warning); *landlock(7)* CAVEATS. [fact]
- **Pre-existing file descriptors escape:** "Files or directories opened before the sandboxing are not subject to these restrictions," and such FDs keep their Landlock properties when passed between processes "even when some of the involved processes do not have an enforced Landlock ruleset." A worker that inherits pre-opened writable FDs from its parent retains write access. — *landlock.rst*; *landlock(7)*. [fact]
- **OverlayFS divergence:** a policy restricting an OverlayFS layer "will not restrict the resulted merged hierarchy, and vice versa" — an OverlayFS upper/lower/merge structure is outside the restricted hierarchy from Landlock's point of view. — *landlock.rst*; *landlock(7)*. [fact]
- **Erratum 3 (documented privilege-escalation-class bug):** "it was possible to widen access rights through rename or link actions involving disconnected directories, potentially bypassing `LANDLOCK_ACCESS_FS_REFER` restrictions… could allow privilege escalation in complex mount scenarios." Fixed only on kernels reporting the errata bit. — *landlock.rst* "Erratum 3: Disconnected directory handling". [fact]
- **Network is late and partial:** no network restriction before ABI v4 (kernel 6.7, TCP bind/connect only); UDP added in ABI v10. On older/backported kernels a best-effort policy silently drops network control. IPv4/IPv6 stream sockets that are not TCP (SMC/MPTCP/SCTP) were mis-gated by TCP rights before Erratum 1. — *landlock.rst* (ABI switch, Network flags, Erratum 1); *landlock(7)*. [fact]
- **Thread semantics:** `landlock_restrict_self` restricts the calling thread and descendants; below ABI v8 (and at v8 without `LANDLOCK_RESTRICT_SELF_TSYNC`) a policy "would only be enforced for the calling thread and its children (and not for all threads, including parents and siblings)." A multithreaded worker that restricts one thread can leave sibling threads unconfined. — *landlock.rst* (restrict flags WARNING). [fact]
- **Truncate/ioctl subtleties:** `truncate` is decoupled from `WRITE_FILE` (e.g. `open(O_RDONLY|O_TRUNC)` truncates without the write right); `creat()` needs the truncate right; `fallocate(FALLOC_FL_COLLAPSE_RANGE)` can shorten a writable file "sidestepping the `LANDLOCK_ACCESS_FS_TRUNCATE` right"; several ioctls (FIOCLEX, FIONBIO, FICLONE, FIDEDUPERANGE…) are exempt from `IOCTL_DEV`. — *landlock.rst*. [fact]
- **Scope limits:** `LANDLOCK_SCOPE_*` does not cover everything — a `sendto()` on an already-connected socket is not restricted, and IPC scoping "does not support exceptions." — *landlock.rst*. [fact]
- Landlock does not and cannot filter syscalls or deny syscall-level primitives (e.g. `ptrace` of a peer is mediated via domain-subset rules, but no generic syscall kill). — *landlock.rst* (Ptrace restrictions). [fact + opinion]

### Seccomp: documented escape vectors and limits

- **Not a sandbox by design:** "System call filtering isn't a sandbox"; logical-behavior and information-flow policy must come from elsewhere. — *seccomp_filter.rst* "What it isn't". [fact]
- **Pointer args unfilterable → semantics escape:** BPF "may not dereference pointers," so pathnames, buffers, and most argument *content* are invisible; only register values are visible. — *seccomp_filter.rst*; *seccomp(2)*. [fact]
- **Deny-list bypass:** an allow-list is strongly recommended "because it is often possible to alter the representation of a value without altering its meaning, leading to a deny-list bypass." — *seccomp(2)* (Filters). [fact]
- **Architecture/ABI confusion vectors:** always check `arch`; on x86-64, the x32 ABI shares `AUDIT_ARCH_X86_64` and a policy that does not account for `__X32_SYSCALL_BIT` "can be bypassed by a malicious program that sets __X32_SYSCALL_BIT"; kernels before 5.4 permitted `nr` 512–547 plus x32-ORed forms that could invoke `ptrace` with confused x32-vs-x86_64 semantics. — *seccomp(2)*. [fact]
- **ptrace escape:** "seccomp-based sandboxes MUST NOT allow use of ptrace, even of other sandboxed processes, without extreme care; ptracers can use this mechanism to escape" (`SECCOMP_RET_TRACE` lets a tracer rewrite the syscall, and before 4.8 the check was not re-run after tracer notification). — *seccomp_filter.rst* (SECCOMP_RET_TRACE / Userspace Notification); *seccomp(2)*. [fact]
- **no_new_privs requirement documents the setuid attack:** the filter may be malicious against a setuid program — e.g. making `setuid()` appear to succeed without doing it, tricking a privileged program into keeping superuser privileges — which is why `PR_SET_NO_NEW_PRIVS` (or CAP_SYS_ADMIN) is mandatory. — *seccomp(2)*. [fact]
- **Userspace notification (SECCOMP_RET_USER_NOTIF) reintroduces TOCTOU and is explicitly not a security mechanism:** "the seccomp user-space notification mechanism **can not** be used to implement a security policy"; `SECCOMP_USER_NOTIF_FLAG_CONTINUE` has a time-of-check/time-of-use race because the target can rewrite syscall arguments while blocked; a notifier "can be bypassed if the existing filters allow the use of seccomp(2) or prctl(2) to install a filter" with higher-precedence action. — *seccomp_unotify(2)* (https://man7.org/linux/man-pages/man2/seccomp_unotify.2.html) DESIGN NOTES; *seccomp_filter.rst*. [fact]
- **PID-reuse race in the supervisor path:** the `pid` in `seccomp_notif` can be recycled after the target dies; the documented mitigation is `SECCOMP_IOCTL_NOTIF_ID_VALID` between reading `/proc/tid/mem` and using the bytes, and "a write by the supervisor into the target's memory can never be considered safe." — *seccomp_unotify(2)*. [fact]
- **vDSO / vsyscall bypass and quirks:** syscalls served in userspace (e.g. `clock_gettime`, `gettimeofday`, `time`) never reach seccomp; vsyscall emulation honors seccomp but with documented `TRAP`/`TRACE` oddities. — *seccomp_filter.rst* Caveats; *seccomp(2)* Caveats. [fact]
- **Argument truncation/visibility mismatches:** seccomp sees the full 64-bit registers while the kernel may only consume the low 32 bits (i386-on-x86-64), so filters can misjudge actual semantics. — *seccomp(2)*. [fact]
- **Unknown actions default to kill** (kernel treats unknown action as `SECCOMP_RET_KILL_PROCESS`), so forward-compatibility mistakes tend to fail-safe; filter size caps: `BPF_MAXINSNS` 4096 per program, `MAX_INSNS_PER_PATH` 32768 total. — *seccomp(2)* (ERRORS, GET_ACTION_AVAIL). [fact]

### Complementary use (both)

- Landlock is an LSM layer stacked over DAC/other LSMs; seccomp constrains the syscall surface; the kernel docs place both as composable hardening layers, and inheritance across `clone`/`execve` is analogous for both. Nothing in the primary sources documents a way to combine them into one primitive; each keeps its separate gaps. — *seccomp_filter.rst*; *landlock.rst* (Inheritance). [fact + opinion]

## Verdict

**Established:** Seccomp is a syscall-surface reducer explicitly documented *not* to be a sandbox; Landlock is an object-level access-control LSM. For agent workers, Landlock supplies the path/write containment seccomp structurally cannot (no pointer inspection), while seccomp shrinks the syscall surface Landlock does not touch. Documented, source-verifiable limits: Landlock cannot mediate `chdir/stat/flock/chmod/chown/setxattr/utime/fcntl/access`, is bypassable via pre-opened FDs and OverlayFS merge hierarchies, has per-ABI availability gaps (network only since ABI v4/v10), thread-enforcement gaps below ABI v8, and shipped at least one escalation-class erratum (disconnected-directory `REFER` widening). Seccomp has the ptrace-escape mechanism, deny-list representation bypass, x32/`arch` confusion, vDSO bypass, no_new_privs-setuid rationale, and a user-notification path the kernel docs state must never be used as a security policy (TOCTOU + PID-reuse race).

**Uncertain / not verified:** I could not fetch every CVEs-referencing claim and did not enumerate real-world exploit histories (e.g. seccomp/container breakout CVEs); the above is confined to what the kernel's own docs and man-pages document. Whether a given distribution kernel exposes Landlock at boot (LSM ordering) is host-specific, not answered by these sources. Kernel-doc "future Landlock evolutions" claims (e.g. restricting `chdir/stat/…`) are direction statements, not commitments.

**What would settle open questions:** for the worker threat model, empirical verification on the target host: (a) confirm `CONFIG_SECURITY_LANDLOCK` + LSM ordering and ABI version; (b) test the exact ADR-0012 policy against pre-opened-FD and OverlayFS workdir scenarios; (c) for seccomp, confirm the worker's syscall set is closed (allow-list) and that `ptrace` is denied in-filter — the two named escape paths. All sources were HTML/man pages, fully readable; no PDFs were involved.
