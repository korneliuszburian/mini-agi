## Findings

### 1. Definitions: what production systems mean by each strategy

- **Compaction** — "taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary"; in Claude Code this is implemented by passing the message history to the model to "summarize and compress the most critical details… preserving architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs or messages. The agent can then continue with this compressed context plus the five most recently accessed files." (fact — Anthropic Engineering, *Effective context engineering for AI agents*, Sep 29 2025, https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Claude Code's operational definition: "Automatic summarization of your conversation when the context window approaches its limit. **Older tool outputs are cleared first, then the conversation is summarized.**" (fact — Claude Code Glossary, https://code.claude.com/docs/en/glossary.md)
- **Summarization** — LLM-written prose condensation of messages; in the Anthropic stack it is the engine *inside* compaction, while OpenAI offers it as a distinct cookbook pattern (see §3).
- **Pruning / truncation** — dropping raw transcript items (tool results, old turns, unplayed audio) without replacing them with a summary.

### 2. Compaction in production (Claude Code / Claude Agent SDK / OpenAI Responses)

- **Claude Code / Agent SDK auto-compact**: "When the context window approaches its limit, the SDK automatically compacts the conversation: it summarizes older history to free space, keeping your most recent exchanges and key decisions intact." A `compact_boundary` message is emitted, and a `PreCompact` hook lets you "archive the full transcript before summarizing" — the documented way to keep evidence. (fact — Claude Agent SDK, *How the agent loop works*, https://code.claude.com/docs/en/agent-sdk/agent-loop.md)
- **What survives / what is lost** (fact — Claude Code *Explore the context window*, https://code.claude.com/docs/en/context-window.md; *How Claude Code works*, https://code.claude.com/docs/en/how-claude-code-works.md):
  - The structured summary keeps: "your requests and intent, key technical concepts, files examined or modified with important code snippets, errors and how they were fixed, pending tasks, and current work."
  - It replaces the verbatim conversation: "full tool outputs and intermediate reasoning are gone. Claude can still reference the work but won't have the exact code it read earlier."
  - "Detailed instructions from early in the conversation may be lost. Put persistent rules in CLAUDE.md." Project CLAUDE.md, auto memory, and MCP tools reload after compaction; the skill listing is the one startup item not re-injected.
  - The context-window simulation models the summary at ~12% of the summarized token count — **estimate/illustrative**, not a measurement (the page marks token counts as illustrative).
- **Evidence is not destroyed, only removed from the window**: every session transcript is written to a JSONL file under `~/.claude/projects/` (fact — *How Claude Code works*), and the SDK can mirror transcripts to S3/Redis so any host can resume (fact — *How the agent loop works*). So "losing evidence" here means losing it from model-visible context, not from storage.
- **Prompt-cache economics**: compaction invalidates the cached conversation prefix by design; a warm mid-session `/compact` reads the prefix from cache so it "costs a fraction of what the context size suggests"; `/rewind` (truncating back to an earlier turn) instead reuses an already-cached prefix; after long breaks Claude Code offers "resume from a summary." (fact — Claude Code *How Claude Code uses prompt caching*, https://code.claude.com/docs/en/prompt-caching.md)
- **OpenAI Responses compaction is a different mechanism**: server-side compaction triggered by `context_management: [{type:"compaction", compact_threshold:200000}]`, or the standalone `/responses/compact` endpoint. It returns "an **encrypted compaction item that carries forward key prior state and reasoning into the next run using fewer tokens. It is opaque and not intended to be human-interpretable**," plus "retained items from the previous window"; you must not prune the output. OpenAI's own latency tip: "After appending output items… you can drop items that came before the most recent compaction item," and with `previous_response_id` chaining "do not manually prune." (fact — OpenAI *Compaction* guide, https://developers.openai.com/api/docs/guides/compaction.md). Note the contrast: Anthropic's compaction output is a readable structured summary; OpenAI's is an opaque encrypted state item whose fidelity is unquantified in the doc — **fact** (doc states opacity) + **opinion** (fidelity implications).

### 3. Summarization as its own strategy

- Anthropic frames summarization as the core of compaction and warns: "The art of compaction lies in the selection of what to keep versus what to discard, as **overly aggressive compaction can result in the loss of subtle but critical context**"; guidance is to "Start by maximizing recall to ensure your compaction prompt captures every relevant piece of information from the trace, then iterate to improve precision." (fact — *Effective context engineering for AI agents*)
- Anthropic also treats **tool-result clearing** ("context editing") as "one of the safest lightest touch forms of compaction." (fact — same article; productized as the context editing feature, https://claude.com/blog/context-management)
- **Research on whether summaries retain evidence**: LoCoMo found that "using session summaries as context does not significantly improve the performance despite high recall accuracies, likely due to **loss of information during the conversion of dialogs to summaries**," whereas retrieval of raw observations did help (+5% for top-5 retrieved observations); for event summarization, *incremental* summarization was the strongest condition. (fact — Maharana et al., *Evaluating Very Long-Term Conversational Memory of LLM Agents*, arXiv:2402.17753, https://arxiv.org/abs/2402.17753)
- OpenAI publishes a transcript-summarization example for Realtime sessions (`Context_summarization_with_realtime_api.ipynb` in the first-party `openai-cookbook` repo). (fact — existence/path verified via GitHub API listing; notebook content not read in this pass — see Verdict) https://github.com/openai/openai-cookbook/blob/main/examples/Context_summarization_with_realtime_api.ipynb

### 4. Pruning / truncation

- **Token-window truncation is the default failure mode and is lossy by definition**: "Tokens generated in excess of the context window limit **may be truncated** in API responses." (fact — OpenAI *Conversation state*, https://developers.openai.com/api/docs/guides/conversation-state.md)
- **Prune the low-value layers first**: Claude Code "clears older tool outputs first, then summarizes" (fact — glossary); the platform's **context editing** "automatically clears stale tool calls and results from within the context window when approaching token limits… removing stale content while preserving the conversation flow." (fact — https://claude.com/blog/context-management)
- **Realtime audio truncation has a documented evidence gap**: `conversation.item.truncate` cuts audio at a point and "remove[s] the text transcript for the unplayed portion," and OpenAI states it explicitly does **not** produce a truncated transcript: "This solves the problem of removing unplayed audio but doesn't provide a truncated transcript." (fact — OpenAI *Realtime conversations*, https://platform.openai.com/docs/guides/realtime-conversations)
- **Ordering matters for pruning**: Lost in the Middle found models use beginning and end of context best, "performance is often highest when relevant information occurs at the beginning or end… and significantly degrades when models must access relevant information in the middle." (fact — Liu et al., TACL 2023, https://arxiv.org/abs/2307.03172) This supports production practice of keeping system instructions + most recent turns (pruning the middle) rather than the oldest turns.

### 5. Non-lossy alternatives used in production (retrieval / memory / subagents)

- **Structured note-taking / agentic memory**: "the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times" — the memory tool keeps "key findings… project state across sessions" out of the window. (fact — *Effective context engineering for AI agents*; https://claude.com/blog/context-management)
- **Sub-agent architectures** bound context growth to a summary: a subagent "returns only a condensed, distilled summary of its work (often 1,000–2,000 tokens)" and "the main agent's context grows by that summary, not by the full subtask transcript." (fact — Anthropic article; Claude Agent SDK *agent-loop*)
- **MemGPT** formalized OS-style virtual context management: "intelligently manages different memory tiers… providing extended context within the LLM's limited context window." (fact — Packer et al., *MemGPT: Towards LLMs as Operating Systems*, arXiv:2310.08560, https://arxiv.org/abs/2310.08560)
- **Retrieval/memory beats recursive summarization on a shared benchmark** (as reported by a second research group): "The MemGPT framework currently leads performance metrics with **93.4% accuracy** using gpt-4-turbo, a significant improvement over the **35.3% baseline achieved through recursive summarization**" on the Deep Memory Retrieval (DMR) benchmark; the same paper reports its own system at 94.8% on DMR and gains "up to 18.5%" with ~90% latency reduction on LongMemEval, using a **non-lossy episodic store** underneath. (fact — Rasmussen et al., *Zep: A Temporal Knowledge Graph Architecture for Agent Memory*, arXiv:2501.13956, https://arxiv.org/abs/2501.13956; note this is one vendor's evaluation of MemGPT, not MemGPT's own paper)

### 6. Quality-retention evidence (measured)

- **Anthropic (vendor-internal evals, published in the launch post)**: on an internal agentic-search evaluation, "combining the memory tool with context editing improved performance by **39%** over baseline. Context editing alone delivered a **29%** improvement"; in a 100-turn web-search evaluation, context editing let agents finish workflows "that would otherwise fail due to context exhaustion — while reducing token consumption by **84%**." (fact as published; methodology is internal and not reproducible from the post — see Verdict) https://claude.com/blog/context-management
- **Chroma context rot (18 models, Jul 2025)**: "Across all models, we see significantly higher performance on focused prompts compared to full prompts" on LongMemEval (focused ≈300 tokens vs full ≈113k tokens); distractor effects amplify with length; even "simple" tasks degrade as input grows. (fact — Chroma Technical Report, https://research.trychroma.com/context-rot) — direct support for *pruning irrelevant context rather than growing the window*.
- **Lost in the Middle** (above) and **LoCoMo** (above) both show long-context stuffing degrades recall and that *curation beats brute-force length* — e.g., LoCoMo: gpt-4-turbo scored 32.4 vs human 87.9 on long-context QA, and a 16k-context model fell to 2.1% on adversarial questions while a 4k-context model got 70.2%. (fact — arXiv:2402.17753)

## Verdict

**Established.** Production systems converge on a three-tier answer, and each tier's loss profile is documented by its vendor: (1) *prune the redundant layer first* — drop stale tool outputs/tool results before anything else (Anthropic context editing; Claude Code clears tool outputs first), which vendors measure as net-positive (Anthropic: +29% eval, −84% tokens); (2) *summarize/compact the conversation* into a decision-level summary that keeps intent, key files, decisions, errors, and pending work while discarding verbatim tool outputs and intermediate reasoning (Claude Code/Agent SDK; OpenAI's opaque encrypted compaction item); (3) *move evidence out of the window* rather than destroying it — persisted transcripts (Claude Code JSONL, SDK session stores), note-taking/memory tools, and subagents that return only condensed summaries. Research independently supports curation over stuffing: Chroma's 18-model report (focused ≫ full prompts), Lost-in-the-Middle position effects, and LoCoMo (retrieval of raw observations > full context > session summaries).

**Uncertain / not verifiable from sources reached.**
- Anthropic's +29%/+39%/−84% figures are vendor-internal evals published without methodology or data; treat as claims, not independently reproduced results.
- OpenAI's compaction-item fidelity ("key prior state and reasoning") is asserted but not measured; the item is opaque by design.
- No public apples-to-apples benchmark exists that runs the *same* agent traces through naive truncation vs LLM summarization vs compaction vs retrieval and reports evidence-retention (recall of trace facts) side by side. The Claude Code summary ratio (~12%) is illustrative, not measured.
- The OpenAI Cookbook Realtime summarization notebook was verified by path only; its content was not read.

**What would settle it.** A public, neutral benchmark that (a) takes fixed agent transcripts, (b) applies token-truncation, LLM-summarization, compaction, and retrieval on identical inputs, and (c) measures both downstream task success and a fact-recall metric (as LoCoMo/DMR do) — plus release of the compaction prompt/eval so recall can be checked per the vendor's own "maximize recall, then precision" guidance. Absent that, vendor numbers are directional evidence, not a ranking.
