## Findings

### 1. Purpose and mechanism (fact)

- GitHub describes Actions caching as "caching dependencies and build outputs to improve workflow execution time" — `actions/cache` README, https://github.com/actions/cache
- Restore sequence is exact-match on `key` → partial (prefix) matches of `key` → `restore-keys` sequentially; exact `key` match sets `cache-hit=true`. On a miss the action saves a new cache only if the job completes successfully. — Dependency caching reference, https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/caching-dependencies-to-speed-up-workflows
- Cache identity is (key, cache *version*, branch). The version is a hash of the compression tool (gzip/zstd) plus the cached `path`s; caches with different versions are treated as unique — so the same key with a different `path` or different runner OS is a miss. `actions/cache` README "Cache Version" section, https://github.com/actions/cache (version hash generated in `actions/toolkit` `packages/cache/src/internal/cacheHttpClient.ts`).

### 2. Cache key strategies (fact)

- **Lockfile-hash key**: `key: cache-${{ hashFiles('**/lockfiles') }}` — reuses the same cache until the dependency files change. `caching-strategies.md`, https://github.com/actions/cache/blob/main/caching-strategies.md
- **restore-keys fallback chain** (most → least specific, e.g. `npm-feature-<hash>` then `npm-feature-` then `npm-`): on a miss, the most recently created prefix-matching cache is restored, so "the build/install step will need to additionally fetch just a handful of newer dependencies, and hence saving build time." — `caching-strategies.md`; key-matching docs, https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/caching-dependencies-to-speed-up-workflows#cache-key-matching
- **OS-scoped keys** for matrix builds (`key: ${{ runner.os }}-cache`) separate caches per OS. `caching-strategies.md`.
- **Short-lived keys**: `cache-${{ github.run_id }}-${{ github.run_attempt }}` or `cache-${{ github.sha }}` create specialized, short-lived entries. `caching-strategies.md`.
- **Composite/multi-factor keys**: e.g. `${{ runner.os }}-${{ hashFiles('**/lockfiles') }}`. `caching-strategies.md`.
- **Immutability**: "You cannot change the contents of an existing cache. Instead, you can create a new cache with a new key." To refresh a hit cache, use a run-unique `key` with `restore-keys` — at the cost of a new entry per run against quota. — docs; `tips-and-workarounds.md` "Update a cache", https://github.com/actions/cache/blob/main/tips-and-workarounds.md
- Keys are max 512 characters; longer keys cause the action to fail. — docs.
- `setup-*` actions (setup-node, setup-python, setup-java, setup-go, setup-ruby, setup-dotnet) implement caching with minimal config; setup-node caches the global package cache rather than `node_modules` so it is reusable across Node versions. — docs "setup-* actions"; https://github.com/actions/setup-node/blob/main/docs/advanced-usage.md#caching-packages-data

### 3. Measured build-time benefits and reported numbers (fact vs. estimate)

- **Official figure (estimate, GitHub's own claim):** the cache backend rewrite (v2 service, rolling out from Feb 1 2025) "will decrease the cache upload duration by up to ~80% when using GitHub Hosted Runners. The cache download performance will be the same." Self-hosted uploads "expected to improve, or in the worst-case stay the same." — official deprecation/announcement, https://github.com/actions/cache/discussions/1510 (maintainer post). This is a service-side figure, not an end-to-end job wall-clock number.
- **Compression improvement:** v2 cache actions "increased performance and improved cache sizes using `zstd` for compression for Linux and macOS runners." — GitHub Changelog, https://github.blog/changelog/2020-05-27-github-actions-v2-cache-actions. No numeric claim.
- **No GitHub-published end-to-end build-time reduction numbers exist** in the primary sources I reached (docs, changelog, action/toolkit repos). GitHub's docs state caching "speeds up" / "improves execution time" but publish no measured job-level reduction percentages. The "~80%" upload figure is the only quantified official claim. Widely quoted job-level numbers (e.g. "X% faster CI") come from third-party benchmarks and are **not** verifiable from primary sources — see Verdict.

### 4. Cache-invalidation pitfalls (fact)

- **Scope/branch isolation causes apparent cache misses:** runs can restore caches from the current branch or the default branch (plus PR base branches); a cache created on a non-default branch is *not* accessible from the default branch; caches created for one tag are not restorable for another tag; a PR-triggered cache is stored under the merge ref (`refs/pull/.../merge`) and is restorable only by re-runs of that PR. — docs "Restrictions for accessing a cache". Confirmed in practice in the v4 rollout thread: a user's prefix-restore failed because an entry was uploaded on a temp branch, and tag-triggered runs could not restore branch-scoped caches (actions/cache discussion #1510 replies; issue #1491 "Cache entry from default branch considered out of scope for tag-triggered workflow").
- **Cache Version mismatch = silent miss:** same key but different `path` or different compression tool/OS yields a different version and no hit; cross-OS reuse is opt-in via `enableCrossOsArchive: true`. — `actions/cache` README; `tips-and-workarounds.md` "Cross OS cache".
- **Eviction / quota / thrashing:** entries unused for 7 days are removed; total cache per repo is capped at 10 GB by default (usage above is billed); at the cap, GitHub deletes oldest-accessed caches and warns that this "may cause cache thrashing, where caches are created and deleted at a high frequency." Branch-scoped caches occupy quota even though other scopes cannot use them. — docs "Usage limits and eviction policy"; `tips-and-workarounds.md` "Force deletion of caches". Eviction cadence was every 24 hours and GitHub announced changing it to every hour (Sept 2025), noting "Increasing the frequency of eviction checks could lead to additional cache thrashing." — https://github.blog/changelog/2025-09-29-new-date-for-enforcement-of-cache-eviction-policy. 10 GB per repo was doubled from 5 GB in 2021. — https://github.blog/changelog/2021-11-23-github-actions-cache-size-is-now-increased-to-10gb-per-repository
- **Rate limits:** 200 cache uploads/min and 1,500 downloads/min per repository; exceeding them fails uploads/downloads until the limit resets (`Retry-After` header). — docs; announced in https://github.blog/changelog/2026-01-16-rate-limiting-for-actions-cache-entries
- **Stale restore correctness risk:** a `restore-keys` hit restores the *most recent prefix-matching* cache, which may predate the current lockfile; docs recommend still running the install step on a non-exact hit. — docs "Cache hits and misses"; README "Skipping steps based on cache-hit" ("It is recommended to install missing/updated dependencies in case of a partial key match").
- **Read-only saves don't fail the job:** forked PRs and other low-trust contexts get read-only cache tokens; a denied save logs a warning and continues without saving. — `actions/cache` README "Read-only access"; June 2026 changelog now makes default-branch cache tokens read-only for untrusted triggers (`pull_request_target`, `issue_comment`, fork `workflow_run`), so such workflows lose cache-write benefit unless a trusted `push`/`schedule` workflow maintains the cache. — https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers
- **Cache poisoning (security invalidation):** only `push`, `workflow_dispatch`, `repository_dispatch`, `delete`, `registry_package`, `page_build`, `schedule` may create/overwrite default-branch-scope caches; cache contents are unsigned and "any workflow run that can read a cache may extract its contents … leading to malicious code execution." — docs "Cache access for low-trust workflow triggers" and "Best practices for using caches securely". The deprecation thread references public reports of cache-poisoning attacks against the legacy service (e.g. the Ultralytics incident) as motivation for scrutiny; maintainers acknowledged the concern without confirming mitigations. — discussion #1510 (user comment + maintainer reply, **opinion/claim**).
- **Download reliability:** caches download in segments (now 128 MB, previously 1–2 GB); stuck segments previously hung jobs, fixed by a 10-minute segment download timeout (`SEGMENT_DOWNLOAD_TIMEOUT_MINS`). — `@actions/cache` README, https://github.com/actions/toolkit/tree/main/packages/cache (note: `tips-and-workarounds.md` still shows the older 1 GB/2 GB wording).

## Verdict

**Established (from primary sources):** the matching algorithm and cache identity (key + version + branch), the canonical key strategies (lockfile-hash, restore-keys fallback chains, OS-scoping, run/sha-scoped keys), the immutability rule, the branch/tag/PR scope restrictions, the 7-day + 10 GB (beyond-limit billed) eviction policy and thrashing risk, 200/1,500 per-minute rate limits, read-only cache tokens for untrusted triggers, and the poisoning threat model are all documented facts.

**Official quantified number (estimate):** GitHub claims the new cache service cuts cache **upload duration by up to ~80%** on hosted runners, with download performance unchanged. This is the only official measured figure; it is about the transfer step, not total job time.

**Uncertain / not verifiable:** GitHub publishes no first-party end-to-end job wall-clock reduction percentages. The "X% faster CI" numbers circulating in write-ups are third-party benchmarks, not primary-source measurements. Because I only cite primary sources, I report the ~80% upload claim and explicitly do not repeat any third-party job-level figure as fact.

**What would settle it:** GitHub publishing cache-hit-rate or job-duration metrics in its docs/engineering blog, or a controlled before/after measurement on the same repository (same jobs, cache on vs. off) with the runner-visible `Cache restored from key …` durations in the run log.
