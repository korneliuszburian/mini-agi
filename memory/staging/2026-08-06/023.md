## S-000 (verification)

The formal notion of vacuity in verification originates from temporal model checking: Beer, Ben-David, Eisner, and Rodeh formalize vacuity and interesting witnesses and detect them in temporal model checking ("Efficient Detection of Vacuity in Temporal Model Checking", FMSD 18(2):141-163, 2001, DOI 10.1023/A:1008779610539).

## S-001 (verification)

The exact formal subformula-replacement definition of vacuity from Beer et al. 2001 could not be verified from sources reached (paper paywalled, abstract publisher-elided); only title, authorship, venue, and abstract sentence are verified.

## S-002 (mini-agi)

mini-agi's kernel defines a declared verifier as VACUOUS if it passes on an empty target and refuses to trust it; its audit runs the verifier on the known-good verify_target (gold check) AND on an empty temp directory (counterfactual check), reporting PASS only when the gate accepts the real target and rejects the empty one (crates/mini-agi-core/src/verifier.rs:163-239).

## S-003 (verification)

Opinion: a gate is vacuous when its verdict does not depend on the thing it claims to check; replacing the target with an empty/wrong one leaves the verdict unchanged. Non-vacuity = the verdict is sensitive to the target.

## S-004 (testing)

Mutation testing is the canonical 'inject a fault and require the gate to detect it' technique: deliberately injected faults (mutants) must be killed by the test suite; surviving mutants mean tests failed to detect an injected fault (Jia & Harman, IEEE TSE 37(5):649-678, 2011).

## S-005 (testing)

Mutation testing evidence is cited from abstract and metadata (Jia & Harman 2011), not from full-text reading.

## S-006 (mini-agi)

mini-agi encodes the falsifier as its proof discipline: '1 focused falsifier for one changed runtime contract, migration, authority boundary, parser, or reproduced bug' — a test that fails when the changed behavior is wrong (AGENTS.md).

## S-007 (mini-agi)

mini-agi's audit_verifier_vacuous refuses to trust a verifier it could not test against a counterfactual: if the empty-dir run cannot be set up or executed, the audit errors rather than trusting the gate (crates/mini-agi-core/src/verifier.rs:246-278).

## S-008 (shell-toolchain)

Bash `for` loop: 'If there are no items in the expansion of words, no commands are executed, and the return status is zero.' A verifier that loops over matched files silently passes with zero iterations (GNU Bash Reference Manual §3.2.5.1).

## S-009 (shell-toolchain)

Bash pipeline exit status without pipefail is the exit status of the last command; with pipefail it is the last (rightmost) command to exit non-zero. `find ... | verify` hides a failing middle stage unless pipefail is on (Bash Reference Manual §3.2.3).

## S-010 (shell-toolchain)

Bash `set -e` (errexit) does not abort when a failing command is part of a while/until command list, part of an if test, part of a `&&`/`||` list (except the command following the final one), or any non-last pipeline command. A verifier relying on `set -e` alone can exit 0 despite a failed intermediate check (Bash Reference Manual §4.3.1).

## S-011 (shell-toolchain)

GNU xargs: if standard input is completely empty, by default the command is run once even with no input; `-r`/`--no-run-if-empty` suppresses this. A gate built as `... | xargs verify` executes its verifier once on empty input (GNU Findutils manual §8.4.1).

## S-012 (shell-toolchain)

GNU `find -exec command {} +` / `-execdir`: 'The result is always true' — find's exit status does not reflect whether the executed command succeeded; a gate ending in such a find is green whenever find runs (GNU Findutils manual §3.3.2).

## S-013 (shell-toolchain)

GNU grep exit status: 0 if a line is selected, 1 if no lines selected, 2 on error — the anti-footgun: `grep -q` as the last stage fails on an empty match set, making 'assert something exists' gates non-vacuous (GNU Grep 3.12 manual §2.3).

## S-014 (testing)

pytest treats a zero-test run as an error: exit code 5 = 'No tests were collected' (pytest docs, Exit codes).

## S-015 (testing)

Jest's `--passWithNoTests` flag allows the test suite to pass when no files are found. Inference (opinion): the flag exists because the default is to fail on a test run that finds nothing; opting in recreates the vacuous pass.

## S-016 (shell-toolchain)

GNU make explicitly supports recipes that do nothing: a recipe consisting of nothing but whitespace (`target: ;`) (GNU Make manual §5.9 Empty Recipes).

## S-017 (mini-agi)

mini-agi does counterfactual audit at gate-authoring time: the kernel re-runs the declared verify_command in an empty directory before trusting it and requires exit != 0 there, and also requires PASS on the real known-good target — both directions checked in audit_verifier (crates/mini-agi-core/src/verifier.rs:176-239); the empty-directory counterfactual is wired into iteration (audit_verifier_vacuous, lines 246-285).

## S-018 (mini-agi)

mini-agi's gate treats a silent target as a failure: 'every target must exit 0 AND produce output; a silent target is a failing target' (scripts/verify.sh:3-4), enforced in step() which fails if output is empty (scripts/gate-lib.sh:12).

## S-019 (mini-agi)

mini-agi executes verify_command via `sh -c` with current_dir set to verify_target (crates/mini-agi-core/src/verifier.rs:87-94), errors if verify_target is not a directory (lines 81-86), reports three-way status verified/disagrees/unverified so a verifier contradicting the run's own claim is surfaced (lines 137-148; ADR-0011), and treats a hung gate (>120s) as a disagreement rather than a pass (verifier.rs:24-26, 95-127).

## S-020 (ci)

GitHub Actions runs `run:` steps on Linux/macOS with default shell `bash -e {0}` and `shell: bash` as `bash --noprofile --norc -eo pipefail {0}`; fail-fast is enforced via `set -e` and `-o pipefail`; a container run step defaults to `sh`, not bash (GitHub Actions Workflow syntax).

## S-021 (verification)

SLSA v1.0 verifying-artifacts prescribes verifying the provenance signature, checking the statement's `subject` matches the digest of the artifact in question, looking up builder identity against a configured root of trust, and comparing buildType/externalParameters/canonical source repo against expectations — 'Any unrecognized externalParameters SHOULD cause verification to fail' (slsa.dev/spec/v1.0/verifying-artifacts).

## S-022 (testing)

pytest-cov `--cov-fail-under MIN` fails if total coverage is less than MIN. Opinion: this only bounds quantity of execution, not whether executed code is the code under review; with an empty suite it is not a strong non-vacuity guarantee (a coverage threshold cannot detect that the wrong branch was checked out).

## S-023 (verification)

Established verdict: a verifier is vacuous if it passes on an empty or wrong target; shell toolchain has documented recurring empty-input holes (bash for loops returning 0 on no items, pipelines hiding failures without pipefail, set -e skipping failures in &&/||/if contexts, xargs running once on empty input, find -exec ... + always-true, make empty recipes) plus guards (grep exit 1 on no match, pytest exit 5 on no tests, Jest failing on no tests by default); production defenses bind the gate to the real target (execute in target dir, require target to exist, require output + exit 0, treat timeouts as failure, propagate pipeline failures, bind verification to a cryptographic subject digest + builder identity per SLSA).
