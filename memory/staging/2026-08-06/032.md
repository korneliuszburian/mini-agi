## S-000 (general)

MCP's trust model: clients trust servers they connect to; local MCP servers are trusted like any other installed software and run with the same privileges as the client; the connection decision rests with the user/administrator (SECURITY.md).

## S-001 (general)

In MCP, command execution to launch STDIO servers, server side effects (filesystem, git, DB, network, system commands), resource access, and LLM-driven tool invocation are declared intended behaviors, not reportable vulnerabilities (SECURITY.md).

## S-002 (general)

MCP's stdio transport is not a sandbox; 'one stdio peer can crash, hang, exhaust resources of, or otherwise deny service to the other' is out of scope, and deployments running stdio at reduced privilege own isolation enforcement (SECURITY.md).

## S-003 (general)

MCP in-scope security categories: protocol-level flaws, auth/authz bypasses, SDK implementation bugs, sandbox escapes, session hijacking, token theft/leakage, cross-tenant access (SECURITY.md).

## S-004 (general)

MCP clientInfo/serverInfo are self-reported, unverified, and MUST NOT be used for security decisions (Spec 2026-07-28).

## S-005 (general)

MCP tool annotations MUST be considered untrusted unless they come from trusted servers (Spec 2026-07-28 Tools).

## S-006 (general)

Confused Deputy (OAuth proxy) attack: a proxy with static client ID + dynamic client registration + consent cookies lets an attacker steal an authorization code; mitigations MUST include per-client server-side consent, exact-string redirect_uri validation, cryptographically random single-use state set only after consent, __Host- prefixed Secure/HttpOnly/SameSite=Lax consent cookies, and frame-ancestors CSP / X-Frame-Options DENY (Security Best Practices).

## S-007 (general)

Token passthrough: MCP servers MUST NOT accept tokens not explicitly issued for the MCP server, nor forward them downstream; clients MUST send the RFC 8707 resource parameter and servers MUST validate audience (Security Best Practices, Authorization Security Considerations).

## S-008 (general)

SSRF during OAuth metadata discovery: servers can point resource_metadata/authorization_servers/token endpoints at cloud metadata (169.254.169.254), localhost, or private ranges; mitigations are HTTPS-only (except loopback in dev), blocking private/link-local/loopback ranges (RFC 9728 7.7), egress proxies, and DNS-pinning (Security Best Practices).

## S-009 (general)

State handle hijacking: MCP is stateless and servers mint state handles returned as tool arguments; possession of a state handle MUST NOT be treated as authentication — per-request authorization, user-bound handles (<user_id>:<handle>), secure non-deterministic handles, and expiry are required (Security Best Practices).

## S-010 (general)

Local server compromise mitigations: mandatory pre-execution consent showing the exact untruncated command, sandboxing, least privilege, warning on dangerous patterns (sudo, rm -rf, network ops); prefer stdio or gate HTTP transports behind tokens / restricted unix sockets (Security Best Practices).

## S-011 (general)

OAuth authorization URL validation: servers MUST only allow http/https (https in production), reject dangerous schemes (javascript:/data:/file:), never open URLs via shell, and apply CSP script-src 'self' (Security Best Practices).

## S-012 (general)

Mix-up attacks: iss-based Authorization Response Validation mitigates them; PKCE alone does not prevent the attack because the client transmits the verifier to the attacker's token endpoint (Security Best Practices).

## S-013 (general)

Scope minimization: use progressive least-privilege scope sets, incremental WWW-Authenticate scope step-up challenges, avoid omnibus scopes, and never trust claimed scopes alone — server-side authorization logic required (Security Best Practices).

## S-014 (general)

MCP auth applies to HTTP transports (server SHOULD conform); STDIO implementations SHOULD NOT use the OAuth spec and instead take credentials from the environment; all authorization-server endpoints must be HTTPS, redirect URIs must be localhost or HTTPS, PKCE S256 is MUST, and clients must refuse to proceed if code_challenge_methods_supported is absent (Spec 2026-07-28).

## S-015 (general)

MCP tools: servers MUST validate all tool inputs, implement access controls, rate-limit tool invocations, and sanitize tool outputs; clients SHOULD prompt for confirmation on sensitive operations, show inputs before calling, validate results before passing to the LLM, implement timeouts, and log usage (Spec 2026-07-28 Tools).

## S-016 (general)

MCP human-in-the-loop: for trust & safety and security there SHOULD always be a human in the loop able to deny tool invocations, with visible tools and confirmation prompts (Spec 2026-07-28 Tools).

## S-017 (general)

MCP tools list MUST NOT vary per-connection or as a side effect of other requests, but MAY vary by the authorization presented on the request (scope-filtered capability exposure) (Spec 2026-07-28 Tools).

## S-018 (general)

MCP JSON Schema $ref resolution must not auto-dereference network URIs by default; composition keywords can be a DoS vector needing depth/sub-schema/time bounds (Spec 2026-07-28).

## S-019 (general)

MCP x-mcp-header (tool params mirrored into HTTP headers) must use token-safe names and primitive types and be rejected if malformed; servers SHOULD NOT mark secrets/PII since header values are visible to intermediaries (Spec 2026-07-28 Tools).

## S-020 (general)

MCP icon URIs/bytes are untrusted: reject unsafe schemes, fetch without credentials, same-origin checks, magic-byte MIME validation, resource-exhaustion limits (SVG can contain embedded JS) (Spec 2026-07-28).

## S-021 (general)

MCP design principle: 'Servers should not be able to read the whole conversation, nor see into other servers'; the host enforces security boundaries and isolation between servers (Spec 2026-07-28 Architecture).

## S-022 (general)

TS SDK CVE-2026-25536 (GHSA-345p-7cg4-v4c7, high, CVSS 7.1): reusing a StreamableHTTPServerTransport or single McpServer across clients causes JSON-RPC ID-collision response misrouting / cross-client data leak (CWE-362); patched in 1.26.0.

## S-023 (general)

TS SDK CVE-2026-0621 (GHSA-cqwc-fm46-7fff, high): ReDoS in UriTemplate.partToRegExp() on exploded array patterns ({/id*}, {?tags*}) -> 100% CPU / DoS via resources/read (CWE-1333); patched in 1.25.2.

## S-024 (general)

TS SDK CVE-2025-66414 (GHSA-w48q-cv73-mx4w, high): DNS-rebinding protection disabled by default for HTTP servers on localhost (CWE-1188); patched in 1.24.0.

## S-025 (general)

Python SDK CVE-2026-52870 (GHSA-hvrp-rf83-w775, CVSS 7.6): experimental tasks feature lets any client read/cancel other clients' tasks (CWE-862); patched in 1.27.2.

## S-026 (general)

Python SDK CVE-2026-52869 (GHSA-jpw9-pfvf-9f58, CVSS 7.1): SSE/Streamable HTTP session routing without principal verification — anyone knowing a session ID can inject on it (CWE-639); patched in 1.27.2.

## S-027 (general)

Python SDK CVE-2026-59950 (GHSA-vj7q-gjh5-988w): deprecated WebSocket transport had no Host/Origin validation (CWE-346/CWE-1385), so cross-origin pages could drive the server; patched in 1.28.1.

## S-028 (general)

Python SDK CVE-2025-66416 (GHSA-9h52-p55h-vw2f): DNS-rebinding protection disabled by default (CWE-1188); patched in 1.23.0.

## S-029 (general)

Python SDK CVE-2025-53366 (GHSA-3qhf-m339-9g5v, CVSS 8.7) and CVE-2025-53365 (GHSA-j975-95f5-7wqh, CVSS 8.7): unhandled exceptions lead to server crash / DoS; patched in 1.9.4 and 1.10.0.

## S-030 (general)

Rust SDK (rmcp) CVE-2026-42559 (GHSA-89vp-x53w-74fx, CVSS 8.8): Streamable HTTP server did not validate Host -> DNS-rebinding attack against loopback servers (CWE-346/CWE-350); patched in 1.4.0.

## S-031 (general)

Rust SDK (rmcp) CVE-2026-63128 (GHSA-9pj6-vhgr-3mwh, CVSS 7.5): unauthenticated session-table memory leak -> permanent DoS (~75 GB/day at 2k req/s) (CWE-400/401/772); patched in 2.0.0.

## S-032 (general)

Rust SDK (rmcp) CVE-2026-63127 (GHSA-33f5-2c5q-wgwj, CVSS 8.2): missing OAuth Protected Resource resource validation lets a malicious server redirect the flow to a legitimate AS and steal tokens; patched in 2.0.0.

## S-033 (general)

Rust SDK (rmcp) CVE-2026-64684 (GHSA-9g45-5xwm-f3wc): custom headers (e.g., X-API-Key) forwarded to cross-origin redirect targets (CWE-200); patched in 2.1.0.

## S-034 (general)

Rust SDK (rmcp) GHSA-c9xm-49cp-xcr9 (no CVE listed): OAuth client fetches server-controlled resource_metadata= URLs without origin/private-network validation -> SSRF (CWE-918); patched in 2.0.0.

## S-035 (general)

Official MCP Registry moderation is permissively scoped: it removes only illegal content, malware, spam, and non-functioning servers; it won't remove servers with security vulnerabilities, and consumers should assume minimal-to-no moderation (registry moderation-policy).

## S-036 (general)

Reference servers in modelcontextprotocol/servers are not production-ready solutions; developers should evaluate their own security requirements (servers README).

## S-037 (general)

SEP-1024 (Final, Standards Track) mandates for one-click local MCP server installation: a consent dialog showing the exact untruncated command, explicit affirmative approval, and a cancel path (motivated by silent command execution, lack of visibility, arbitrary code execution via crafted configs).

## S-038 (general)

'Breaking the Protocol' (arXiv 2601.17549) reports three architectural MCP weaknesses — absence of capability attestation, bidirectional sampling without origin authentication (enables server-side prompt injection), implicit trust propagation across multi-server configs — and measures that MCP's design amplifies attack success by 23–41% versus non-MCP integrations; a proposed MCPSec extension cuts measured success from 52.8% to 12.4% (study-produced estimates).

## S-039 (general)

Two studies of 7 MCP clients (Claude Desktop, Claude Code, Cursor, Cline, Continue, Gemini CLI, Langflow) identify tool poisoning (malicious instructions embedded in tool metadata/descriptions) as the most prevalent client-side vector, with wide disparities (Claude Desktop 'implements strong guardrails', Cursor 'exhibits high susceptibility to cross-tool poisoning') (reported; arXiv 2603.21642, 2603.22489).

## S-040 (general)

MPMA (arXiv 2505.11154) documents a Preference Manipulation Attack: a customized MCP server inserts manipulative words into tool names/descriptions to make the LLM prefer it; a genetic-algorithm variant (GAPMA) adds stealth.

## S-041 (general)

MCP-38 (arXiv 2603.18063) defines a 38-category MCP threat taxonomy (tool-description poisoning, indirect prompt injection, parasitic tool chaining, dynamic trust violations) mapped to STRIDE and OWASP LLM/Agentic frameworks; a companion SoK (arXiv 2512.08290) systematizes indirect prompt injection and tool poisoning and surveys defenses (cryptographic provenance, runtime intent verification).

## S-042 (general)

MCP-Guard (arXiv 2508.10991) reports a multi-stage detection pipeline with 96.01% accuracy on adversarial prompts and the MCP-ATTACKBENCH benchmark of 70,448 samples (study-reported).

## S-043 (general)

A measurement study of 6 MCP marketplaces (arXiv 2509.25292, 8,060 servers) found more than half of listed projects invalid or low-value, plus dependency-monoculture and maintenance risks (study-reported).

## S-044 (general)

An empirical MCPApps study (arXiv 2607.25635, 1,723 apps) found only 37.2% gate tool execution behind a blocking approval step, leaving the LLM able to invoke any enabled tool unconditionally in most apps (study-reported).

## S-045 (general)

Synthesis (opinion): safe MCP capability exposure = advertise capabilities conservatively and filter tools by request authorization/scopes; isolate servers so each cannot see the conversation or other servers; validate all tool inputs server-side and sanitize outputs; keep a human in the loop with denial ability and clear indicators; least-privilege progressive scopes with step-up challenges; treat all tool metadata/annotations/icons/results as untrusted; sandbox server processes with consent before launch; enforce audience-bound tokens, per-request auth, and per-client instance isolation.

## S-046 (general)

Established (material verdict): MCP documents its trust model and out-of-scope items (SECURITY.md); the spec and Security Best Practices mandate concrete mitigations for confused-deputy, token passthrough/audience, SSRF, state-handle hijacking, local-server compromise, OAuth URL scheme validation, mix-up, and scope-minimization attacks; the registry does not moderate for vulnerabilities; the three official SDKs have 14+ published GHSAs/CVEs (2025–2026) covering cross-client data leaks, DNS-rebinding, ReDoS/DoS, session-principal bypass, header leakage, OAuth metadata token theft, and SSRF.

## S-047 (general)

Uncertain (material verdict): (1) how widely mandated client mitigations are implemented — measurement studies indicate a majority of MCP apps still let the LLM invoke tools without blocking approval; (2) whether 'Breaking the Protocol' arguments (capability attestation, sampling origin authentication) are accepted by MCP maintainers or addressed in-spec; (3) patch status of third-party (non-official) servers/clients is out of scope and unknown.
