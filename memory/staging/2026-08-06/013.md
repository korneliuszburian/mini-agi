## S-000 (general)

OPA keeps policy/data (the enforcement input) in a replaceable data document while decision logs are a separate stream; decision-log events include the policy queried, the input, and bundle metadata, enabling auditing and offline debugging of policy decisions. (Fact)

## S-001 (general)

Vault audit devices record all API requests and responses in detail, distinct from server logs; disabling a device immediately stops writing but leaves the existing log information untouched. (Fact)

## S-002 (general)

Akka: the journal (event log) is the history; the snapshot store is separate and exists only to optimize recovery. (Fact)

## S-003 (general)

Rekor (sigstore) trails are verifiable logs where consolidation is forbidden: the log remains append-only and entries are never mutated or removed. (Fact)

## S-004 (general)

Akka snapshots are point-in-time copies of state; recovery initializes from the latest saved snapshot then replays events after it; incoming commands are stashed until the snapshot is saved, so the snapshot is internally consistent. (Fact)

## S-005 (general)

Akka explicitly documents that deleting events loses the history of how the system changed before reaching current state (one of the main reasons for event sourcing); snapshot-is-optional=true is unsafe if events have been deleted because it would result in wrong recovered state. (Fact)

## S-006 (general)

RocksDB compaction uses CompactionIterator, which is aware of all snapshots and preserves the data visible to each snapshot; a snapshot captures a point-in-time view of the DB at creation. (Fact)

## S-007 (general)

RocksDB compaction eliminates superseded key versions: a version of a key in L0 must be newer than versions of that same key in all levels below L0. (Fact)

## S-008 (general)

OPA distributes policy/data as immutable signed bundles; a new snapshot bundle erases and overwrites all policy and data in its cache before activation (scoped to declared roots); activation is gated on signature verification — on failure OPA continues using its existing bundle and reports an activation failure; the REST API prevents modifying policy and data loaded via bundles. (Fact)

## S-009 (general)

OPA delta bundles rewrite data incrementally via JSON Patch (upsert/replace/remove) applied in order to the in-memory store; patch failure fails the whole activation; an empty patch list removes all data. (Fact)

## S-010 (general)

OPA docs warn that with multiple bundle sources there are no ordering guarantees for which bundle loads first and takes over a root; if multiple bundles conflict OPA may go into an error state. (Fact)

## S-011 (general)

OPA decision-log events carry bundles[_].revision (the revision of the bundle at evaluation time) and a per-decision decision_id, enabling a past decision to be replayed/audited against the policy revision in force even after that revision was erased from live memory. (Fact)

## S-012 (general)

Vault refuses to service an API request if audit devices are enabled and it cannot log to at least one enabled device; audit data is confidentiality-protected via keyed HMAC-SHA256 hashes by default. (Fact)

## S-013 (general)

Kafka's log.cleanup.policy=compact enables log compaction, which retains the latest value for each key; with delete,compact old segments are dropped by retention while retained segments are compacted — consolidation that deliberately discards history for the keyed-state use case. (Fact, cited from the generated topic-config reference; the long-form 'Log Compaction' prose was not reached as primary text)

## S-014 (general)

RocksDB's compaction_filter allows an application to modify/delete a key-value during background compaction. (Fact)

## S-015 (general)

Synthesis (opinion): across OPA, RocksDB, Akka, Vault, Kafka and Rekor the consistent pattern appears to be (1) the trail is never the thing being consolidated — it is append-only and either kept immutable or hash-chained; (2) consolidation targets derived state, built as snapshots or latest-value compactions; (3) enforcement correctness during the rewrite is guaranteed by snapshot pinning or atomic version activation (readers see old-or-new, never torn); (4) auditability of past decisions is preserved by recording the policy revision alongside each decision. (Opinion, not established)
