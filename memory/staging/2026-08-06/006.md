## S-000 (agent-memory)

Two consolidation regimes exist in published agent-memory systems: batch/scheduled (Generative Agents, MemGPT, Letta) and continuous background (Zep/Graphiti, Mem0, A-MEM) [S1]-[S7].

## S-001 (agent-memory)

No system in the surveyed sources uses a literal 'nightly cron'; 'nightly' is approximated by daily-frequency batch reflection (Generative Agents) and idle-time scheduled consolidation (Letta sleep-time compute); continuous background consolidation is approximated by per-event incremental ingestion (Zep/Graphiti, Mem0, A-MEM).

## S-002 (agent-memory)

Generative Agents (Stanford 2023) batch-reflection triggers when the sum of importance scores for latest events exceeds a threshold of 150; agents reflected roughly 2-3 times per day [S4].

## S-003 (agent-memory)

Generative Agents ablation (TrueSkill): no-reflection scored mu=26.88 (sigma=0.69), no-reflection-and-no-planning mu=25.64 (sigma=0.68), crowdworker baseline mu=22.95, no-memory/no-reflection/no-planning mu=21.21; full architecture vs no-memory baseline gives Cohen's d=8.16; authors concluded 'each of these components is critical to strong performance' [S4].

## S-004 (agent-memory)

MemGPT runs timed events on a regular schedule, allowing it to run 'unprompted' without user intervention; on memory pressure (warning at ~70% of context) the agent self-edits working/archival memory; at flush (~100%) it evicts ~50% of the window and generates a new recursive summary from the existing recursive summary and evicted messages [S1].

## S-005 (agent-memory)

MemGPT DMR accuracy was 93.4% (GPT-4 Turbo + MemGPT) vs 35.3% (recursive summarization alone); MemGPT reports no separate consolidation cost figures [S1].

## S-006 (agent-memory)

Letta sleep-time compute (2025) is the closest published analogue to 'nightly' consolidation: an idle-time batch process where a sleep-time agent owns the memory-edit tools and rewrites the primary agent's in-context memory blocks; frequency is configurable, with higher frequency using more tokens [S3].

## S-007 (agent-memory)

Letta paper reports sleep-time compute can reduce test-time compute needed for the same accuracy by ~5x on Stateful GSM-Symbolic and Stateful AIME, increase accuracy by up to 13% on Stateful GSM-Symbolic and 18% on Stateful AIME, and decrease average cost per query by 2.5x on Multi-Query GSM-Symbolic [S2].

## S-008 (agent-memory)

Zep/Graphiti design rationale: continuous incremental (dynamic community) updates significantly reduce latency and LLM inference costs but their community quality gradually diverges from a full label-propagation run, so 'periodic community refreshes remain necessary' [S5].

## S-009 (agent-memory)

Zep/Graphiti (2025) performs per-message incremental ingestion: each episode triggers entity extraction (with prior n=4 messages for context), entity resolution, fact extraction, deduplication, temporal extraction, and LLM-based edge invalidation on contradictions; 'Graphiti consistently prioritizes new information' [S5].

## S-010 (agent-memory)

Zep vs full-context baseline on LongMemEval (~115k token conversations): accuracy +15.2% (gpt-4o-mini) and +18.5% (gpt-4o); latency 31.3s -> 3.20s and 28.9s -> 2.58s (~90% reduction); context tokens 115k -> 1.6k [S5].

## S-011 (agent-memory)

Zep caveats reported in its own paper: on DMR Zep scored 94.8% vs MemGPT 93.4%, but the full-conversation baseline scored 94.4% (gpt-4-turbo) and 98.0% (gpt-4o-mini), so the DMR gap is within noise; Zep declined on single-session-assistant questions (-17.7% gpt-4o, -9.06% gpt-4o-mini) [S5].

## S-012 (agent-memory)

Mem0 (2025) performs incremental consolidation at write time (per message pair) plus an async background summarization module that periodically refreshes the conversation summary independently of the main pipeline; per candidate fact the LLM chooses ADD/UPDATE/DELETE/NOOP [S6].

## S-013 (agent-memory)

Mem0 cost vs full-context on LOCOMO: full-context p95 latency ~17.1s (p50 9.87s); Mem0 p50 0.708s/p95 1.440s; graph variant p50 1.091s/p95 2.590s; paper claims '91% lower p95 latency and saves more than 90% token cost' vs full-context [S6].

## S-014 (agent-memory)

Mem0^g reached the highest LLM-judge score among memory systems (J~68.4 overall) with '26% relative improvements in the LLM-as-a-Judge metric over OpenAI' [S6].

## S-015 (agent-memory)

On LOCOMO open-domain questions Zep beat Mem0 (J 76.60 vs 72.93), a cross-vendor result, not a batch-vs-continuous one [S6].

## S-016 (agent-memory)

A-MEM (2025) performs per-interaction continuous evolution: each new interaction triggers note construction (LLM keywords/tags/context), top-k link generation, and 'memory evolution' that rewrites the contextual representation of existing memories [S7].

## S-017 (agent-memory)

A-MEM cost: ~1,200 tokens per memory operation, 85-93% token reduction vs baseline methods (LoCoMo and MemGPT with 16,900 tokens); under $0.0003 per operation; 5.4 seconds using GPT-4o-mini and 1.1 seconds with locally-hosted Llama 3.2 1B; retrieval scales to 1M memories at 3.70 microseconds with linear storage; DialSim F1 3.45 vs LoCoMo 2.55 and MemGPT 1.18 [S7].

## S-018 (agent-memory)

No published batch-vs-continuous head-to-head exists: all measured quality/cost differences are within-system comparisons against full-context or RAG baselines; none of [S1]-[S7] reports the same system under both nightly-batch and continuous consolidation.

## S-019 (agent-memory)

Opinion: the closest evidence for the nightly-batch vs continuous trade-off is Zep's own design claim that continuous dynamic extension trades graph quality (periodic refresh needed) for latency/LLM cost [S5].

## S-020 (agent-memory)

Uncertain: (a) no source reports a controlled comparison of nightly-batch vs continuous consolidation on the same system; (b) cost accounting is incomparable across papers (tokens vs latency vs USD, different benchmarks/models); (c) 'nightly' as such is not used by any source — closest are '~2-3 times a day' [S4] and configurable idle-time [S3].

## S-021 (agent-memory)

The study that would settle batch-vs-continuous (a controlled ablation running one system under per-event vs daily-batch consolidation on a fixed benchmark with identical token/latency metering, scored on a staleness-sensitive benchmark) does not yet exist in the surveyed sources [S1]-[S7].
