## S-000 (general)

GitHub routes code review requests to specific people/teams and gives each reviewer a filterable 'awaiting your review' list; each PR is decided with one of three discrete outcomes: Comment, Approve, Request changes.

## S-001 (general)

GitLab shows an approval-state icon on each merge request in the project/group MR list ('required approvals missing' vs 'approvals satisfied') and a widget on the MR showing per-reviewer state (Awaiting review / In progress / Approved / Commented / Requested changes); an eligible reviewer approves from the widget or via the '/approve' quick action.

## S-002 (general)

Stripe Radar presents a review queue ('a prioritized list of completed or to-be-captured payments') in two modes: a list view to scan without opening details, and a detailed view with customizable risk context; operators navigate with J/K keys or Previous/Next buttons and act on each item (Approve / Refund / Refund-and-report-fraud).

## S-003 (general)

AWS CodePipeline's Manual approval action stops a stage; approvers see it in the console with an optional review URL, comments, and an SNS notification when it is ready.

## S-004 (general)

Google Cloud Deploy shows a Review link in the delivery-pipeline visualization when a rollout is pending approval; each pending rollout opens an Approve rollout screen with a Manifest diff tab showing exactly what changed versus the current deploy, then Approve or Reject (console or 'gcloud deploy rollouts approve|reject').

## S-005 (general)

Azure Pipelines' ManualValidation@0 task pauses a YAML pipeline and shows a message bar linking to a Manual validation dialog containing the 'instructions'; users with Queue-builds permission choose resume or reject.

## S-006 (general)

Spinnaker's Manual Judgment pipeline stage waits for the user to click Continue, with optional instructions and user-selectable input options that drive downstream pipeline behavior.

## S-007 (general)

LaunchDarkly delivers approval requests to an Approvals dashboard, email, and in-app inbox, plus per-object 'Pending changes' panels and Slack/Teams notifications.

## S-008 (general)

Amazon A2I presents review tasks to a configured work team (internal workforce, Mechanical Turk, or AWS-prescreened vendors) when a flow-definition condition fires; the work team sees items via a human task UI, and results land in S3 with CloudWatch Events on completion.

## S-009 (general)

GitHub code review auto assignment picks reviewers by one of two algorithms: round robin (who has received the least recent request) or load balance (counts recent and outstanding reviews, aiming for an equal number per member within any 30-day period); members whose status is 'Busy' are excluded.

## S-010 (general)

GitLab's Automatic reviewer assignment assigns CODEOWNERS automatically; the GitLab Duo Agent Platform strategy chooses the minimum number of reviewers needed to satisfy each approval rule, weighing availability, review workload (open MRs awaiting their review), local time, and recency of activity.

## S-011 (general)

A peer-reviewed field study of 1,112 parole rulings by experienced judges found the share of favorable rulings fell from ≈65% to near zero within each decision session and jumped back to ≈65% after a break; the authors argue the depletion comes from the act of deciding, not elapsed time (Danziger, Levav & Avnaim-Pesso, PNAS 108(17):6889-6892, 2011). The observational result is the fact; the causal 'mental depletion' interpretation is the authors' and is contested in later literature.

## S-012 (general)

Stripe's stated best practice is to focus reviewer time on payments where human judgment adds insight and let automation decide the majority, and to avoid adding a review step where no inherent fulfillment delay exists because it becomes a bottleneck for good customers (vendor guidance, not measured evidence).

## S-013 (general)

AWS A2I human-review loops fire on confidence-range conditions (e.g., review a label when its confidence is below X or above Y) or on random sampling of a percentage of items; thresholds are adjustable over time.

## S-014 (general)

Stripe Radar lets operators write rules that automatically place payments into review and provides Smart Refunds recommendations ranked by refund-confidence, so operators triage a ranked list rather than scan everything.

## S-015 (general)

If a customer disputes a payment already in Stripe's review queue, the review is automatically closed.

## S-016 (general)

Azure Manual Validation defaults onTimeout to reject (reject or auto-resume after a configured timeout, up to 30 days), so a stalled approval cannot silently hold a deployment.

## S-017 (general)

GitLab auto-approves approval rules that are impossible to satisfy (e.g., zero eligible approvers) so MRs are not blocked forever, except for policy-created rules, which instead block the MR and show 'Action required.'

## S-018 (general)

LaunchDarkly lets Enterprise accounts require approvals only for specific environments (e.g., prod but not dev), with per-role review permissions.

## S-019 (general)

AWS restricts who may update an approval via IAM identities.

## S-020 (general)

Stripe's review queue is prioritized and filterable (e.g., 'Smart Refunds' quick filter for high/very-high fraud-likelihood; 'my reviews' vs 'unassigned'), with a dense list view for rapid scanning and a keyboard-driven detail view.

## S-021 (general)

Stripe reviewers assign themselves to reviews, see who is working what, and filter to unassigned or owned items; assignment changes are recorded in the review timeline.

## S-022 (general)

Verified systems do not ship a 'bulk approve everything' action; batch efficiency comes from batching which items enter review (rules, thresholds, random-sampling percentages) and batching recommendations (ranked lists); each high-risk decision still requires per-item review with a diff (e.g., Cloud Deploy manifest diff, AWS review URL + comments).

## S-023 (general)

Cloud Deploy publishes approval-required notifications to the 'clouddeploy-approvals' Pub/Sub topic so an external workflow system (e.g., ServiceNow) can approve or reject rollouts via the API, enabling bulk/policy-driven approvals outside the human console.

## S-024 (general)

Stripe's review timeline shows a complete history of assignment changes and other actions, and the API emits 'review.opened' / 'review.closed' events with the close reason.

## S-025 (general)

Every Cloud Deploy ApproveRollout (and RejectRollout/advance/cancel/rollback) produces an Admin Activity audit log entry, queryable in Cloud Logging by 'protoPayload.methodName'; the docs enumerate which methods are Admin Activity vs Data Access and which IAM permission type each requires.

## S-026 (general)

Cloud Deploy records a rejected rollout with state APPROVAL_REJECTED, and a rejected rollout can't be approved later unless re-promoted.

## S-027 (general)

GitLab records who approved and shows per-reviewer state on the MR; GitHub keeps review conversations in the pull request timeline so the team can track feedback and decisions; GitLab freezes existing MRs against later approval-rule changes (rule overrides do not apply retroactively).

## S-028 (general)

Amazon A2I writes every review outcome to the flow definition's S3 output path and notifies CloudWatch Events on completion; DescribeHumanLoop returns the loop's outcome.

## S-029 (general)

Uncertain: no vendor publishes controlled evaluations proving that any specific approval feature (e.g., load-balancing routing) measurably reduces errors or approval latency — fatigue-mitigation claims are product design rationale, not measured outcomes.
