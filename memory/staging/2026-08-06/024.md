## S-000 (general)

WAL central invariant (PostgreSQL 18): changes to data files must be written only after WAL records describing them have been flushed to permanent storage; recovery is roll-forward (REDO).

## S-001 (general)

SQLite WAL inverts the rollback journal: changes append to a separate -wal file, a COMMIT can happen without writing to the original database, and the commit becomes durable when the commit record is appended and (per the synchronous setting) synced.

## S-002 (general)

MongoDB/WiredTiger recovery procedure: find last checkpoint ID in data files, find matching record in journal, apply journal operations since the last checkpoint; journaling is required to recover info after the last checkpoint.

## S-003 (general)

Journal durability is a knob, not on/off: WiredTiger buffers records in memory (up to 128 kB) and syncs on j:true, on the 100 ms commit interval, and when a journal file is cut (~100 MB); updates in buffers can be lost on hard shutdown — fsync timing, not just append, defines the recovery point.

## S-004 (general)

RocksDB default contract: process crash consistency by flushing the WAL after every user write; a single WAL spans all column families and is only deleted once all column families have flushed beyond the largest sequence number contained in the WAL; recovery replays the WAL to rebuild the memtable.

## S-005 (general)

LevelDB log format (canonical physical format RocksDB inherited): records split into 32 KB blocks with per-record CRC32C checksums and FULL/FIRST/MIDDLE/LAST framing, so on corruption recovery can skip to the next block boundary.

## S-006 (general)

Even mature WALs have crash-consistency bugs: SQLite's WAL-reset bug (present 3.7.0–3.51.2, fixed 3.51.3) is a data race where a second checkpoint can wrongly mark part of a reset WAL as already checkpointed, corrupting the database; the fix required instrumentation to reproduce. WAL correctness is subtle and version-dependent.

## S-007 (general)

Checkpoint is the mechanism that converts a WAL into a bounded recovery window; SQLite runs it automatically at 1000 pages and requires syncs: WAL synced before moving content into the DB, and DB file synced before resetting the WAL.

## S-008 (general)

WiredTiger creates checkpoints every 60 seconds; the previous checkpoint stays valid while a new one is written, so recovery returns to the last valid checkpoint even if the process dies mid-checkpoint; the new checkpoint is permanent only when the metadata table is atomically updated to reference it.

## S-009 (general)

RocksDB Checkpoint API: consistent snapshot by hard-linking SST files (same filesystem), copying MANIFEST/CURRENT, and copying log files covering the checkpoint start/end to provide consistency across column families.

## S-010 (general)

Raft makes snapshotting load-bearing for catch-up: etcd --snapshot-count (default 100,000 since v3.2) persists snapshot data then truncates old entries; when a slow follower requests logs before a compacted index, the leader sends the snapshot forcing the follower to overwrite its state.

## S-011 (general)

Compaction discards history and changes the failure model: revisions prior to the compaction revision become inaccessible; after compaction only a periodic snapshot restores the keyspace.

## S-012 (general)

etcd recovery is snapshot-first: etcdctl snapshot save then etcdutl snapshot restore builds fresh data directories; all members must restore the same snapshot; restore overwrites member/cluster ID metadata and must start a new logical cluster; restoring from the raw member/snap/db file may lose data not yet written but present in the wal folder.

## S-013 (general)

etcd file-level split: member/snap/db (bbolt) stores applied data plus a consistent_index marker of the last applied WAL entry; member/wal/*.wal is append-only Raft WAL (recent accepted transactions, periodic snapshots, CRC records); the entire Raft state is recoverable from the WAL alone, and recovery only trusts entries up to the committed hard state since entries with index > HardState.commit are subject to change.

## S-014 (general)

Hybrid snapshot + WAL replay is the standard disaster-recovery recipe (PostgreSQL PITR): restore a filesystem backup then replay from backed-up WAL files; the base backup need not be an instantaneous snapshot (inconsistency is repaired by replay), and stopping replay early gives point-in-time recovery.

## S-015 (general)

Estimate: snapshot frequency bounds recovery time (replay length) and storage cost (archived WAL/old snapshots); no source gives universal numbers — the etcd example snapshot of 2.1 MB for 7 keys/rev 10 is illustrative, not a rule; choose checkpoint interval per write volume and RTO/RPO.

## S-016 (general)

Fowler's Event Sourcing: all changes to application state are stored as a sequence of events, enabling complete rebuild by re-running events on an empty application, plus temporal query and event replay; explicitly paired with snapshots (replay from an overnight snapshot on crash).

## S-017 (general)

Event sourcing replay re-runs side effects, so external systems must be wrapped with a Gateway that can detect replay mode and suppress outbound calls — the same problem durable-execution platforms solve with idempotency.

## S-018 (general)

Temporal's durable execution is event sourcing in disguise: the workflow sends Commands mapped to Events persisted to a complete durable log; on worker crash, the worker uses the Event History to replay the code and recreate the workflow state as it was immediately before the crash.

## S-019 (general)

Temporal Durable Execution: a workflow maintains its state and progress across failures, crashes, or server outages because the Event History records state at each step and the execution resumes from the last recorded event.

## S-020 (general)

LangGraph uses a checkpointer that saves a snapshot of graph state at each super-step, organized into threads; if nodes fail at a super-step, the graph can be restarted from the last successful step.

## S-021 (general)

LangGraph durability is tunable: "exit" persists only when execution exits (mid-run crash loses state), "async" persists while the next step executes (small risk of no checkpoint if the process crashes), "sync" persists synchronously before the next step starts — an explicit durability-vs-throughput trade mirroring WAL synchronous settings.

## S-022 (general)

LangGraph separates full snapshots from finer-grained writes: per-node pending writes are written durably within a super-step so successful nodes are not re-run on resume, while time-travel/replay resumes only at full super-step checkpoints — snapshot-restore plus per-task delta.

## S-023 (general)

LangGraph documents an unbounded-growth failure mode: over long conversations checkpoints accumulate, increasing latency and storage costs; the fix is pruning or a retention policy (equivalent to compaction), and DeltaChannel stores deltas instead of full values to bound checkpoint size.

## S-024 (general)

AWS Step Functions: Standard workflows are durable and exactly-once with execution state persisting between transitions and full history retrievable; Express workflows are at-least-once (async) or at-most-once (sync) with no state persistence between transitions; retrying on at-least-once requires idempotent actions.

## S-025 (general)

The three approaches (WAL+checkpoint, snapshot-restore, event sourcing) are one family, not alternatives: every credible system (PostgreSQL, SQLite, WiredTiger/MongoDB, RocksDB, etcd/Raft, Temporal, LangGraph, AWS Step Functions) combines an append-only, checksummed, order-preserving log with periodic state snapshots that bound replay.

## S-026 (general)

Opinion (sourced inference, not a measured study): the selector for agents is which failure you must survive and at what cost — WAL+checkpoint gives strongest crash consistency and minimal replay but needs a storage-engine contract and is overkill for small agent state; snapshot-restore is simplest with a bounded recovery window but loses everything since the last snapshot unless combined with a log (RPO = snapshot interval); event sourcing enables exact resume, audit, time travel, and human-in-the-loop review at the cost of side-effect duplication, unbounded history requiring compaction/pruning, and schema/version evolution of events.

## S-027 (general)

Uncertain, not established from these sources: no primary source quantifies end-to-end failure-recovery success rates, RTO/RPO for arbitrary agent workloads, or a cost model for choosing among the three approaches; the WAL-reset bug shows latent-corruption risk exists even in the most battle-tested implementation, and nothing in these docs proves any engine's recovery is correct under every crash point.

## S-028 (general)

A claim that a failure was recovered is only as good as its verifier: this repo's AGENTS.md requires run verify to actually execute the declared verify_command before an outcome is trusted — no external source substitutes for executing a recovery path on your own system.

## S-029 (general)

What would settle the open questions: (a) a crash-injection fault-injection harness run against each candidate with asserted post-crash invariants; (b) measured RPO per configuration; (c) replay-cost curves for agent-sized state; (d) a verifier that executes a restored snapshot plus replay and asserts the agent's state equals a reference trajectory.
