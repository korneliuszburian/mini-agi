## S-000 (general)

Anthropic prices per input/output token at per-1M-token rates per model, with a per-token 'cache write'/'cache read' cost structure for prompt caching (Cache hit/miss pricing on the Models overview; per-1M rates on the Pricing page).

## S-001 (general)

OpenAI publishes per-model pricing per 1M tokens on its Pricing page; its models endpoint returns token metadata (input_tokens_per_output_token capacity ratios) but not prices.

## S-002 (general)

Both Anthropic and OpenAI bill input and output tokens at different rates, so a budget/forecast must model input and output token volumes as separate random variables.

## S-003 (general)

The OpenAI API returns actual spend via usage.prompt_tokens and usage.completion_tokens in each response; tiktoken is the deterministic local estimator for token counting.

## S-004 (general)

Anthropic returns usage.input_tokens and output_tokens in every message response; prompt caching is metered separately as cache_creation_input_tokens / cache_read_input_tokens.

## S-005 (general)

Real spend per response comes from vendor usage objects; most production stacks forward them to tracing platforms (LangSmith, Langfuse, Helicone), whose cost figures are derived from vendor usage objects, not primary meter sources. (industry-observed pattern/opinion)

## S-006 (general)

The MCP spec has no token-metering field: mcp_usage (2025-03-26 / 2025-06-18 spec) carries opaque total_tokens counters only — no input/output split and no cost — so agent frameworks cannot reliably cost MCP tool calls without sampling tool payloads themselves.

## S-007 (general)

Anthropic states 'you cannot get the exact token count of a string from the API without calling the model' and recommends local count approximation; tiktoken is the canonical local estimator. These are deterministic estimators, not forecasts (cost = rate × counts).

## S-008 (general)

The most common production approach is retrospective billing/estimation from actual per-response usage, not prediction; forecasting a future workload decomposes into (a) expected # calls per unit time, (b) expected input tokens per call (often from observed prompt-size distributions), (c) expected output tokens per call (harder; some use OpenAI capacity hints as an upper bound). The decomposition is standard practice; 'most common' prevalence is opinion/industry observation.

## S-009 (general)

Anthropic Admin API exposes budget history and current spend (BudgetHistory) for spend-threshold alerts; OpenAI usage/billing endpoints set hard/soft limits — these are enforcement primitives, not predictive models.

## S-010 (general)

OpenAI lets you set a hard spend limit that rejects requests over budget; Anthropic has BudgetAlert notifications on threshold crossing, while hard blocking requires an org limit.

## S-011 (general)

Both vendors return 429 with Retry-After on rate-limit overrun and officially recommend exponential backoff; this handles throughput overruns but does not stop cost overruns.

## S-012 (general)

Per-call cost cutoffs are application-level: OpenAI Responses API supports max_output_tokens and Anthropic Messages API has max_tokens, both truncating output to bound per-call cost.

## S-013 (general)

No vendor-side 'agent budget' exists: no primary Anthropic/OpenAI doc defines a per-agent budget object; agent-loop cost containment is model-level max_tokens plus loop-level budget checks, with per-call and per-org limits as the primitives.

## S-014 (general)

Unverified: whether any vendor or major production system publishes a predictive workload→token-cost model beyond the token-counts×rates decomposition and OpenAI model capacity ratios — none found in primary sources.

## S-015 (general)

Unverified: no primary source defines an industry-standard 'token budget' schema for agents.

## S-016 (general)

Established: cost = input-rate×input-tokens + output-rate×output-tokens; per-response usage objects from Anthropic and OpenAI are the source of truth for actual spend; local estimators (tiktoken, Anthropic token counting) are deterministic converters, not predictors; overrun control primitives are per-call max_tokens/max_output_tokens, hard/soft org spend limits, budget alerts, and 429/Retry-After backoff; MCP carries opaque total_tokens only.

## S-017 (general)

The 'decompose into call count × input-token distribution × output-token distribution' heuristic is standard in the industry but could not be cited to a primary source stating it as a method — labeled industry-observed opinion. (would be settled by primary vendor docs or open-source codebases like LangSmith/Langfuse/Helicone/LiteLLM exposing actual forecast formulas)
