## S-000 (general)

GitHub's actions/cache caches dependencies and build outputs to improve workflow execution time.

## S-001 (general)

GitHub Actions cache restore sequence is exact-match on `key` first, then partial (prefix) matches of `key`, then `restore-keys` sequentially; an exact `key` match sets cache-hit=true. On a miss the action saves a new cache only if the job completes successfully.

## S-002 (general)

GitHub Actions cache identity is (key, cache version, branch); the version is a hash of the compression tool (gzip/zstd) plus the cached paths, so the same key with a different path or different runner OS is a miss.

## S-003 (general)

The lockfile-hash cache key (`key: cache-${{ hashFiles('**/lockfiles') }}`) reuses the same cache until the dependency files change.

## S-004 (general)

A restore-keys fallback chain (most to least specific, e.g. `npm-feature-<hash>` then `npm-feature-` then `npm-`) restores the most recently created prefix-matching cache on a miss, so the build/install step fetches only a handful of newer dependencies.

## S-005 (general)

OS-scoped keys (e.g. `key: ${{ runner.os }}-cache`) separate caches per OS for matrix builds.

## S-006 (general)

Short-lived keys such as `cache-${{ github.run_id }}-${{ github.run_attempt }}` or `cache-${{ github.sha }}` create specialized, short-lived cache entries.

## S-007 (general)

Composite/multi-factor cache keys such as `${{ runner.os }}-${{ hashFiles('**/lockfiles') }}` are a documented strategy.

## S-008 (general)

GitHub Actions caches are immutable: you cannot change the contents of an existing cache, only create a new cache with a new key; to refresh a hit cache use a run-unique key with restore-keys, at the cost of a new entry per run against quota.

## S-009 (general)

GitHub Actions cache keys are max 512 characters; longer keys cause the action to fail.

## S-010 (general)

setup-* actions (setup-node, setup-python, setup-java, setup-go, setup-ruby, setup-dotnet) implement caching with minimal config; setup-node caches the global package cache rather than node_modules so it is reusable across Node versions.

## S-011 (general)

GitHub claims the cache backend rewrite (v2 service, rolling out from Feb 1 2025) 'will decrease the cache upload duration by up to ~80% when using GitHub Hosted Runners', with download performance unchanged; self-hosted uploads 'expected to improve, or in the worst-case stay the same'. This is a service-side figure, not an end-to-end job wall-clock number.

## S-012 (general)

GitHub v2 cache actions use zstd compression for Linux and macOS runners, increasing performance and improving cache sizes; no numeric claim is attached.

## S-013 (general)

GitHub publishes no first-party end-to-end job wall-clock build-time reduction percentages; widely quoted 'X% faster CI' job-level figures are third-party benchmarks and are not verifiable from primary sources.

## S-014 (general)

GitHub Actions caches are scope-isolated: runs restore from the current branch or the default branch (plus PR base branches); a cache created on a non-default branch is not accessible from the default branch; caches created for one tag are not restorable for another tag; PR-triggered caches are stored under the merge ref (`refs/pull/.../merge`) and restorable only by re-runs of that PR.

## S-015 (general)

A Cache Version mismatch causes a silent cache miss: same key but different path, compression tool, or OS yields a different version; cross-OS reuse is opt-in via `enableCrossOsArchive: true`.

## S-016 (general)

GitHub Actions cache eviction: entries unused for 7 days are removed; total cache per repo is capped at 10 GB by default (usage above is billed) and at the cap GitHub deletes oldest-accessed caches, warning this may cause cache thrashing; branch-scoped caches occupy quota even though other scopes cannot use them.

## S-017 (general)

GitHub announced (Sept 2025) changing cache eviction checks from every 24 hours to every hour, noting increased eviction frequency could lead to additional cache thrashing.

## S-018 (general)

The 10 GB per-repository Actions cache limit was doubled from 5 GB in 2021.

## S-019 (general)

GitHub Actions cache rate limits are 200 uploads/min and 1,500 downloads/min per repository; exceeding them fails uploads/downloads until the limit resets, signaled via the Retry-After header.

## S-020 (general)

A restore-keys hit restores the most recent prefix-matching cache, which may predate the current lockfile; docs recommend still running the install step on a non-exact hit.

## S-021 (general)

Read-only cache saves do not fail the job: in low-trust contexts a denied save logs a warning and continues without saving; since June 2026 default-branch cache tokens are read-only for untrusted triggers (pull_request_target, issue_comment, fork workflow_run), so such workflows lose cache-write benefit unless a trusted push/schedule workflow maintains the cache.

## S-022 (general)

Cache poisoning threat model: only push, workflow_dispatch, repository_dispatch, delete, registry_package, page_build, and schedule may create/overwrite default-branch-scope caches; cache contents are unsigned and any workflow run that can read a cache may extract its contents, leading to malicious code execution.

## S-023 (general)

Public reports of cache-poisoning attacks against the legacy Actions cache service (e.g. the Ultralytics incident) were cited in the deprecation thread as motivation for scrutiny; maintainers acknowledged the concern without confirming mitigations — opinion/claim, not confirmed fact.

## S-024 (general)

Actions cache downloads are segmented (now 128 MB, previously 1-2 GB); stuck segments previously hung jobs, fixed by a 10-minute segment download timeout (SEGMENT_DOWNLOAD_TIMEOUT_MINS).
