## S-000 (general)

Seccomp is a syscall filter: a BPF program evaluated on struct seccomp_data (syscall number, arch, instruction_pointer, up to 6 raw register arguments) deciding KILL/TRAP/ERRNO/USER_NOTIF/TRACE/LOG/ALLOW. BPF cannot dereference pointers, which kernel docs credit with making the filter itself immune to the TOCTOU problems of syscall interposition frameworks (source: seccomp_filter.rst, seccomp(2)).

## S-001 (general)

Landlock is a stackable LSM restricting operations on objects (file hierarchies via filesystem access rights; TCP/UDP ports via network access rights since ABI v4/v10; IPC via scope flags since ABI v6), enforced on a thread and its descendants (source: landlock.rst, landlock(7)).

## S-002 (general)

Kernel docs state: 'System call filtering isn't a sandbox... It is meant to be a tool for sandbox developers to use. Beyond that, policy for logical behavior and information flow should be managed with... potentially, an LSM of your choosing.' Direct corollary: seccomp alone is insufficient as a worker sandbox; an LSM layer (Landlock is one) is the documented complement (opinion derived directly from that statement).

## S-003 (general)

Seccomp reduces the kernel syscall surface but cannot express path/object policy (no pointer deref); Landlock expresses path-based filesystem and port-based network policy but does not filter syscalls at all.

## S-004 (general)

Capability gating: installing a seccomp filter requires prctl(PR_SET_NO_NEW_PRIVS, 1) or CAP_SYS_ADMIN; Landlock is documented as usable by unprivileged processes ('Landlock empowers any process, including unprivileged ones, to securely restrict themselves').

## S-005 (general)

Both seccomp and Landlock are one-way/irreversible: seccomp filters survive execve and can only be added to; Landlock: 'Once a thread is landlocked, there is no way to remove its security policy; only adding more restrictions is allowed.'

## S-006 (general)

Landlock is kernel 5.13+ and opt-in at boot (lsm=...landlock...); its API is ABI-versioned (v1..v8+ as of 7.0), and features silently shrink per kernel unless the sandbox layer degrades explicitly. Seccomp BPF is CONFIG-gated (CONFIG_SECCOMP_FILTER) and has per-arch and kernel-version surface (e.g. the x32 nr fix in 5.4).

## S-007 (general)

This repo's ADR-0012 chose Landlock write-containment for the worker (read+execute on the tree, write confined to workdir/state) over a full namespace sandbox, citing 'no root, no user namespaces, no external binary' and the binding risk being filesystem writes rather than network egress. The threat-model ranking ('writes are the real risk') is repo opinion.

## S-008 (general)

Landlock unmediatable operations: 'It is currently not possible to restrict some file-related actions accessible through these syscall families: chdir(2), stat(2), flock(2), chmod(2), chown(2), setxattr(2), utime(2), fcntl(2), access(2).' A worker can still stat/read metadata, chdir, lock, and chmod what it can reach.

## S-009 (general)

Landlock pre-existing FD escape: 'Files or directories opened before the sandboxing are not subject to these restrictions,' and such FDs keep their Landlock properties when passed between processes 'even when some of the involved processes do not have an enforced Landlock ruleset.' A worker that inherits pre-opened writable FDs from its parent retains write access.

## S-010 (general)

Landlock OverlayFS divergence: a policy restricting an OverlayFS layer 'will not restrict the resulted merged hierarchy, and vice versa' — an OverlayFS upper/lower/merge structure is outside the restricted hierarchy from Landlock's point of view.

## S-011 (general)

Landlock Erratum 3 (documented privilege-escalation-class bug): 'it was possible to widen access rights through rename or link actions involving disconnected directories, potentially bypassing LANDLOCK_ACCESS_FS_REFER restrictions... could allow privilege escalation in complex mount scenarios.' Fixed only on kernels reporting the errata bit.

## S-012 (general)

Landlock network support is late and partial: no network restriction before ABI v4 (kernel 6.7, TCP bind/connect only); UDP added in ABI v10. On older/backported kernels a best-effort policy silently drops network control. IPv4/IPv6 stream sockets that are not TCP (SMC/MPTCP/SCTP) were mis-gated by TCP rights before Erratum 1.

## S-013 (general)

Landlock thread semantics: landlock_restrict_self restricts the calling thread and descendants; below ABI v8 (and at v8 without LANDLOCK_RESTRICT_SELF_TSYNC) a policy 'would only be enforced for the calling thread and its children (and not for all threads, including parents and siblings).' A multithreaded worker that restricts one thread can leave sibling threads unconfined.

## S-014 (general)

Landlock truncate/ioctl subtleties: truncate is decoupled from WRITE_FILE (e.g. open(O_RDONLY|O_TRUNC) truncates without the write right); creat() needs the truncate right; fallocate(FALLOC_FL_COLLAPSE_RANGE) can shorten a writable file 'sidestepping the LANDLOCK_ACCESS_FS_TRUNCATE right'; several ioctls (FIOCLEX, FIONBIO, FICLONE, FIDEDUPERANGE...) are exempt from IOCTL_DEV.

## S-015 (general)

Landlock scope limits: LANDLOCK_SCOPE_* does not cover everything — a sendto() on an already-connected socket is not restricted, and IPC scoping 'does not support exceptions.'

## S-016 (general)

Landlock does not and cannot filter syscalls or deny syscall-level primitives (e.g. ptrace of a peer is mediated via domain-subset rules, but no generic syscall kill).

## S-017 (general)

Seccomp: BPF 'may not dereference pointers,' so pathnames, buffers, and most argument content are invisible; only register values are visible.

## S-018 (general)

Seccomp deny-list bypass: an allow-list is strongly recommended 'because it is often possible to alter the representation of a value without altering its meaning, leading to a deny-list bypass.'

## S-019 (general)

Seccomp architecture/ABI confusion vectors: always check arch; on x86-64, the x32 ABI shares AUDIT_ARCH_X86_64 and a policy that does not account for __X32_SYSCALL_BIT 'can be bypassed by a malicious program that sets __X32_SYSCALL_BIT'; kernels before 5.4 permitted nr 512-547 plus x32-ORed forms that could invoke ptrace with confused x32-vs-x86_64 semantics.

## S-020 (general)

Seccomp ptrace escape: 'seccomp-based sandboxes MUST NOT allow use of ptrace, even of other sandboxed processes, without extreme care; ptracers can use this mechanism to escape' (SECCOMP_RET_TRACE lets a tracer rewrite the syscall, and before 4.8 the check was not re-run after tracer notification).

## S-021 (general)

Seccomp no_new_privs requirement documents the setuid attack: the filter may be malicious against a setuid program — e.g. making setuid() appear to succeed without doing it, tricking a privileged program into keeping superuser privileges — which is why PR_SET_NO_NEW_PRIVS (or CAP_SYS_ADMIN) is mandatory.

## S-022 (general)

Seccomp userspace notification (SECCOMP_RET_USER_NOTIF) reintroduces TOCTOU and is explicitly not a security mechanism: 'the seccomp user-space notification mechanism can not be used to implement a security policy'; SECCOMP_USER_NOTIF_FLAG_CONTINUE has a time-of-check/time-of-use race because the target can rewrite syscall arguments while blocked; a notifier 'can be bypassed if the existing filters allow the use of seccomp(2) or prctl(2) to install a filter' with higher-precedence action.

## S-023 (general)

Seccomp PID-reuse race in the supervisor path: the pid in seccomp_notif can be recycled after the target dies; the documented mitigation is SECCOMP_IOCTL_NOTIF_ID_VALID between reading /proc/tid/mem and using the bytes, and 'a write by the supervisor into the target's memory can never be considered safe.'

## S-024 (general)

Seccomp vDSO/vsyscall bypass and quirks: syscalls served in userspace (e.g. clock_gettime, gettimeofday, time) never reach seccomp; vsyscall emulation honors seccomp but with documented TRAP/TRACE oddities.

## S-025 (general)

Seccomp argument truncation/visibility mismatches: seccomp sees the full 64-bit registers while the kernel may only consume the low 32 bits (i386-on-x86-64), so filters can misjudge actual semantics.

## S-026 (general)

Seccomp unknown actions default to kill (kernel treats unknown action as SECCOMP_RET_KILL_PROCESS), so forward-compatibility mistakes tend to fail-safe; filter size caps: BPF_MAXINSNS 4096 per program, MAX_INSNS_PER_PATH 32768 total.

## S-027 (general)

Landlock is an LSM layer stacked over DAC/other LSMs; seccomp constrains the syscall surface; kernel docs place both as composable hardening layers, and inheritance across clone/execve is analogous for both. Nothing in the primary sources documents a way to combine them into one primitive; each keeps its separate gaps.

## S-028 (general)

Unverified: whether a given distribution kernel exposes Landlock at boot (LSM ordering) is host-specific, not answered by the documented sources. Kernel-doc 'future Landlock evolutions' claims (e.g. restricting chdir/stat/...) are direction statements, not commitments.

## S-029 (general)

Unverified: no enumeration of real-world exploit histories (e.g. seccomp/container breakout CVEs) was done; findings confined to what the kernel's own docs and man-pages document.
