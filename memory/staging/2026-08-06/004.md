## S-000 (general)

SQLite allows multiple processes to do SELECT at the same time, but only one process can make changes to the database at any moment; it uses reader/writer locks and writers lock the whole database file during their update; on lock conflict the default is SQLITE_BUSY, adjustable via a busy handler/timeout.

## S-001 (general)

SQLite supports an unlimited number of simultaneous readers but only one writer at any instant; the explicit guidance for many concurrent writers is to choose a client/server DBMS.

## S-002 (general)

SQLite defines five lock states (UNLOCKED/SHARED/RESERVED/PENDING/EXCLUSIVE) for rollback mode, including writer-starvation avoidance via PENDING locks.

## S-003 (general)

SQLite WAL mode lets readers and writers proceed concurrently, but since there is only one WAL file there can only be one writer at a time.

## S-004 (general)

SQLite WAL does not work over a network filesystem; all processes using a database must be on the same host computer because the wal-index lives in a shared-memory mmap.

## S-005 (general)

The SQLite wal-index is backed by a file mmapped in the same directory as the database; processes with a different root directory (via chroot) will see different files and use different shared memory areas, leading to database corruption — a chroot'd sandbox worker cannot reliably share a WAL-mode store on the same filesystem path.

## S-006 (general)

Even in WAL mode SQLite queries can return SQLITE_BUSY: when another connection holds exclusive locking mode, while the last connection does close/cleanup, or while the first connection after a crash holds the recovery lock.

## S-007 (general)

SQLite checkpoint starvation: if concurrent overlapping readers mean there is always at least one active reader, checkpoints never complete and the WAL grows without bound, causing excess disk use and slow queries.

## S-008 (general)

The SQLite WAL-reset corruption bug only affects WAL-mode databases with two or more connections open on the same file in separate threads or processes that attempt to write or checkpoint at the same instant; it is present in all versions 3.7.0–3.51.2, fixed in 3.51.3 (2026-03-13), and rare with low probability.

## S-009 (general)

SQLite rollback mode gives atomic commit via a rollback journal; a 'hot journal' left by a crash is automatically rolled back by the next process to open the file, and the commit point is journal deletion.

## S-010 (general)

If an application, OS, or power failure occurs mid-transaction, SQLite's partially written transaction should be automatically rolled back the next time the database file is accessed; SQLite is 'not immune' to corruption.

## S-011 (general)

SQLite recovery breaks if journals are interfered with: if hot journal files are moved, deleted, or renamed after a crash or power failure, automatic recovery will not work and the database may go corrupt.

## S-012 (general)

PRAGMA synchronous=OFF can corrupt an SQLite database on OS crash/power loss; SQLite should always be run with its default synchronous setting of FULL; WAL is more forgiving of out-of-order writes than rollback mode (only checkpoint needs a correct sync).

## S-013 (general)

SQLite database files are ordinary disk files; any process can open the file and overwrite it with garbage, there is nothing the SQLite library can do to defend against this, and there is no built-in access control — protection is whatever the OS filesystem permissions provide.

## S-014 (general)

POSIX advisory locking is buggy/unreliable on NFS; two or more clients might try to modify the same part of the same SQLite database at the same time, resulting in corruption.

## S-015 (general)

A close() on any file descriptor for a SQLite file in one thread cancels the POSIX advisory locks held by all threads of the process, which can lead to two or more threads or processes writing to the database at the same time and corrupting it; only partially fixed defensively in 3.51.0.

## S-016 (general)

Linking two copies of SQLite into one application, using two different locking protocols, unlinking/renaming the file while open, and multiple hard/symlinks to the file are all documented sources of SQLite corruption.

## S-017 (general)

Do not open an SQLite database connection then fork() then use that connection in the child process — locking problems result and the database can easily end up corrupt; under Unix an open SQLite database should not be carried across a fork() into the child process.

## S-018 (general)

A read-only mount of a WAL-mode SQLite database fails unless the -shm/-wal files already exist and are readable, or the directory is writable, or the database is opened immutable.

## S-019 (general)

OpenAI Agents SDK session guide assigns: SQLiteSession to local development and simple apps, AsyncSQLiteSession to async dev, RedisSession to shared session memory across multiple workers or services, SQLAlchemySession to production apps with existing databases (PostgreSQL, MySQL, SQLite, etc.), MongoDBSession to multi-process horizontally-scalable session storage, and DaprSession to production cloud-native deployments; the documented production path for concurrent workers is a shared-server DB or a single long-running app server that serializes access, not a shared SQLite file.

## S-020 (general)

SQLAlchemy sessions use SQLAlchemy to provide a production-ready session implementation, allowing use of any database supported by SQLAlchemy (PostgreSQL, MySQL, SQLite, etc.).

## S-021 (general)

OpenAI Agents SDK handles concurrency by identifying sessions by session_id (a row key), not by file ownership; multiple sessions share one conversations.db and different agents can share the same session.

## S-022 (general)

LangGraph makes the same split explicitly: SqliteSaver is 'ideal for experimentation and local workflows' while PostgresSaver (used in LangSmith) is 'ideal for use in production'.

## S-023 (general)

Estimate/opinion: neither OpenAI Agents SDK nor LangGraph documents 'many sandboxed workers sharing a single SQLite file' as a supported pattern; their documented answers are (a) serialize through one server, or (b) move to Redis/Postgres/MongoDB/Dapr; the single-file SQLite store is documented as the local/dev topology.

## S-024 (general)

LangGraph writes a checkpoint at each super-step boundary and persists per-node writes to a checkpoint_writes table so that if one node fails, successful nodes' writes are durable ('pending writes') and are not re-run on resume; resume restarts from the last successful step.

## S-025 (general)

LangGraph durability modes trade recovery vs. performance: 'exit' persists only on exit (no mid-execution recovery after a process crash), 'async' persists during the next step (small loss window on crash), 'sync' persists every checkpoint before the next step (high durability, performance cost).

## S-026 (general)

OpenAI sandbox agents recover sandbox work via serialized session_state and workspace snapshots (SnapshotSpec); in the SDK-owned lifecycle the runner persists snapshot-backed workspace state on shutdown, and stop() explicitly checkpoints the live workspace mid-lifecycle.

## S-027 (general)

At the SQLite layer crash recovery is the automatic hot-journal / WAL replay; framework-layer checkpoint/resume sits on top of that file-level guarantee.

## S-028 (general)

OpenAI Agents SDK automatically tracks token usage for every run: requests, input_tokens, output_tokens, total_tokens, per-request entries, and input_tokens_details.cached_tokens / output_tokens_details.reasoning_tokens; aggregated across tool calls and handoffs; usage is per-run and independent, and previous messages may be re-fed as input to each run which affects the input token count in subsequent turns.

## S-029 (general)

Persisting cost telemetry into the store is application-driven, not automatic: OpenAI AdvancedSQLiteSession provides detailed usage analytics by storing token usage per conversation turn, entirely dependent on the store_run_usage method being called after each agent run, into a turn_usage table keyed by (session_id, branch_id, user_turn_number).

## S-030 (general)

Anthropic returns a usage object on every Messages response described as 'Billing and rate-limit usage': input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens; total input tokens is the summation of input_tokens, cache_creation_input_tokens, and cache_read_input_tokens, and output_tokens is the inclusive, authoritative total used for billing; token counts will not match one-to-one with the exact visible content.

## S-031 (general)

Anthropic token counting (/v1/messages/count_tokens) is explicitly an estimate ('The token count is an estimate') and free, and you are not billed for system-added tokens.

## S-032 (general)

Anthropic telemetry pitfall: models since Opus 4.7 use a newer tokenizer producing approximately 30 percent more tokens for the same text, so token counts are not portable across models — don't reuse token counts measured on a model before Claude Opus 4.7 to estimate costs.

## S-033 (general)

OpenAI Agents SDK tracing records generation/function/tool spans with usage by default; in long-running workers the batch exporter flushes every few seconds, so for per-job delivery guarantees call flush_traces() after the trace context exits.

## S-034 (general)

OpenAI SDK architecture keeps state out of the sandbox by design: the outer runtime owns approvals, tracing, handoffs, and resume bookkeeping, while the sandbox session owns commands, file changes, and environment isolation; the conversational Session is explicitly distinct from a sandbox session.

## S-035 (general)

Sandbox manifests treat path grants as trusted config: treat manifests that contain extra_path_grants as trusted configuration, do not load grants from model output or other untrusted payloads unless the application has already approved those host paths, and read_only=True is recommended for host data the sandbox should not modify.

## S-036 (general)

Both OpenAI Agents SDK and LangGraph document encrypting persisted session state at rest: LangGraph EncryptedSerializer for checkpoints, OpenAI EncryptedSession wrapper (encryption + TTL on top of another session).

## S-037 (general)

Unverified/opinion: whether a single SQLite file is a viable store for many concurrent sandboxed workers is not documented by any vendor as a blessed topology; production frameworks instead document sharing via Redis/Postgres/MongoDB/Dapr or a single server, with SQLite reserved for dev/local.

## S-038 (general)

SQLite labels the WAL-reset bug's real-world occurrence rate as 'less than or equal to the expected occurrence rate of SSD malfunctions'; no reproducible stress evidence surfaced from primary sources.
