## S-000 (general)

rustc lints run during compilation and can produce a warning, an error, or nothing; warn-by-default lints exist because code "might be a bug" without being wrong.

## S-001 (general)

Lint levels are allow, expect, warn, force-warn, deny, forbid, configurable via -A/-W/-D/-F flags, attributes, or --cap-lints; forbid cannot be overridden downward and --force-warn takes precedence over everything.

## S-002 (general)

The `warnings` group covers all lints at warn level; #[deny(warnings)] lifts every warning to an error; unsafe_code is allow by default, so it is only caught after being raised into the warnings group.

## S-003 (general)

#[expect(C)] suppresses a lint but emits unfulfilled_lint_expectations if the lint does not fire — a mechanism that turns stale suppressions into errors.

## S-004 (general)

Future-incompatible lints give a warned transition period before behavior becomes a hard error (policy in RFC 1589).

## S-005 (general)

Cargo compiles dependencies with --cap-lints allow so dependency warnings do not pollute build output; force-warn lints are exempt from this cap.

## S-006 (general)

Official CI pattern: keep a project warnings-clean via build.warnings = "deny" (config) or CARGO_BUILD_WARNINGS=deny (env), then run cargo clippy --all-targets --all-features --keep-going.

## S-007 (general)

Official caveat: CI can fail due to new toolchain versions because there are limited compatibility guarantees around warnings; pinning the toolchain version with an automated toolchain-upgrade PR job is recommended.

## S-008 (general)

Since Cargo 1.97, CARGO_BUILD_WARNINGS is preferred over -D warnings because it does not invalidate build caches.

## S-009 (general)

Clippy is a collection of >800 lints with default levels: correctness = deny, suspicious/style/complexity/perf = warn (together clippy::all); pedantic, restriction, nursery, cargo are allow by default.

## S-010 (general)

Official warning: the clippy restriction group should emphatically not be enabled as a whole — it may lint perfectly reasonable code and lints may contradict each other; use case-by-case (e.g. unwrap_used).

## S-011 (general)

Official claim: clippy pedantic contains some very aggressive lints prone to false positives.

## S-012 (general)

Clippy CI integration documented by the project: rustup component add clippy; CARGO_BUILD_WARNINGS=deny cargo clippy --all-targets --all-features fails the build on any clippy or rustc warning; cargo clippy --fix auto-applies suggestions.

## S-013 (general)

rustfmt formats Rust code according to style guidelines; its default style conforms to the Rust style guide formalized through RFC 3338.

## S-014 (general)

CI gate: cargo fmt --all -- --check exits non-zero if formatting changes would be made.

## S-015 (general)

Post-1.0 formatting stability guarantees exist for whole programs, with listed carve-outs (macros, comments, non-ASCII, fragments).

## S-016 (general)

rustfmt has edition and style_edition config; rustfmt.toml options are split into stable and nightly-only.

## S-017 (general)

Unsafe grants exactly five capabilities (deref raw pointer, call unsafe fn, access/alter mutable statics, implement unsafe trait, access union fields); it does not disable the borrow checker.

## S-018 (general)

Official guidance: keep unsafe blocks small; wrap unsafe code in a safe abstraction prevents uses of unsafe from leaking out; SAFETY: comments on unsafe fns and blocks are idiomatic.

## S-019 (general)

Since Rust 2024, unsafe_op_in_unsafe_fn warns by default — unsafe ops inside an unsafe fn need an explicit unsafe block; the rationale (RFC 2585) determined the implicit allowance was too risky without explicit unsafe blocks.

## S-020 (general)

Miri is an official dynamic UB checker; it only flags UB in code paths actually executed and does not cover every possible way code can be unsound; the book demonstrates it catching a real dangling-pointer UB.

## S-021 (general)

The official unsafe reference is The Rustonomicon.

## S-022 (general)

Book guidance: returning Result is the default for fallible functions; panic! for unrecoverable bad state / violated contracts; expect/unwrap appropriate in tests, prototypes, examples, and where the programmer has more information than the compiler; encode invalid states in types.

## S-023 (general)

The panic-vs-Result choice is codifiable as lints: clippy restriction lints such as unwrap_used exist specifically to prevent panicking in certain functions on CI.

## S-024 (general)

The Rust API Guidelines are authored largely by the Rust library team and are explicitly only guidelines, not a mandate; they cover naming, interoperability, type safety, predictability, flexibility, dependability, debuggability, and future-proofing (including sealed traits, C-SEALED).

## S-025 (general)

The Rust API Guidelines claim crates that conform integrate better with the existing crate ecosystem — a claim of benefit stated without measurement in that document.

## S-026 (general)

Semver consequences of API design are catalogued in the Cargo Book: adding a non-defaulted trait item, changing trait signatures, tightening generic bounds, and adding enum variants without non_exhaustive are Major; adding a defaulted trait item or defaulted type parameter are Minor or Possibly-breaking; sealed traits and #[non_exhaustive] are cited as mitigation strategies.

## S-027 (general)

The Cargo Book SemVer chapter opens saying the rules are only guidelines, not necessarily hard-and-fast rules all projects will obey.

## S-028 (general)

cargo test runs unit tests in src, integration tests in tests/, compiles examples, and runs doctests.

## S-029 (general)

Proptest defines property testing as checking properties over automatically generated inputs with automatic shrinking to a minimal failing case; it positions itself as a complement to, not replacement for, hand-written unit tests.

## S-030 (general)

cargo-fuzz wraps libFuzzer, requires a nightly compiler, provides fuzz run, input minification (tmin/cmin), and coverage; the project maintains a trophy case of real bugs found by fuzzing.

## S-031 (general)

Fuzzing-efficacy is supported only by anecdata (the trophy-case list) in the sources reached; no controlled measurement is cited there.

## S-032 (general)

#![no_std] links core instead of std; core is a platform-agnostic subset with no libstd runtime; trade-offs include no heap without the alloc crate, no stack-overflow protection, no init code before main, and no OS abstractions.

## S-033 (general)

Semver-wise, switching from no_std support to requiring std is classified as a Major change — making a library std-only is a breaking release.

## S-034 (general)

The Cargo Book is the canonical classification of compatible/breaking changes (major/minor/possibly-breaking) and defines that 0.y.z bumps treat y as major; possibly-breaking items explicitly depend on maintainer judgment.

## S-035 (general)

cargo-semver-checks lints API diffs against the Cargo SemVer reference, supports deny/warn/allow lint levels and required-update (major/minor), has defined exit codes (0 clean, 100 violations, 101 error), and targets not to have false positives; its FAQ states it does not catch every violation.

## S-036 (general)

rust-toolchain.toml pins channel, components, and targets per-project and is suitable to check in to source control; the rustup book notes that if the toolchain is pinned to a specific release, Cargo.lock should probably be tracked too.

## S-037 (general)

Cargo's official CI chapter shows testing across stable/beta/nightly channels, verifying the rust-version field with cargo-hack/cargo-msrv, and a separate latest-dependencies job (with continue-on-error) to keep dependency ranges honest.

## S-038 (general)

The Cargo Book's CI chapter is the closest thing to an official CI gate spec: build+test on a channel matrix; warnings gate via CARGO_BUILD_WARNINGS=deny; a latest-deps job marked continue-on-error; a rust-version verification job; and explicit trade-off notes (exhaustiveness vs turnaround, CI cost, toolchain-upgrade churn).

## S-039 (general)

The fmt and clippy gates are documented by those projects themselves; neither the Cargo Book nor clippy/rustfmt READMEs present measurements of these gates' effect on defect rates.

## S-040 (general)

Every behavioral practice covered — warnings-deny in CI, small unsafe blocks, SAFETY comments, Result over panic, sealed traits, property-testing as a complement, toolchain pinning, the CI channel matrix — appears in primary sources as expert/official guidance supported by stated rationale, not by controlled or comparative measurement; none of the sources cites a study measuring defect-reduction effects.

## S-041 (general)

The closest things to evidence in the reached sources are (a) Miri demonstrably catching a concrete UB in the Book's worked example, and (b) the cargo-fuzz trophy-case list — both are existence proofs, not efficacy comparisons.
