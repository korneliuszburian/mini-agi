## F-000 `804ffb8a7c26c4aa`

Bazel's `flaky` test attribute executes a test up to three times, marking it failed only if it fails every time; default False (single execution). Its use is generally discouraged. (Bazel Build Encyclopedia)

## F-001 `f647744ca1f24b4f`

Bazel `--flaky_test_attempts` retries each failing test up to the specified count; tests needing more than one attempt are marked 'FLAKY' in the test summary. Default is one attempt for regular tests and three for tests marked flaky (flaky=1). Supports per-pattern targeting, e.g. --flaky_test_attempts=//foo/.*,-//foo/bar/.*@3.

## F-002 `fac277b31fa74875`

Bazel `--runs_per_test=N` runs every test N times and fails the test if any attempt fails; `--runs_per_test_detects_flakes` (default false) marks a shard FLAKY if at least one run passes and at least one fails.

## F-003 `3880083953a8f0d3`

Gradle Test Retry plugin retries failed tests within the same task up to maxRetries (default 0 = off); defaults: failOnPassedAfterRetry=false (pass-on-retry does not fail the task), failOnSkippedAfterRetry=true, maxFailures=0 (circuit-breaker cap off). Supports include/exclude filters by class name and annotations, plus whole-class retry (classRetry) for Spock @Stepwise/TestNG dependsOn. The README warns retrying tests alone is not a viable flaky-test mitigation strategy and should accompany tracking/fixing.

## F-004 `45d823a2f58dba76`

pytest-rerunfailures supports --reruns N, --reruns-delay with exponential backoff (delay for n-th re-run = reruns_delay * factor**(n-1), default factor 1.0), --only-rerun/--rerun-except regex filters, per-test @pytest.mark.flaky(reruns=5), --force-reruns overrides, --reruns-mode=append (additive marker+CLI counts), --max-suite-reruns suite-wide cap. Priority order: marker > CLI > ini.

## F-005 `bb634c81a4c4c097`

JUnit Pioneer @RetryingTest: maxAttempts is required and caps executions; minSuccess (default 1) requires the test to succeed that many times within maxAttempts; suspendForMs pauses between retries; onExceptions retries only on listed exception types. Assumption failures (aborts) are not retried; failed-then-passed executions are reported as aborted/ignored.

## F-006 `e6b84c294456ecd4`

Google denotes a test flaky so it reports failure only if it fails 3 times in a row, reducing false positives but encouraging developers to ignore flakiness; Google also supports re-running only failing tests and automatic re-run when tests fail. (John Micco, Google Testing Blog, 2016)

## F-007 `fb857bcd7b9b0020`

Google runs an automated quarantine tool that monitors test flakiness and, when flakiness is 'too high' (threshold not specified in the source), automatically removes the test from the critical path and files a bug to reduce flakiness; this could mask a real race condition or other bug. (Google Testing Blog, 2016)

## F-008 `24f290b647ef095e`

Kubernetes quarantines a single test by adding [Flaky] to its test name; most CI jobs exclude these tests, which run only in explicitly flaky jobs (e.g. the gci-gce-flaky job). Quarantining a presubmit test requires a release-milestone issue labeled priority/critical-urgent, lifecycle/frozen, and kind/flake, with the owning SIG expected to fix and reintroduce or delete the test. Whole-suite quarantine uses [Feature:Foo] names plus dedicated jobs, which merge-blocking suites avoid unless proven non-flaky.

## F-009 `a02663aaf66927cd`

Kubernetes has a 'zero-flake' policy: test jobs must not automatically retry on test failures. Effective 2019-12-13 (ginkgo.flakeAttempts=2 removed for e2e), confirmed as policy in 2023.

## F-010 `af500e05f86d5f38`

pytest.mark.xfail with strict=False can be used as a manual quarantine so a test's failure does not break the whole build, though it is rather dangerous to use permanently; the pytest API reference says strict=False is particularly useful to mark flaky tests (random failures) to be tackled later.

## F-011 `56702ea84de54b43`

Develocity/Gradle warns retry-only flake handling is not a complete solution: flaky tests go unnoticed and you will inevitably accrue more flaky tests. (gradle.com/blog/flaky-tests/)

## F-012 `d6354b5974db8518`

Develocity considers a test flaky if it fails and then succeeds within the same Gradle task or Maven goal execution, marking such tests FLAKY in build scans; retry is required to detect this, requires no code changes, applies to the whole suite, and enables proactive detection of newly introduced flaky tests. The Tests Dashboard ranks the most severe flaky tests and plots trends over time to confirm fixes.

## F-013 `d2375864da7ee620`

Google defines a flaky test result as a test exhibiting both a passing and a failing result with the same code, and reports a continual rate of about 1.5% of all test runs being 'flaky', almost 16% of tests having some flakiness, and about 84% of observed pass-to-fail transitions involving a flaky test; these figures are single-company 2016 self-reports. A second Google tool detects changes in a test's flakiness level and works to identify the change that caused it.

## F-014 `f8e399d3786cdd54`

Kubernetes flakiness detection tooling: flakes-latest.json (top 10 flakes per week across PR jobs), go.k8s.io/triage (interactive 2-week failure drill-down), testgrid's sort-by-flakiness view, the kind/flake GitHub label, and unit-test stress reproduction via golang.org/x/tools/cmd/stress with -race -count=1.
