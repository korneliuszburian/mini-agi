## F-000 `ce69ffc93f18ed5b`

Anthropic eval guidance defines good success criteria as Specific, Measurable, Achievable, Relevant, measured on a 'held-out test set' (e.g., 'F1 >= 0.85 on a held-out test set of 10,000 diverse Twitter posts').

## F-001 `bf6ba5ce46a474d0`

Anthropic eval design principles: be task-specific, 'automate when possible' (multiple-choice, string match, code-graded, LLM-graded), and 'prioritize volume over quality' (many automated-graded questions over fewer human-graded ones).

## F-002 `0950282a69d5217e`

Anthropic agent-eval practice: a good task is one 'where two domain experts would independently reach the same pass/fail verdict'; each task should be passable given a reference solution; 'a 0% pass rate across many trials (0% pass@100) is most often a signal of a broken task, not an incapable agent'.

## F-003 `33379f8028c507ae`

SWE-bench Verified (OpenAI, 93 professional annotators, each sample labeled 3x, ensembled by max severity) filtered out 68.3% of the original SWE-bench test set for underspecified problem statements (38.3%), unit tests that unfairly reject valid solutions (61.1%), or other issues.

## F-004 `4a75ebc1387e623f`

As-reported (Anthropic citing external sources): Opus 4.5 initially scored 42% on CORE-Bench and jumped to 95% after fixing rigid grading (e.g., penalizing '96.12' for expected '96.124991...'), ambiguous specs, and unreproducible stochastic tasks; METR likewise found misconfigured time-horizon tasks whose graders required exceeding the score threshold stated in the task.

## F-005 `fda4c8c9837bba04`

Anthropic grader taxonomy: code-based (fast, objective, reproducible, but 'brittle to valid variations'), model-based (flexible but 'non-deterministic', requires calibration with human graders), human (gold standard, calibrates LLM graders); recommendation is deterministic graders where possible and grading outcomes rather than tool-call sequences.

## F-006 `251b28fe96799da2`

## F-007 `99ec949f854d2660`

## F-008 `1ee6755802152b1d`

OpenAI collaborated with SWE-bench authors to build a Docker-containerized harness because SWE-bench environments were 'difficult to reliably set up... inadvertently causing unit tests to fail regardless of the solution'.

## F-009 `21114a6bac5e12fc`

Anthropic harness guidance: each trial must start from a clean, isolated environment; 'unnecessary shared state between runs... can cause correlated failures due to infrastructure flakiness rather than agent performance' (Claude was observed gaining an unfair advantage by reading git history from prior trials).

## F-010 `adc8bcda2c13dd44`

Anthropic: 'An eval suite is a living artifact that needs ongoing attention and clear ownership'; effective structure was dedicated evals teams owning infrastructure while domain/product teams contribute tasks; automated evals require ongoing maintenance as product and model evolve to avoid drift.

## F-011 `a7da537959884446`

Anthropic separates capability evals (low initial pass rate, a 'hill to climb') from regression evals (~100% pass rate, protect against backsliding); once capabilities plateau, high-pass-rate capability evals 'graduate' into a continuously run regression suite.

## F-012 `8313bde3b0ba0e0b`

'Test set contamination, wherein test data from a benchmark ends up in a newer model's training set, is a well-documented obstacle for fair LLM evaluation and can quickly render benchmarks obsolete.' (LiveBench)

## F-013 `30e358a2763714ce`

Magar & Schwartz (ACL 2022): pretrained models are trained on web corpora 'often contaminated' with downstream test sets; controlled experiments show exploitation 'exists in some cases, but in others the models memorize the contaminated data, but do not exploit it'; memorization vs exploitation is affected by duplication count and model size.

## F-014 `ea85a2da072f7a6a`

LiveBench mitigates contamination by (1) frequently updated questions drawn from recent math competitions, arXiv papers, news, and datasets ('questions are added and updated on a monthly basis'), and (2) harder 'contamination-limited' versions of prior benchmarks.

## F-015 `f718f7e999afdd74`

EleutherAI harness ships a 'Test Set Decontamination' utility scoring only 'data points not found in the model training set', via precomputed 13-gram exact-match indices against The Pile.

## F-016 `515eceaeb6949b62`

MLE-bench (agent benchmark from 75 Kaggle competitions) explicitly investigates 'the impact of contamination from pre-training' alongside its main results.

## F-017 `3cc8e5c15b13c683`

OpenAI states SWE-bench, being scraped from public GitHub repos, is 'likely to be contaminated' for models pre-trained on internet text, and that static datasets are 'inherently limited' — so they must be supplemented by other evals.

## F-018 `469930fe1449fcbf`

OpenAI Evals offers 'private evals' on a company's own data so teams represent common LLM patterns in their workflow without exposing that data publicly.

## F-019 `aa56393d93a19846`

Anthropic: because model outputs vary between runs, multiple trials are run for more consistent results; a task 'that passed on one eval run might fail on the next'; complementary metrics pass@k (at least one of k trials succeeds) and pass^k (all k trials succeed); for a 75% per-trial success rate, pass^3 is about 42%.

## F-020 `ef026a1a1cae7b2e`

## F-021 `beb33e0d0a29d161`

SWE-bench Verified identified three reliability problems: overly-specific/unrelated unit tests (false rejections), underspecified issue descriptions, and unreliable dev-environment setup; addressed via human annotation plus a containerized (Docker) harness.

## F-022 `b01301fb9acbfab8`

Anthropic failure-triage guidance: read transcripts to distinguish 'a genuine mistake' from 'graders rejected a valid solution'; design graders 'resistant to bypasses or hacks'; build partial credit for multi-component tasks.

## F-023 `30f149934a3231a5`

## F-024 `531ebba427c1608f`

Chen, Zaharia, Zou (2023): GPT-4 (March 2023) identified primes with 84% accuracy; GPT-4 (June 2023) scored 51% on the same questions; instruction-following decreased over that window; the 'same' LLM service can change substantially in a short time, 'highlighting the need for continuous monitoring of LLMs'.

## F-025 `01c89c6dfe6fb3b6`

OpenAI regression-eval recipe: define one eval (data source + grader), run a baseline run against the current prompt, then a candidate ('regression-run') after a prompt change; the lower score on the same dataset flags the regression before shipping.
