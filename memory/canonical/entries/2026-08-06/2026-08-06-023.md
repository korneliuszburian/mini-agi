Estimate: snapshot frequency bounds recovery time (replay length) and storage cost (archived WAL/old snapshots); no source gives universal numbers — the etcd example snapshot of 2.1 MB for 7 keys/rev 10 is illustrative, not a rule; choose checkpoint interval per write volume and RTO/RPO.

## F-001 `ecca3611145516e6`

Fowler's Event Sourcing: all changes to application state are stored as a sequence of events, enabling complete rebuild by re-running events on an empty application, plus temporal query and event replay; explicitly paired with snapshots (replay from an overnight snapshot on crash).

## F-002 `1c641abef370327a`

Event sourcing replay re-runs side effects, so external systems must be wrapped with a Gateway that can detect replay mode and suppress outbound calls — the same problem durable-execution platforms solve with idempotency.

## F-003 `a40757229890299e`

Temporal's durable execution is event sourcing in disguise: the workflow sends Commands mapped to Events persisted to a complete durable log; on worker crash, the worker uses the Event History to replay the code and recreate the workflow state as it was immediately before the crash.

## F-004 `a66abf4c0c1f97cf`

Temporal Durable Execution: a workflow maintains its state and progress across failures, crashes, or server outages because the Event History records state at each step and the execution resumes from the last recorded event.

## F-005 `dbc7cbf9a748d51b`

LangGraph uses a checkpointer that saves a snapshot of graph state at each super-step, organized into threads; if nodes fail at a super-step, the graph can be restarted from the last successful step.

## F-006 `b556d77f45006ee2`

LangGraph durability is tunable: "exit" persists only when execution exits (mid-run crash loses state), "async" persists while the next step executes (small risk of no checkpoint if the process crashes), "sync" persists synchronously before the next step starts — an explicit durability-vs-throughput trade mirroring WAL synchronous settings.

## F-007 `7fcceed280fcc7b0`

LangGraph separates full snapshots from finer-grained writes: per-node pending writes are written durably within a super-step so successful nodes are not re-run on resume, while time-travel/replay resumes only at full super-step checkpoints — snapshot-restore plus per-task delta.

## F-008 `a495d4c500ec01b5`

LangGraph documents an unbounded-growth failure mode: over long conversations checkpoints accumulate, increasing latency and storage costs; the fix is pruning or a retention policy (equivalent to compaction), and DeltaChannel stores deltas instead of full values to bound checkpoint size.

## F-009 `8b0d2fb3cb59a7d9`

AWS Step Functions: Standard workflows are durable and exactly-once with execution state persisting between transitions and full history retrievable; Express workflows are at-least-once (async) or at-most-once (sync) with no state persistence between transitions; retrying on at-least-once requires idempotent actions.

## F-010 `6665ad2250b0bf6a`

The three approaches (WAL+checkpoint, snapshot-restore, event sourcing) are one family, not alternatives: every credible system (PostgreSQL, SQLite, WiredTiger/MongoDB, RocksDB, etcd/Raft, Temporal, LangGraph, AWS Step Functions) combines an append-only, checksummed, order-preserving log with periodic state snapshots that bound replay.

## F-011 `8baa3b2f82d7faa6`

Opinion (sourced inference, not a measured study): the selector for agents is which failure you must survive and at what cost — WAL+checkpoint gives strongest crash consistency and minimal replay but needs a storage-engine contract and is overkill for small agent state; snapshot-restore is simplest with a bounded recovery window but loses everything since the last snapshot unless combined with a log (RPO = snapshot interval); event sourcing enables exact resume, audit, time travel, and human-in-the-loop review at the cost of side-effect duplication, unbounded history requiring compaction/pruning, and schema/version evolution of events.

## F-012 `649f2dd5755ff2c1`
