## F-000 `26963aa692752e78`

Default agent run state is in-memory in all major agent frameworks; persistence is an added layer. LangGraph splits it into checkpointers (thread-scoped short-term state) and stores (cross-thread long-term memory), and says persistence 'matters when an agent needs to continue a conversation, resume after an interruption, recover from a failure, or remember information across interactions'.

## F-001 `cacdebebd3626767`

OpenAI Agents SDK's built-in session memory (SQLiteSession) exists to avoid manually re-sending .to_input_list() history between runs.

## F-002 `b93d7d79db9d851e`

Microsoft's Agent Framework treats durability as an extension: 'An ordinary Agent Framework agent runs in-process: its conversation history lives in memory and is lost when the process ends.'

## F-003 `2b319322a0428380`

When frameworks add persistence, they route production durability to databases, not flat files. LangGraph's checkpointer table: MemorySaver/InMemorySaver = RAM, lost on restart; SqliteSaver = 'Ideal for experimentation and local workflows… local file-based storage for development'; PostgresSaver = 'used in LangSmith. Ideal for using in production.'

## F-004 `7b02843dca2475f6`

OpenAI Agents SDK built-in session backends: SQLiteSession is the default for 'local development and simple apps'; documented shared/multi-process paths are RedisSession ('shared memory across workers… low-latency distributed deployments'), SQLAlchemySession (Postgres etc.), MongoDBSession ('horizontally-scalable, multi-process session storage'), and DaprSession. Operational guidance: in-memory SQLite for temporary, file-based SQLite for persistent, Redis for shared low-latency, MongoDB for multi-process horizontally-scalable storage.

## F-005 `12fe0bcb03d20370`

Microsoft durable agents persist session state in external storage (Durable Task / Azure Storage) specifically to get multi-instance scale-out (any worker can resume a session), crash recovery, and human-in-the-loop waits of days/weeks with zero compute.

## F-006 `0f28c5715a50722b`

Checkpoint-style run state has a documented scaling cost: 'Over long conversations, checkpoints accumulate. This can increase latency and storage costs. Fix: prune old checkpoints or set a retention policy.'

## F-007 `e268c955dcf1bd2f`

By default LangGraph checkpoints write the full value of every state channel at each super-step; DeltaChannel stores only deltas, making checkpoint blobs 'O(1) per step instead of O(N)… at the cost of… storage-vs-latency tradeoff.'

## F-008 `330187df00ed1779`

LangGraph custom-checkpointer guidance: get-by-id must be 'O(1) or close to it'; 'A scan with a value filter on every lookup works but does not scale'; index design is correctness+performance-critical.

## F-009 `8c506f6dd07767f9`

LangGraph offers durability modes (exit/async/sync): 'exit' is fastest but 'you cannot recover from system failures (like process crashes) mid-execution'; 'sync' persists every checkpoint before continuing 'at the cost of some performance overhead.'

## F-010 `b7d8338a5de669c3`

Filesystem-as-state is used where human readability, git, and zero-infra win, with explicit first-party limits. Claude Code: the first 200 lines of MEMORY.md, or the first 25KB, are loaded at the start of every conversation; topic files are not loaded at startup but read on demand; auto memory is machine-local and files are not shared across machines or cloud environments; CLAUDE.md should target under 200 lines per file because longer files 'consume more context and reduce adherence.'

## F-011 `bf3e747ec837d4b4`

The MCP reference Knowledge Graph Memory Server persists the whole knowledge graph to a single JSONL file (MEMORY_FILE_PATH, default memory.jsonl) — a file-backed, single-process memory with no server-side DB.

## F-012 `4e221bfa0c5d7bc3`

OPINION (local first-party experience, not a benchmark): mini-agi is a filesystem-as-state agent kernel (canonical memory + a checkpoint journal); its AGENTS.md records file-based operational hazards — never restore the checkpoint journal through git (it destroys working-tree journal lines and orphans BEGINs; repair through checkpoint.sh only) and never chain a grep -c with && (a zero-match exits 1 and silently breaks the chain). This is documented pain from the flat-file model, not a measured comparison.

## F-013 `8d8f35ea68bf6ccc`

SQLite is an embedded database that is itself a file, and its own docs bound its scaling: 'SQLite does not compete with client/server databases. SQLite competes with fopen().'

## F-014 `2766f5af4ab026e3`

SQLite supports an unlimited number of simultaneous readers but only one writer at any instant in time.

## F-015 `3e5e18d029069f90`

Over a network filesystem, SQLite warns that file-locking logic is buggy in many network filesystem implementations, two or more clients might modify the same part of the same database at the same time resulting in corruption, and there is nothing SQLite can do to prevent it.

## F-016 `7c86cd916f6513f8`

SQLite lists 'very large datasets' and 'many concurrent writers' as cases where a client/server RDBMS 'may work better.'

## F-017 `73649fc34b71a4f6`

ESTIMATE (vendor design guidance, no published numbers in the sources reached): the scaling curve implied by LangGraph's and OpenAI's backend menus is roughly in-memory → SQLite file → Postgres/Redis/MongoDB, but neither publishes a benchmark for agent state at scale in the cited pages.

## F-018 `c65a4ce6cdb624b8`

Long-term cross-thread agent memory has a different shape than run state and is DB- or vector-store-backed in the frameworks. LangGraph's long-term memory is a Store abstraction (namespace + key + JSON value) with production backends PostgresStore, MongoDBStore, RedisStore, UpstashStore and optional semantic/vector search; the reference SQL schema uses TEXT[] namespace + JSONB value + GIN index.

## F-019 `d0090b3e0a85c898`

Microsoft Agent Framework ships a separate 'vector-stores-and-embeddings' feature area, i.e. durable memory is treated as a database/vector-store concern rather than a filesystem one.

## F-020 `5d0c374aed68c1f0`

Run state durability is not free in any architecture: default agent run state is in-memory and lost on process end, and even file-backed checkpoints grow unboundedly and need pruning/delta encoding.

## F-021 `28a317b7a861c29c`

All three major frameworks route production durability to databases, not flat files: LangGraph to Postgres ('Ideal for using in production'), OpenAI Agents SDK to Redis/SQLAlchemy/MongoDB/Dapr for 'shared', 'distributed', 'horizontally-scalable' memory, Microsoft to Durable Task external storage for 'multi-instance scale-out.'

## F-022 `ebcb42396b17bd81`

Flat-file memory is chosen for readability/git/zero-infra (Claude Code, MCP memory server) and its costs are explicit in primary docs: context-window limits (~200 lines/25KB), on-demand loading, and machine-locality (not shared across machines/cloud).

## F-023 `86bb11459302600d`

File/SQLite concurrency is bounded: one writer at a time, and network-filesystem file-locking bugs can corrupt state (sqlite.org); 'scale-out' and 'concurrent writers' are exactly the cases the primary docs route to client/server DBs.

## F-024 `f1bbc7cc63d0bf3b`

Uncertain: 'which scales better' is only answered as vendor design guidance, not measurement, in the sources reached; no published benchmark was found comparing flat-file vs SQLite vs Postgres for agent run state at load.

## F-025 `180a819281a6e18b`

Unverified: scale-out behavior of a flat-file model across many worker processes — both Claude Code and the MCP memory server are explicitly single-machine/single-process.
