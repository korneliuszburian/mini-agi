## F-000 `1f4b9fc62486cff6`

PostgreSQL REFRESH MATERIALIZED VIEW completely replaces the view contents by re-executing the backing query; stock PostgreSQL has no incremental refresh path, only full recomputation.

## F-001 `8097fca3fceebe45`

PostgreSQL REFRESH MATERIALIZED VIEW CONCURRENTLY still re-executes the full backing query; the option only avoids locking concurrent readers, requires a plain UNIQUE index covering all rows, and works only when the view is already populated.

## F-002 `e1f2e874ff8f4e1d`

Oracle fast refresh applies to the materialized view only the changes to master tables recorded in materialized view logs; COMPLETE refresh re-executes the defining query; FORCE (default) does fast refresh if possible else complete refresh.

## F-003 `6268ad4cbce610b0`

Oracle fast refresh requires materialized view logs to exist on the master tables at CREATE time, and eligibility for fast refresh is verified when the definition is created.

## F-004 `19fdc143f081ed4f`

Oracle offers three refresh timings: ON COMMIT (refresh as part of commit on a master table, may increase commit time), ON DEMAND (manual via DBMS_MVIEW, default), and ON STATEMENT (per-DML; only for fast-refreshable star/snowflake views that include the fact table ROWID).

## F-005 `cfddc08e47e6dcf7`

Oracle real-time materialized views avoid refreshing entirely: the optimizer writes a query combining existing MV rows with changes recorded in log files since the last refresh (on-query computation).

## F-006 `266b8325088b1614`

pg_ivm (PostgreSQL extension) computes and applies only incremental changes to materialized views, updated immediately in AFTER triggers when a base table is modified, instead of recomputing from scratch as REFRESH MATERIALIZED VIEW does.

## F-007 `3faec3e0b1d80803`

pg_ivm keeps incremental maintenance efficient via an automatically-created unique index (on GROUP BY columns, DISTINCT target list, or base-table primary keys) used as scan keys to locate affected rows.

## F-008 `60fdbe45190d2e94`

pg_ivm README shows a doc example where a single-row update costs ~20.6 s via full refresh vs ~15 ms as a base-table write for an incremental MV (doc-reported example timings).

## F-009 `1a17006009583ba8`

pg_ivm documents that IVM is not effective when a base table is modified frequently, or when a large part is modified or large data is inserted — maintenance cost can exceed refresh from scratch.

## F-010 `f481b98eb5ba6799`

CouchDB runs the map function over all documents only once, on first query; when a document is changed, the map function runs only once for that single document.

## F-011 `9b9296bb8b2fc470`

CouchDB invalidates per-document view rows via back-references and applies changes since the last query as a batch operation, since usually multiple documents change between queries.

## F-012 `d58edf0e65fb0f8f`

CouchDB caches reduce results in B-tree interior nodes, so range-aggregate queries are answered from cached partial reductions, recalculating only a minimum number of nodes.

## F-013 `8c38fd0e61beee75`

Changing a CouchDB view definition invalidates its index; views that change often and share a design document with others force those other views' indexes to rebuild from scratch when the design document is written.

## F-014 `3c52730566932ab6`

SQL Server indexed views are views with a unique clustered index; the optimizer can consider the view for substitution without it being referenced in the query, and DML on base tables must update referenced indexed views, so DML query performance can degrade significantly.

## F-015 `c6f1f175eb359cd1`

SQL Server indexed views are gated on determinism and precision: only precise deterministic expressions can participate in key columns and WHERE/GROUP BY clauses; plus fixed SET options, WITH SCHEMABINDING, and a restricted dialect (AVG must be expressed via COUNT_BIG + SUM; LEFT/RIGHT/FULL OUTER JOIN, subqueries, SELECT DISTINCT, window functions, and set operators are excluded).

## F-016 `33aa2b6ddca3a89e`

dbt incremental models build the table from all source rows on first run and transform only the rows the user filters for on subsequent runs; is_incremental() is true only when the target table exists, full-refresh is not passed, and the model is materialized='incremental'.

## F-017 `7b3058140a429de1`

dbt's standard incremental filter is a high-watermark against the derived table itself: where event_time >= (select coalesce(max(event_time),'1900-01-01') from {{ this }}); new-rows-only semantics suit append-only sources directly.

## F-018 `c436a95d905a7aa0`

dbt unique_key turns pure append into upsert semantics (update-or-ignore on match, insert on new), required to avoid bringing modified records in as duplicates; without it most adapters result in append-only behavior. incremental_predicates push predicates into the merge to limit scans of the existing table.

## F-019 `15355f27b297c061`

When dbt incremental logic changes, incremental results diverge from historical rows stored in the target table, so the model must be rebuilt via dbt run --full-refresh; the default on_schema_change policy is 'ignore', meaning a removed column makes the run fail.

## F-020 `ed80831515a47d10`

Materialize distinguishes plain views (results recomputed from scratch each access) from indexed and materialized views, whose results are persisted in durable storage and incrementally updated as new data arrives; indexed views keep the incrementally-maintained result in cluster-local memory.

## F-021 `855675ab421a6d0b`

Materialize rehydrates materialized views on restart from its own storage layer, not from upstream sources: hydration reconstructs in-memory state by reading Materialize's storage layer and does not require reading the upstream system.

## F-022 `ae4ee7c4c7369b1f`

BigQuery has two materialized-view classes: incremental views, which BigQuery precomputes/updates in the background from base-table changes, and non-incremental views, where every refresh runs the full query; freshness is served by reading rest of the data from the MV and only the changes from base tables.

## F-023 `5d32c1280761f55f`

BigQuery incremental eligibility is strict: incremental views support a limited feature set; AVG, ARRAY_AGG, and APPROX_COUNT_DISTINCT results are stored as intermediate sketches rather than final values; a deletion in a base table can force a full refresh (notably for BigLake sources) because the partition layout is what permits update-in-place.

## F-024 `6dbd271b7ce0e25e`

Incremental aggregate maintenance requires auxiliary state beyond the visible columns: pg_ivm adds hidden __ivm_count__/__ivm_count_avg__/__ivm_sum_avg__ columns and recomputes min/max from base tables when the extreme tuple is deleted (a documented slow path); BigQuery stores AVG/APPROX_COUNT_DISTINCT as sketches; CouchDB caches partial reduce values in B-tree nodes.

## F-025 `1a44ed072b912b06`

Consistency has a price on the write path: SQL Server DML query performance can degrade significantly on tables referenced by indexed views; pg_ivm immediate maintenance slows base-table writes and raises errors in REPEATABLE READ/SERIALIZABLE for multi-base-table views under concurrent updates; Oracle ON COMMIT may increase commit time.

## F-026 `16f2c921fa480440`

Staleness is an explicit knob: BigQuery max_staleness bounds lag at 30 minutes to 3 days (doc-stated, not measured); Materialize's reaction time is framed as freshness + latency (doc-reported, page not fetched directly); Oracle real-time MVs trade stored freshness for on-query computation; dbt's default is batch staleness bounded by run cadence.

## F-027 `8ab263a3dc129e33`

Five established mechanisms avoid full recomputation, all from primary docs: (1) delta-capture + replay via change logs/triggers (Oracle fast refresh + MV logs, pg_ivm AFTER triggers); (2) index-structured materialization updated per changed document (CouchDB B-tree views); (3) view-as-physical-index maintained by DML (SQL Server indexed views); (4) batch incremental pipelines with high-watermark + upsert keys (dbt); (5) continuous/streaming maintenance with durable or in-memory storage (Materialize, BigQuery incremental MVs).

## F-028 `53591a59c549819a`

All incremental-maintenance mechanisms impose eligibility constraints on the derivation (deterministic, restricted SQL), keep auxiliary state for incremental correctness, and expose a full-rebuild escape hatch and an explicit staleness/write-cost tradeoff.

## F-029 `e761f79662ed051f`

Transferable patterns for regenerating derived documents from append-only sources (source constraints are fact; the generalization is opinion): pure/deterministic derivation, a durable change/append log plus high-watermark position, keyed upsert for idempotent replay, incremental state stored adjacent to the output, an explicit full-rebuild path for when logic changes, and bounded staleness with in-place swap or merge.

## F-030 `f89a7953b2d236cf`

Kafka's log-compaction and EventStoreDB projections as mechanisms for derived state are unverified: the Kafka documentation site served only a JS redirect and EventStoreDB's projections docs were unreachable, so compacted-topic-as-derived-state and projection-over-event-stream claims must not be attributed to primary sources until fetched directly.

## F-031 `00d9b00db4beee22`

Oracle and BigQuery performance figures (refresh times, cost claims) are vendor-reported and unbenchmarked; the pg_ivm timing example is doc-reported; Materialize's reaction-time formula and BigQuery's max_staleness numeric range come from doc statements, not measured data.
