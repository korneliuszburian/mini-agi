- `9fd0d62f3cea36ac` DMR (Deep Memory Retrieval) is a task introduced in the MemGPT paper, built on the Multi-Session Chat (MSC) dataset; the agent is asked a question referring back to a prior conversation with a very narrow expected answer range, with QA pairs generated by a separate LLM instructed to write questions answerable only from the old chat log and not contained in persona information.
- `8de41cd967fdda17` DMR/MSC setup: MSC conversations have five sessions of ~12 messages, plus a new session 6 containing one QA pair; Zep reports DMR as a 500-conversation subset of MSC. Metrics are ROUGE-L plus an LLM judge scoring CORRECT/WRONG. Reported accuracies: GPT-3.5 Turbo 38.7% -> MemGPT 66.9%; GPT-4 32.1% -> 92.5%; GPT-4 Turbo 35.3% -> 93.4%.
- `672b4912c42144b2` DMR measures single-session-hop fact recall (opinion grounded in source): whether an agent can pull one specific fact out of a prior session; it tests retrieval/consistency, not updating, temporal reasoning, or abstention. Zep's primary text criticizes it: 'The evaluation relies exclusively on single-turn, fact-retrieval questions... Each conversation contains only 60 messages, easily fitting within current LLM context windows.'
- `94dcf0d91a61e711` LoCoMo is a dataset of very long-term conversations, each ~300 turns and ~9K tokens on avg. over up to 35 sessions, 50 dialogues, generated via a machine-human pipeline grounded in personas and temporal event graphs, including multimodal (image-sharing) turns.
- `1052dd5a927ed18a` LoCoMo has three tasks: (1) QA in five categories — single-hop, multi-hop, temporal reasoning, open-domain (commonsense/world) knowledge, and adversarial (designed to trick the agent into providing wrong answers, with expectation the agent identifies them as unanswerable); (2) event-graph summarization scored with FactScore against the ground-truth temporal event graph; (3) multi-modal dialogue generation scored with MMRelevance.
- `a6e2c69032154967` LoCoMo findings: long-context LLMs/RAG improve QA 22–66% but significantly lag human levels (by 56%), especially in temporal reasoning (by 73%); long-context models are especially prone to misassigning dialogs or events to the wrong speaker; gpt-3.5-turbo-16k scored 2.1% on adversarial questions. RoMem later classifies LoCoMo as the 'hybrid' benchmark: a mixture of dynamic temporal updates and general knowledge queries.
- `9cd6a6c67868558e` LongMemEval: 500 manually curated questions over task-oriented user-assistant histories evaluating five abilities — information extraction (IE), multi-session reasoning (MR), temporal reasoning (TR), knowledge updates (KU), and abstention (ABS); seven question types; two standard settings: LongMemEval_S (~115k tokens/question) and LongMemEval_M (500 sessions, ~1.5M tokens).
- `045bcab59e18db4a` LongMemEval KU definition: 'Ability to recognize the changes in the user's personal information and update the knowledge of the user dynamically over time.' KU error analysis states the retriever was only able to identify the updated knowledge but failed to retrieve the previous information before update, counted as retrieval failure.
- `0e8c9801a605c550` LongMemEval findings: long-context LLMs drop 30–60% vs. oracle retrieval on LongMemEval_S; commercial ChatGPT and Coze dropped 37% and 64% vs. offline reading; ChatGPT tended to overwrite crucial information as chat continues, while Coze often failed to record indirectly provided user information.
- `348e2784f9115e96` On knowledge-update and temporal reasoning: LongMemEval authors report 'Naive time-agnostic memory designs perform poorly on temporal reasoning questions'; time-aware indexing/query expansion improves temporal-reasoning recall by 6.8–11.3%; KU questions require retrieving BOTH pre-update and post-update evidence, with a store that drops the older fact counted as failed retrieval.
- `e286837b45d310e8` Static-dynamic dilemma (RoMem primary text): 'most existing approaches model time as discrete metadata, either sorting by recency (burying old-yet-permanent knowledge), simply overwriting outdated facts, or requiring an expensive LLM call at every ingestion step, leaving them unable to distinguish persistent facts from evolving ones.' Failure directions: recency sorting silently buries static knowledge (decades-old fact ranked below fresher irrelevant entries); disabling recency bias leaves temporal conflicts unresolved, confusing the downstream LLM. RoMem asserts its append-only store works only because contradictions are resolved geometrically at query time, and claims all existing baselines (Mem0, Zep, LicoMemory, HippoRAG) treat memory as a static snapshot, causing contradictory facts to cluster together in retrieval space and confuse the LLM.
- `9fd23bfe4eb2af7f` RoMem cross-benchmark numbers (single-paper, author-reported): LoCoMo Recall@10 (GPT-5-mini impl.) — Mem0 temporal 0.690, HippoRAG 0.645, Zep 0.553, A-Mem 0.691, RoMem 0.726; DMR-MSC MRR — Mem0 0.847, HippoRAG 0.848, RoMem 0.856, with naive-recency handling claimed to be precisely the behaviour naive recency-based approaches would destroy for static fact retrieval.

LoCoMo likewise: session-summary RAG does not improve QA, likely due to loss of information during conversion of dialogs to summaries.
- `dd8a402cb34e9585` Adversarial/abstention failures: facts never stored can't be abstained on — Coze often failed to record indirectly provided user information (implicitly-stated facts never enter the store), and compressed/overwriting stores corrupt prior facts over time (ChatGPT); LoCoMo's adversarial category (2.1% for a long-context model) is the same failure surface.

- `d71aa36a9e81bc8c` Seccomp is a syscall filter: a BPF program evaluated on struct seccomp_data (syscall number, arch, instruction_pointer, up to 6 raw register arguments) deciding KILL/TRAP/ERRNO/USER_NOTIF/TRACE/LOG/ALLOW. BPF cannot dereference pointers, which kernel docs credit with making the filter itself immune to the TOCTOU problems of syscall interposition frameworks (source: seccomp_filter.rst, seccomp(2)).
- `c7f2552aa3ba9e0c` Landlock is a stackable LSM restricting operations on objects (file hierarchies via filesystem access rights; TCP/UDP ports via network access rights since ABI v4/v10; IPC via scope flags since ABI v6), enforced on a thread and its descendants (source: landlock.rst, landlock(7)).
- `980038e5090eec8b` Kernel docs state: 'System call filtering isn't a sandbox... It is meant to be a tool for sandbox developers to use. Beyond that, policy for logical behavior and information flow should be managed with... potentially, an LSM of your choosing.' Direct corollary: seccomp alone is insufficient as a worker sandbox; an LSM layer (Landlock is one) is the documented complement (opinion derived directly from that statement).
- `a68feba40bd78382` Seccomp reduces the kernel syscall surface but cannot express path/object policy (no pointer deref); Landlock expresses path-based filesystem and port-based network policy but does not filter syscalls at all.
- `3f11178717f2bfc4` Capability gating: installing a seccomp filter requires prctl(PR_SET_NO_NEW_PRIVS, 1) or CAP_SYS_ADMIN; Landlock is documented as usable by unprivileged processes ('Landlock empowers any process, including unprivileged ones, to securely restrict themselves').
- `9e867896987f3592` Both seccomp and Landlock are one-way/irreversible: seccomp filters survive execve and can only be added to; Landlock: 'Once a thread is landlocked, there is no way to remove its security policy; only adding more restrictions is allowed.'
- `554ea35e5b4867b0` Landlock is kernel 5.13+ and opt-in at boot (lsm=...landlock...); its API is ABI-versioned (v1..v8+ as of 7.0), and features silently shrink per kernel unless the sandbox layer degrades explicitly. Seccomp BPF is CONFIG-gated (CONFIG_SECCOMP_FILTER) and has per-arch and kernel-version surface (e.g. the x32 nr fix in 5.4).
- `7c6f0eb74c7ce6fc` This repo's ADR-0012 chose Landlock write-containment for the worker (read+execute on the tree, write confined to workdir/state) over a full namespace sandbox, citing 'no root, no user namespaces, no external binary' and the binding risk being filesystem writes rather than network egress. The threat-model ranking ('writes are the real risk') is repo opinion.
- `1711f8ebaaa6ff1c` Landlock unmediatable operations: 'It is currently not possible to restrict some file-related actions accessible through these syscall families: chdir(2), stat(2), flock(2), chmod(2), chown(2), setxattr(2), utime(2), fcntl(2), access(2).' A worker can still stat/read metadata, chdir, lock, and chmod what it can reach.
- `d6f4e1893008deef` Landlock pre-existing FD escape: 'Files or directories opened before the sandboxing are not subject to these restrictions,' and such FDs keep their Landlock properties when passed between processes 'even when some of the involved processes do not have an enforced Landlock ruleset.' A worker that inherits pre-opened writable FDs from its parent retains write access.
- `9663caa7535ed43a` Landlock OverlayFS divergence: a policy restricting an OverlayFS layer 'will not restrict the resulted merged hierarchy, and vice versa' — an OverlayFS upper/lower/merge structure is outside the restricted hierarchy from Landlock's point of view.
- `dd98058876169ac0` Landlock Erratum 3 (documented privilege-escalation-class bug): 'it was possible to widen access rights through rename or link actions involving disconnected directories, potentially bypassing LANDLOCK_ACCESS_FS_REFER restrictions... could allow privilege escalation in complex mount scenarios.' Fixed only on kernels reporting the errata bit.
- `356b94ef83a50a9a` Landlock network support is late and partial: no network restriction before ABI v4 (kernel 6.7, TCP bind/connect only); UDP added in ABI v10. On older/backported kernels a best-effort policy silently drops network control. IPv4/IPv6 stream sockets that are not TCP (SMC/MPTCP/SCTP) were mis-gated by TCP rights before Erratum 1.
- `8926e976facd2be8` Landlock thread semantics: landlock_restrict_self restricts the calling thread and descendants; below ABI v8 (and at v8 without LANDLOCK_RESTRICT_SELF_TSYNC) a policy 'would only be enforced for the calling thread and its children (and not for all threads, including parents and siblings).' A multithreaded worker that restricts one thread can leave sibling threads unconfined.
- `7390cd3a09477737` Landlock truncate/ioctl subtleties: truncate is decoupled from WRITE_FILE (e.g. open(O_RDONLY|O_TRUNC) truncates without the write right); creat() needs the truncate right; fallocate(FALLOC_FL_COLLAPSE_RANGE) can shorten a writable file 'sidestepping the LANDLOCK_ACCESS_FS_TRUNCATE right'; several ioctls (FIOCLEX, FIONBIO, FICLONE, FIDEDUPERANGE...) are exempt from IOCTL_DEV.
- `b773707e3c794a0a` Landlock scope limits: LANDLOCK_SCOPE_* does not cover everything — a sendto() on an already-connected socket is not restricted, and IPC scoping 'does not support exceptions.'
- `ef358e65af2c75f9` Landlock does not and cannot filter syscalls or deny syscall-level primitives (e.g. ptrace of a peer is mediated via domain-subset rules, but no generic syscall kill).
- `d1df44ba19d24fa5` Seccomp: BPF 'may not dereference pointers,' so pathnames, buffers, and most argument content are invisible; only register values are visible.
- `d83a963660e3cc87` Seccomp deny-list bypass: an allow-list is strongly recommended 'because it is often possible to alter the representation of a value without altering its meaning, leading to a deny-list bypass.'
- `a0ae947f3627d7ca` Seccomp architecture/ABI confusion vectors: always check arch; on x86-64, the x32 ABI shares AUDIT_ARCH_X86_64 and a policy that does not account for __X32_SYSCALL_BIT 'can be bypassed by a malicious program that sets __X32_SYSCALL_BIT'; kernels before 5.4 permitted nr 512-547 plus x32-ORed forms that could invoke ptrace with confused x32-vs-x86_64 semantics.
- `7b032b76d2592172` Seccomp ptrace escape: 'seccomp-based sandboxes MUST NOT allow use of ptrace, even of other sandboxed processes, without extreme care; ptracers can use this mechanism to escape' (SECCOMP_RET_TRACE lets a tracer rewrite the syscall, and before 4.8 the check was not re-run after tracer notification).
- `59e0420458d34317` Seccomp no_new_privs requirement documents the setuid attack: the filter may be malicious against a setuid program — e.g. making setuid() appear to succeed without doing it, tricking a privileged program into keeping superuser privileges — which is why PR_SET_NO_NEW_PRIVS (or CAP_SYS_ADMIN) is mandatory.
- `76649269e1ba035d` Seccomp userspace notification (SECCOMP_RET_USER_NOTIF) reintroduces TOCTOU and is explicitly not a security mechanism: 'the seccomp user-space notification mechanism can not be used to implement a security policy'; SECCOMP_USER_NOTIF_FLAG_CONTINUE has a time-of-check/time-of-use race because the target can rewrite syscall arguments while blocked; a notifier 'can be bypassed if the existing filters allow the use of seccomp(2) or prctl(2) to install a filter' with higher-precedence action.
- `b917c9b0c660aa39` Seccomp PID-reuse race in the supervisor path: the pid in seccomp_notif can be recycled after the target dies; the documented mitigation is SECCOMP_IOCTL_NOTIF_ID_VALID between reading /proc/tid/mem and using the bytes, and 'a write by the supervisor into the target's memory can never be considered safe.'
- `6a6de58f8e958687` Seccomp vDSO/vsyscall bypass and quirks: syscalls served in userspace (e.g. clock_gettime, gettimeofday, time) never reach seccomp; vsyscall emulation honors seccomp but with documented TRAP/TRACE oddities.
- `7323ccdc175dbfdf` Seccomp argument truncation/visibility mismatches: seccomp sees the full 64-bit registers while the kernel may only consume the low 32 bits (i386-on-x86-64), so filters can misjudge actual semantics.
- `f63bce506848d83d` Seccomp unknown actions default to kill (kernel treats unknown action as SECCOMP_RET_KILL_PROCESS), so forward-compatibility mistakes tend to fail-safe; filter size caps: BPF_MAXINSNS 4096 per program, MAX_INSNS_PER_PATH 32768 total.
- `9a5b5080bf5a63c4` Landlock is an LSM layer stacked over DAC/other LSMs; seccomp constrains the syscall surface; kernel docs place both as composable hardening layers, and inheritance across clone/execve is analogous for both. Nothing in the primary sources documents a way to combine them into one primitive; each keeps its separate gaps.

- `ecca3611145516e6` Fowler's Event Sourcing: all changes to application state are stored as a sequence of events, enabling complete rebuild by re-running events on an empty application, plus temporal query and event replay; explicitly paired with snapshots (replay from an overnight snapshot on crash).
- `1c641abef370327a` Event sourcing replay re-runs side effects, so external systems must be wrapped with a Gateway that can detect replay mode and suppress outbound calls — the same problem durable-execution platforms solve with idempotency.
- `a40757229890299e` Temporal's durable execution is event sourcing in disguise: the workflow sends Commands mapped to Events persisted to a complete durable log; on worker crash, the worker uses the Event History to replay the code and recreate the workflow state as it was immediately before the crash.
- `a66abf4c0c1f97cf` Temporal Durable Execution: a workflow maintains its state and progress across failures, crashes, or server outages because the Event History records state at each step and the execution resumes from the last recorded event.
- `dbc7cbf9a748d51b` LangGraph uses a checkpointer that saves a snapshot of graph state at each super-step, organized into threads; if nodes fail at a super-step, the graph can be restarted from the last successful step.
- `b556d77f45006ee2` LangGraph durability is tunable: "exit" persists only when execution exits (mid-run crash loses state), "async" persists while the next step executes (small risk of no checkpoint if the process crashes), "sync" persists synchronously before the next step starts — an explicit durability-vs-throughput trade mirroring WAL synchronous settings.
- `7fcceed280fcc7b0` LangGraph separates full snapshots from finer-grained writes: per-node pending writes are written durably within a super-step so successful nodes are not re-run on resume, while time-travel/replay resumes only at full super-step checkpoints — snapshot-restore plus per-task delta.

- `8b0d2fb3cb59a7d9` AWS Step Functions: Standard workflows are durable and exactly-once with execution state persisting between transitions and full history retrievable; Express workflows are at-least-once (async) or at-most-once (sync) with no state persistence between transitions; retrying on at-least-once requires idempotent actions.
- `6665ad2250b0bf6a` The three approaches (WAL+checkpoint, snapshot-restore, event sourcing) are one family, not alternatives: every credible system (PostgreSQL, SQLite, WiredTiger/MongoDB, RocksDB, etcd/Raft, Temporal, LangGraph, AWS Step Functions) combines an append-only, checksummed, order-preserving log with periodic state snapshots that bound replay.
- `8baa3b2f82d7faa6` Opinion (sourced inference, not a measured study): the selector for agents is which failure you must survive and at what cost — WAL+checkpoint gives strongest crash consistency and minimal replay but needs a storage-engine contract and is overkill for small agent state; snapshot-restore is simplest with a bounded recovery window but loses everything since the last snapshot unless combined with a log (RPO = snapshot interval); event sourcing enables exact resume, audit, time travel, and human-in-the-loop review at the cost of side-effect duplication, unbounded history requiring compaction/pruning, and schema/version evolution of events.

- `f481b98eb5ba6799` CouchDB runs the map function over all documents only once, on first query; when a document is changed, the map function runs only once for that single document.
